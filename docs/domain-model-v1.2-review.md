## 2. P1-01 快照双层化完整验证

### 2.0 最终粒度结论

**E25 采用 Payment 级 + 转消费份额级（E25b）组合快照**。理由：

1. 一笔押金 Payment 同时承载**本金归属**与**多个独立转消费份额归属**，各份额可归属不同版本、不同行（D-39 金额份额互斥 + D-80b 规则 5"各份归属可不同"的直接结果）——Payment 级单条快照只有一个 budgetLineId，结构性无法表达多份额归属（本轮任务书指出的缺陷成立）。
2. 只做份额级也不行：份额快照回答"这份转消费归哪"，回答不了"原押金本金归哪"（D-72a 第 4 条要求能回答"这笔钱当时属于哪一版、哪一行、多少金额"）。
3. 两种粒度数据塞同一条记录会互相挤占字段语义（一条记录无法同时表示本金金额与份额金额而不歧义），违反任务书"不要强行塞入同一条记录"的告诫。故**双层组合**：各自回答各自的问题，键与生命周期互不干扰；快照均仅追溯、不参与计算（D-72a 第 4 条不变）。

### 2.2 场景 S1~S11 逐场景验证（任务书 §2.4 全清单）

每个场景给出：设定 / 快照记录数量与内容 / 清理前后状态 / 金额计算结果。

**S1 单笔押金、单次转消费**
- 设定：PAY-001 押金 500 → V1 住宿 BL-001；份额 C1 = 500 → V1 住宿 BL-001。
- 清理 V1 快照：E25 ×1（{PAY-001, V1, BL-001, LL-001, 住宿, 500, 500}）+ E25b ×1（{C1, PAY-001, V1, BL-001, LL-001, 住宿, 500, 500}），共 **2 条**。
- 前后状态：清理前 V1 完整、归属活引用；清理后 V1 删除，PAY-001/C1 悬空引用 + 各自快照，**均不转待归位**。
- 金额：清理前 V1 行已付 500、V1（指定版本）已付 500、口径 A 500、池 0；清理后旅行级指标不变（口径 A 500、全程现金 Q2=B 500），版本级失去主体。

**S2 单笔押金、多次转消费（同版本同行，D-80b 规则 5 允许）**
- 设定：PAY-001 押金 500 → V1 住宿；C1 = 200 → BL-001，C2 = 300 → BL-001。
- 清理 V1 快照：E25 ×1 + E25b ×2（C1=200、C2=300 各一条，键 (C1,V1)/(C2,V1) 不同），共 **3 条**。
- 金额：V1 住宿行已付 = 200+300 = 500；守恒 `500 = 0(池) + 500(转消费) + 0(退回)` ✓；口径 A 500。

**S3 多个转消费份额归属不同预算行（同版本）**
- 设定：PAY-001 押金 400 → V1 交通 BL-002；C1 = 250 → V1 住宿 BL-001，C2 = 150 → V1 交通 BL-002。
- 清理 V1 快照：E25 ×1 + E25b ×2，共 **3 条**。
- 金额：V1 住宿行已付 250、交通行已付 150、V1（指定版本）已付 400 = 口径 A 400；守恒 ✓。两份额各计一次，无重复。

**S4 多个转消费份额归属不同预算版本**
- 即 §2.1 标准场景：份额 A → V1、份额 B → V2。清理 V1 时 **E25 ×1 + E25b ×1 = 2 条**（份额 B 不在预检范围）；跨版本归属逐份额独立可追溯（问题 3/4/8 通过）。

**S5 部分退款后再转消费**
- 即 §2.1 标准场景的时间线：押金 500 → 退回 100（上限校验：剩余可退份额 500）→ 转消费 200 + 100（每次录入按剩余可退份额 400 校验）→ 池 100。守恒 `500 = 100 + 200 + 100 + 100` ✓；快照与指标见 §2.1。

**S6 转消费后再退款（现有需求允许：押金退回上限 = 剩余可退份额 = 原额 − 已转消费 − 已退回，§6.5/D-39）**
- 设定：PAY-001 押金 500 → V1 住宿；先确认份额 C1 = 200 → V1 住宿；后登记押金退回 300（上限 = 500 − 200 = 300 ✓）。
- 清理 V1 快照：E25 ×1 + E25b ×1，共 **2 条**；押金退回 REF-001 是独立支付记录，不受清理影响。
- 金额：池 = 500 − 200 − 300 = 0；口径 A = 200；全程现金（Q2=B）= 500 − 300 = 200。退款（押金退回）金额**不进任何已付**（只冲押金池），不会把 300 误当消费。

**S7 清理原始支付归属所在版本（份额归属另一版本）**
- 设定：PAY-001 押金 500 → V1 交通 BL-002；份额 B = 100 → V2 交通 BL-102。
- 清理 V1 快照：**E25 ×1（PAY-001 → BL-002）+ E25b ×0**（无份额归属 V1 行），共 **1 条**。
- 前后状态：V2 与份额 B 完全不受影响；V2（指定版本）已付 100 不变。
- 金额：口径 A 100、池 400、全程现金（Q2=B）400，清理前后均不变。

**S8 清理转消费份额归属所在版本（本金归属另一版本）**
- 设定同 S7，但清理 **V2**：预检——归属 V2 行实例的 Payment = ∅（PAY-001 在 V1），DepositConversion = {B}。
- 快照：**E25 ×0 + E25b ×1（{B, PAY-001, V2, BL-102, LL-002, 交通, 400, 100}）**，共 **1 条**。
- 前后状态：V1 与 PAY-001 完全不受影响；份额 B 悬空引用 + 快照可追溯。
- 金额：V1（指定版本）已付 0、口径 A 100、池 400——清理前后不变（快照不参与计算）。

**S9 不同版本分批清理（含同一主体跨两次清理）**
- 分批（标准场景）：先清 V1 → 快照键 (PAY-001,V1)、(DC-A,V1)；后清 V2 → 快照键 (DC-B,V2)。三键互不相同，**无重复、无覆盖**；两轮清理之间互不触碰对方的快照。
- 同一主体跨两次清理：PAY-002 流出类 300 → V1 住宿 → 清理 V1（生成 E25(PAY-002,V1)）→ 用户显式转移到 V3 住宿行 BL-301（支付转移审计，BC-30 累计校验）→ 清理 V3（生成 E25(PAY-002,V3)）。**两份 E25 并存**，分别记录两个清理时点的真实归属；"PAY-002 的原始归属是 V1"由归属建立审计链回答（§4.13 快照与审计链分工），快照不覆盖、不丢历史。

**S10 清理失败与撤销清理**
- 失败：任一步（预检/生成/校验）失败 → 清理整体不生效。因快照与清理**同批写入**，失败整批回滚：版本完整、无悬空引用、无快照残留、给出可见错误（DM-08）。
- 撤销清理：撤销栈数据快照恢复版本完整内容；本次清理生成的快照**随数据回退一并消失**；悬空引用回到活引用。此后再次清理会重新生成**同键同内容**快照，不产生重复记录（§7.7 多次清理规则 4）。

**S11 清理后继续进行合法的归属调整**
- 活主体调整：份额 B（→V2）改归属 → 正常归属变更审计（before 冗余信息取自活数据）。
- 悬空主体调整：PAY-001 / 份额 A（悬空引用 BL-001）显式转移/改归属到 V2 住宿行 BL-101 → 生成对应审计，**before 的冗余信息取自其快照**；转移受 BC-30 累计校验（BL-101 已有支付 + 转入 ≤ 600）。
- 金额验证（份额 A 200 转归 BL-101）：BL-101 行已付 +200、V2（指定版本）已付 100 → 300；全程现金与口径 A 不变；既有快照保留（历史事实），悬空历史引用被活引用替换，不等于"待归位"。

### 2.3 验证结论

## 4. 金额守恒检查

1. **押金守恒（DM-05，未改动）**：`原额 = 押金池 + Σ已转消费 + Σ已退回`。标准场景 500 = 100+200+100+100 ✓；S6（先转后退）500 = 0+200+300 ✓；录入端按剩余可退份额校验（AC-LED-19k/19l）。
2. **快照零参与（DM-08）**：E25/E25b 全部字段不进任何现金指标——口径 A/B/C、行已付、版本已付的取数路径与 v1.1 完全一致，双层快照只是"展示层恢复被删行的信息"，不存在"快照金额被当消费统计"的通道。任务书问题 7（重复统计）在 §2.1 量化验证为否。
3. **本金与份额不叠加**：押金本金只在押金池式出现；转消费按份额计入口径 A 与归属行的已付；两者对同一笔钱各表达一个去向（互斥份额），不是两笔钱。
4. **退款（押金退回）永不进已付**：只冲押金池（D-80b 规则 3）；S6 验证转消费后再退款不会把退款误计为消费。
5. **纠错不改金额（DM-10）**：跨分类纠错只改类型字段，金额/日期/归属不变，全部口径按新分类重算；纠错前置保证离开押金类的记录份额清零（无转消费、无关联押金退回），DM-05 对仍属押金类的记录继续成立，守恒不被破坏。
6. **版本清理不影响旅行级指标**：口径 A、全程现金总额、押金池均与归属/版本无关，清理前后不变（§2.1 对照表）；只有行级/版本级指标随被清理版本失去汇总主体——这是 D-72a 第 4 条"清理版本完整内容"的预期行为，不是数据丢失。
