## 2. P1-01 验证：清理时点类型与历史退款上限复原

### 2.0 缺口确认与修复概述

审查判定成立：v1.2.1 的上限恢复规则写的是"支付类型从活记录读取，类型永不悬空"——这在模型允许**支付类型纠错**（v1.2 P2-02）后不成立：清理之后发生的纠错会改变活记录的类型，用当前类型反推清理时点的基数会失真。修复四件套：

1. E25 新增 `paymentTypeAtCleanup`（清理时点类型）；
2. 上限基数按 `paymentTypeAtCleanup ∈ 流出类` 判定，禁止以当前类型反推；
3. **快照一经生成不可改写**（纠错、金额调整、改关联均不回写快照）写入共同规则与 DM-08；
4. 快照/审计分工扩含类型：**快照记时点事实（清理时什么类型、多少金额），审计记变更过程（何时从什么改成什么）**。

### 2.1 基础场景设定

| 对象 | 设定 |
|---|---|
| V1 | 住宿行 BL-001（LL-001，金额 5000） |
| PAY-01 | 预付款 1000，归属 BL-001 |
| PAY-02 | 尾款 4000，归属 BL-001 |
| PAY-03 | 押金 800，归属 BL-001（未转消费） |
| REF-01 | 退款 500，refundTarget=预算行，refundTargetId=BL-001 |
| 清理时点基数 | PAY-01 + PAY-02 = **5000**（PAY-03 为押金不计入基数）；累计退款 500 ≤ 5000 ✓ |

清理 V1 生成快照：E25×3（PAY-01{类型=预付款, 1000}、PAY-02{类型=尾款, 4000}、PAY-03{类型=押金, 800}）+ E25c×1（REF-01{500}）。

### 2.2 五场景推演（任务书要求全清单）

**S-A 清理前：预付款纠正为押金，再清理**
- 纠错前置核查：PAY-01 无指向它的单笔关联退款（REF-01 是行关联）；新增前置——纠错后行基数 5000−1000=4000 ≥ 累计退款 500 ✓ → **允许纠错**。
- 清理 V1：E25(PAY-01).paymentTypeAtCleanup=**押金**；基数复原 = PAY-02 的 4000（PAY-01/PAY-03 均按清理时点类型排除）。
- 结果：**历史退款上限按清理时点准确恢复为 4000**；500 ≤ 4000 ✓。若错误地用纠错前的"预付款"身份推 5000，反而失真——快照记的是清理时点事实，纠错发生在清理前就反映在快照里。

**S-B 清理后：预付款纠正为押金**
- 先按基础场景清理（E25: PAY-01 类型=预付款，基数复原 5000）；随后纠错 PAY-01 → 押金（无单笔关联退款指向它；所在行已悬空，行基数守卫不适用——历史已由快照固定）。
- E25 **不变**（paymentTypeAtCleanup 仍=预付款）→ **历史上限仍复原为 5000**（清理时点它是流出类）；活世界按新分类重算（押金池 +1000），历史不受影响。纠错审计记录 before=预付款/after=押金，与快照分工清晰。

**S-C 清理后：押金纠正为预付款**
- PAY-03（押金 800）纠错 → 预付款（前置：无转消费份额、无关联押金退回 ✓）。
- E25 **不变**（PAY-03 清理时点类型=押金）→ **历史上限仍复原为 5000，而不是 5800**——这正是本字段的动机案例：若以当前类型反推（PAY-03 现在是流出类），会错误地把 800 算进历史基数。

**S-D 清理后：预付款金额发生调整**
- PAY-02 由 4000 调整为 3500（金额调整审计 before=4000/after=3500）。
- E25.paymentAmountCents **不变**（清理时点 4000）→ **历史上限仍复原为 5000**（1000+4000）；活世界口径按 3500 重算。快照不覆盖、审计记录过程，分工与任务书第 6/7 条要求一致。

**S-E 清理后：退款关联目标发生调整**
- REF-01 的悬空行关联（BL-001）显式改关联为 PAY-02（D-40 二.5 调整，审计 before 的冗余信息取自 E25c：BL-001（V1）/after=PAY-02）。
- E25c **不变**（清理时点按整行关联 BL-001）→ 历史答案不变："REF-01 在清理时点按整行关联 V1 住宿行、金额 500"；累计退款（清理时点）= 500；上限 5000。改关联只改变活世界的冲减对象，审计记录变更过程。

**五场景总结论**：无论纠错/调整/改关联发生在清理前还是清理后，历史退款上限与关联语义**始终按清理时点状态复原**（4000 或 5000，视清理时点事实而定）——判定依据是 E25.paymentTypeAtCleanup + 不可改写的快照金额，绝不使用当前活记录类型反推。

## 3. P1-02：冲减类归属字段适用范围——冻结需求逐条对照（问答 + 论证）

**审查判定成立**：v1.2.1 把"冲减类不适用归属字段"写成定案式"澄清"，超出了冻结文本可唯一界定的范围。v1.2.2 逐条对照五处冻结条款后**改列待人工裁决**（§4.11 裁决段 + §15 P2-7）。

### 3.1 逐条对照

| 条款 | 原文要点 | 对冲减类归属的说明力 |
|---|---|---|
| **D-40**（退款冲减） | 退款必须关联具体费用条目或具体支付记录；无法关联→未关联退款并显式提示；上限按关联方式 | 只定义**关联方式**（refundTarget 语义），全文无"退款需有归属对象/归属状态"的要求；退款取数只经关联。→ 两读法均兼容，无唯一结论 |
| **D-80**（归属定义与三形态） | ①集合口径："支付记录是唯一的、统一的集合：每一笔实际发生的付款就是一条支付记录；**归属对象是它的一个取值**（预算行/预算外/空）"；②三形态表（计划内"✅ 进入该预算行的实际支付"/预算外/待处理）；③类型清单含退款/押金退回 | **两读法的分水岭**：读法 B（全类型携带归属）依据 ①的字面（每条记录有归属取值）；读法 A（归属适用于流出/押金类的钱）依据 ②——退款"进入预算行的实际支付"不可能成立（退款只冲减），且"待处理支付"的语义是"钱付了归属未定"（D-87a），冲减记录不是待归属的钱。→ **文本可两读，无唯一结论** |
| **D-80b**（三分类与口径） | 口径 A/B/C 与押金池式的完整取数路径 | 退款只以"Σ 退款"减项出现、押金退回只在押金池式出现；**不存在任何按归属过滤冲减类的公式路径**。→ 两选项下所有公式取值完全一致 |
| **D-81**（已付） | 已付口径"退款只作减项"；行已付公式取"关联该行的退款" | 取数锚点是**关联**（refundTarget），不是归属。→ 两选项无差异 |
| **D-87a**（三现金指标） | 全程现金总额 = 口径 B/C；"待处理支付"段："钱确实付了，只是预算归属未定" | Σ 退款整体扣减、与关联方式无关；待处理段描述的是付款的钱。→ 两选项无差异 |

### 3.2 四问逐条回答

1. **D-80 的三种归属形态是否适用于所有 Payment 类型？** 冻结文本未唯一界定："一笔支付…归属对象是它的一个取值"可读为全类型适用（读法 B），三形态表的"进入该预算行的实际支付"列又只对流出/押金类的钱成立（读法 A）。**待人工裁决。**
2. **退款的 refundTarget 是否独立于 ownershipType？** **是**（两读法下均独立）：refundTarget 决定冲减对象与退款上限（D-40/I-20d），是统计取数锚点；归属字段（无论存在与否）不参与任何冲减统计。此问答与裁决无关，模型已按此实现。
3. **冲减类是否应保留归属字段但不参与归属统计？** 这正是**选项二**：可行且与全部公式兼容；需追加裁决"归属为空时是否判待归位"（判则与 D-87a"待处理支付=已付款归属未定"的语义不符；不判则实质回到选项一的限定）。**待人工裁决。**
4. **完全不适用（选项一）如何证明兼容？** 逐条如 §3.1：所有统计公式（D-80b 口径 A/B/C、押金池式、D-81、D-87a）无冲减类归属路径；D-40 只定义关联方式；因此选项一**不违反任何公式**；但 D-80 集合口径句的存在使命题"唯一"不成立 → **列待裁决而非定案**（本模型登记取向仍为选项一，供终审确认或推翻）。

### 3.3 裁决无关性声明（重要）

无论最终裁决为选项一还是选项二：**全部现金指标取值、三层快照内容与生成规则、类型纠错机制、退款上限恢复规则均不变**——两选项的差异仅在归属字段的存在性与展示语义。因此本项裁决不阻塞其余部分的审查与实现准备。
