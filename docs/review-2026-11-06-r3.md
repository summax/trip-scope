## 二、新引入的问题

### R1【低】草稿箱删除"当前正在编辑"的草稿会被 pendingDraft 复活

- **实测**:编辑中(300ms debounce 未到)→ 打开草稿箱 → 删除当前旅行草稿 → 等 1.2s 后草稿键**重新出现**:

```
删除前存在 = true ; 删除后草稿键 = ["tripscope:draft:09654321-…"] ; 复活 = true
```

- **边界确认**(我特意测了对照):删除**非当前**旅行(旧草稿)时,pending 不会牵连,旧草稿真的删掉了(`剩余名 = ["B当前"]`,旧草稿消失)。所以影响面仅限"删除自己正在编辑的那份"。
- **根因**:`deleteFromPanel`(`store.ts:521-525`)只做 `deleteDraft(id)`,没有清 `pendingDraft`;300ms 后 `flushDraft()` 把排期快照写回同一个键。

```ts
export function deleteFromPanel(id: string): void {
  deleteDraft(id)
  refreshDraftsPanel()
  setToast('草稿已删除')   // ← 可能随后被复活,提示失真
}
```

- **影响**:用户看到「草稿已删除」,但草稿又回来了。不是数据丢失(方向相反,是删不掉),但提示与事实不符,且用户会困惑「为什么删了还在」。刷新面板后该行消失,再刷新又会回来。
- **修法**(二选一):
  - **A. 删当前草稿时连 pending 一起清**:

```ts
export function deleteFromPanel(id: string): void {
  if (pendingDraft && pendingDraft.node.project.id === id) pendingDraft = null
  deleteDraft(id)
  refreshDraftsPanel()
  setToast('草稿已删除')
}
```

  - **B. 删除后立即 `flushDraft()` 再删**,顺序反过来:先落盘(把 pending 写掉),再 `deleteDraft`,确保最终态是删掉的。
- 建议 A,语义更直接。

### R2【极低】草稿箱无数量上限

面板一次性渲染全部草稿,无分页/折叠。骨架阶段可接受;若长期积累几十份,面板会很长。可与"新建旅行时询问是否清理旧草稿"一起考虑。

## 四、数据安全回归确认(重点)

这轮改动触及草稿层的核心路径,我重点复核了"会不会破坏原有安全承诺":

| 承诺 | 复核结果 |

| 高版本只读 | RH5 仍 PASS(v99 草稿恢复 → 只读 + 输入禁用);草稿箱走 `restoreDraftNode` → `admitNode`,无旁路 |

| 节点唯一性 | 产物 strict 命中 = 1;`replaceDataNode` 用捕获组开标签,不再 `indexOf` |
| `<` 转义 | S5b / S5f / S5h 全 PASS(`</script>`、emoji 往返一致) |
| 损坏数据不写回 | S6d PASS(原文件未被覆盖);RN3 确认损坏草稿恢复不离开安全屏 |
| 草稿不静默删除 | H4 / RH4a-b PASS;新增草稿箱让"删"变成用户显式动作 |

**结论:本轮改动没有让任何一项原有安全承诺退化。**
