## 一、高优先级

### H1. 仓库里的示例文件是过期产物,「另存为副本」必然失败

- **现象**:双击 `examples/示例旅行.html` → 点「另存为副本」→ 无任何反应、无提示、文件未生成。
- **证据**:`DataCloneError: Failed to execute 'structuredClone' on 'Window': #<Object> could not be cloned. at Do (示例旅行.html:7:67032)`;`window.__savedContent === null`;页面无 toast。
- **根因**:`examples/示例旅行.html` 构建时间 18:57,而 `deepClone` 从 `structuredClone` 改为 JSON 往返是 19:09 的改动(`af2fe10`)。产物未随代码重建,烂在版本库里。`dist/trip-scope.html` 无此问题(实测同一操作写出 113948 字符、零错误)。
- **影响**:示例文件是 README 首推的「打开就能用」入口,对第一次接触这个项目的人是**开箱即坏**。

**修法**
1. 立即重建并提交产物:`npm run build && npm run example`。
2. 根治 —— 把示例重建绑进构建,禁止出现「代码已改、示例未建」的提交:

```jsonc
// package.json
"build": "vue-tsc --noEmit && vite build && node scripts/rename.mjs && node scripts/build-example.mjs"
```

3. 加产物守卫:在 `build-example.mjs` 末尾断言示例里不含已移除的 API(或直接断言示例与 `dist` 的数据节点解析结果一致),让这类漂移在构建期就失败而不是上线后。

### H2. 失败在 UI 上完全不可见(静默失败)

- **现象**:H1 的失败从头到尾没有任何用户可见反馈 —— 无 toast、无横幅、无禁用态变化,只有 console 有一行错误。用户会认为「点过了 = 存好了」。
- **证据**:`window.__unhandledrejection = []`、toast 节点数 `0`、页面文本无「操作失败」。错误被 Vue 运行时 `callWithAsyncErrorHandling` 的 `.catch` 捕获后**只做 console 输出**;该产物缺少 `app.config.errorHandler`(由 `af2fe10` 才加入 `src/main.ts:10-13`)。
- **根因**:错误可观测性依赖单一兜底(`app.config.errorHandler`),而
  - 过期产物里这层根本不存在;
  - 即使存在,它也**只覆盖经 Vue 调度器调用的处理器**。`scheduleDraft` 的 `setTimeout` 回调、以及任何未被 `return` 给 Vue 的 promise 链,都不在它的覆盖范围内;
  - 全仓没有 `window.addEventListener('unhandledrejection', ...)`,漏网即静默。

**修法(三层,缺一不可)**
1. **动作自带 try/catch**:每个导出给 UI 的 `async` 动作失败必 `setToast`。当前 `saveAsCopy()`(`src/core/store.ts:308-328`)的 `deepClone` 在 try 之外抛出,是典型样本:

```ts
export async function saveAsCopy(): Promise<void> {
  if (!canEdit() || !state.node) return
  try {
    const clone = deepClone(state.node)
    // …既有逻辑
  } catch (e) {
    surfaceError(e)   // 保证「失败必可见」
  }
}
```

需要同样处理:`save`、`openHandleFile`、`importFile`、`resolveExternalConflict`。

2. **全局兜底补一层**(`src/main.ts`):

```ts
window.addEventListener('unhandledrejection', (e) => {
  console.error(e.reason)
  surfaceError(e.reason)
})
```

3. **验收断言改成「二选一必成立」**:点击保存类按钮后,**要么出现 toast、要么文件已生成**;两者都没有即判 FAIL。现有 53 项断言全是「正向路径必成功」,没有一条能抓住「静默失败」——这正是 H1 能带着 bug 进仓库的原因。

### H3. 「新建旅行」后刷新/关标签页,未保存内容彻底找不回

- **现象**:新建旅行 → 输入内容 → 未保存就刷新 → 内容全空,且**没有任何恢复入口**。与 README「编辑内容始终有 localStorage 草稿兜底」直接矛盾。
- **证据**:刷新前草稿键 `tripscope:draft:f9974d4e-…` 已写入;刷新后该键**仍然存在**,但输入框为空、无草稿横幅。
- **根因**:两处配合失误
  - `src/core/store.ts:217-224` — `newTrip()` 立刻把 `project.id` 换成新 UUID;
  - `src/core/bootstrap.ts:28-37` — 空白工具启动时**只**查 `loadDraft(BLANK_TOOL_ID)`,永远查不到那个 UUID 草稿。
  - 结果:草稿变孤儿,占着 localStorage 配额却再也读不回来。

**修法(推荐 A)**
- **A. 延迟固化 UUID**(改动最小):`newTrip()` 沿用 `BLANK_TOOL_ID`,`save()` 首次落盘时才 `newId()`。这段「空白工具首次保存固化真实 UUID」的逻辑 `src/core/store.ts:295-298` 已经写好并配有 `deleteDraft(BLANK_TOOL_ID)`,把 `newTrip` 里的提前分配删掉即可,自动恢复原语立刻生效。
- **B. 启动时恢复孤儿草稿**:空白分支在 `BLANK_TOOL_ID` 无草稿时,用 `listDrafts()` 列出候选交用户选择。需要新增「孤儿判定」,复杂度更高,收益重复(A 已解决)。

必须补验收:新建 → 输入 → 刷新 → 内容仍在。

### H4. 只改项目名会被判成「冗余草稿」静默删除

- **现象**:草稿里项目名是 `2027 国庆云南旅行`,重新打开同一文件后显示 `未命名旅行`,草稿被清空,无横幅、无提示。
- **证据**:打开前草稿键存在 → 打开后草稿键 `[]`;无「检测到较新的本地草稿」横幅;输入框为文件里的旧名。
- **根因**:`src/core/persistence/storage.ts:71` 的 `contentEquals(d.node.data, fileData)` **只比 `data`,不含 `project.name`**。只改名不改数据 → 判为「与文件一致 → 冗余 → 静默删除」。
- **注意**:`updatedAt` 不参与比较是**刻意的正确设计**(时间戳不该触发误报),不要为了修这个 bug 把时间戳拉进来。

**修法**
把「内容一致」的定义扩到「用户可见的持久字段」。考虑到后续还要加日期/交通/住宿等字段,建议用「抹掉时间戳后整节点比对」而不是逐字段列举,天然抗新增字段漂移:

```ts
// schema.ts
export function userVisibleEquals(a: TripNode, b: TripNode): boolean {
  const strip = (n: TripNode) => ({ ...n, updatedAt: '', appVersion: '', schemaVersion: 0 })
  return JSON.stringify(strip(a)) === JSON.stringify(strip(b))
}
```

```ts
// storage.ts —— resolveDraftOnOpen(node: TripNode, file: TripNode)
if (userVisibleEquals(d.node, file)) { deleteDraft(id); return { entry: null } }
```

调用点 `src/core/store.ts:148` 相应改为传入整个节点而非仅 `data`。

> **这是本次最值得警惕的一类 bug**:它不会报错,只会让用户「改了、保存了、下次打开发现没改」,且事后无法追溯。修复必须配验收断言,否则同类问题会以新字段形态复现。

### H5. 草稿恢复路径绕过准入检查,高版本草稿可进入可编辑状态

- **现象**:把一份 `schemaVersion: 99` 的草稿放进 `tripscope:draft:__blank__`,打开空白工具 → 界面显示「**可编辑 · 数据版本 v99**」,无只读横幅,保存按钮可用。
- **证据**:
  - 徽标 = `可编辑 · 数据版本 v99`
  - 「只读模式」横幅数量 = `0`
  - 保存按钮 `disabled = false`
- **根因**:两条恢复路径都直接 `openTrip()`,**没有走 `admitNode()`**:
  - `src/core/bootstrap.ts:29-36` — 空白工具分支 `loadDraft(BLANK_TOOL_ID)` 后直接 `openTrip(..., skipDraftCheck: true)`;
  - `src/core/store.ts:416-426` — `restoreFromSafe(id)` 同样直接 `openTrip(d.node, {...})`。
- **影响**:README 把「未知更高版本 → 只读(仅可导出 JSON)」列为数据安全的核心承诺,而草稿通道把这道闸门整个绕开了。现实触发路径:
  - 同一台机器上并存两个版本的旅行文件(Chromium 下所有 `file://` 页面共享 localStorage),新版本写的草稿被旧版本读到 → 旧版本以旧知识编辑并写回新格式数据,造成**静默有损重写**;
  - 安全模式(`SafeScreen`)本身就是「数据已损坏」时才到达的界面,此处恢复草稿若无准入校验,用户可能把损坏草稿恢复后保存,覆盖掉仍然完好的原文件。
- **修法**:两处 `loadDraft()` 之后统一插入准入,与文件路径共用同一套裁决:

```ts
const d = loadDraft(...)
if (d) {
  const adm = admitNode(JSON.stringify(d.node))
  if (!adm.ok) { openSafe('草稿数据损坏,未载入'); return }
  openTrip(adm.node, { ..., readonly: adm.mode === 'readonly', readonlyReason: adm.reason ?? '' })
}
```

或更省事:抽一个 `openFromDraft(entry, opts)` 工厂,内部强制走 `admitNode`,让「恢复草稿」在结构上不可能绕过准入。补验收:注入 v99 草稿 → 必须进只读、保存必须禁用。

## 二、中优先级

### M1. 项目名输入框逐字吞空格

- **现象**:逐字键入 `2027 国庆云南`,实际得到 `2027国庆云南`(空格被吃);粘贴正常。
- **证据**:`inputValue() === "未命名旅行2027国庆云南"`(前缀是我未清空输入框所致,关键点是**空格丢失**);改用 `fill()` 则 `"2027 国庆云南"` 正常。
- **根因**:`src/core/store.ts:170-175` 每次按键都 `name.trim()` —— 输入到一半的词尾空格当场被裁掉,导致**空格根本无法输入**。
- **修法**:输入期不裁剪,裁剪挪到落盘时。

```ts
// store.ts —— 输入中保留原文
export function renameProject(name: string): void {
  if (!canEdit() || !state.node) return
  state.node.project.name = name          // 不 trim
  state.node.updatedAt = nowIso()
  scheduleDraft()
}

// 落盘前统一规范化
function normalizedName(): string {
  const n = state.node!.project.name.trim()
  return n.length > 0 ? n : '未命名旅行'
}
```

`save()` / `saveAsCopy()` / `doExportJson()` 的取名路径统一走 `normalizedName()`(`sanitizeFileName` 已经兜了空名,这里主要是避免文件名前后空格)。

### M2. 草稿 debounce 无 flush,与「始终有兜底」的承诺不符

- **现象**:编辑后 300ms 内切换上下文或关页,最后一次编辑不进草稿。
- **根因**:`src/core/store.ts:181-192` `scheduleDraft()` 固定 300ms 延迟;`newTrip` / `openHandleFile` / `importFile` / `openSafe` 都会**直接切上下文而不等草稿落盘**;全仓无 `beforeunload`。
- **附带的隐性 bug**:定时器回调里读的是**触发时的 `state.node`**,而不是排期时的那个节点。若 300ms 内 `openTrip()` 换了节点,写入的是新旅行的草稿 —— 旧旅行的编辑丢失,且新旅行多出一条可能被误判为「冗余」的草稿(见 H4)。
- **修法**:
  1. 抽 `flushDraft(): void`(取消防抖、立即写),在上述所有切换上下文的函数**开头**调用;
  2. `main.ts` 注册 `window.addEventListener('beforeunload', flushDraft)`;
  3. 定时器回调改为闭包捕获排期时的节点与 `project.id`,避免跨上下文写错 key。

### M3. 验收脚本不在版本库里

- **现状**:53 条断言全在 `dev-fixtures/harness/`,而 `.gitignore:3` 忽略整个 `dev-fixtures/`。`git ls-files` 共 30 个受管文件,**零测试、零 CI、`package.json` 无 `test` script**,也无 eslint/prettier 配置。
- **风险**:这些断言是当前质量的主要证据,一旦本机目录丢失,后续改动没有任何回归网 —— H1/H3/H4 能存在,正是因为没有断言覆盖。
- **修法**:
  1. `harness/*.mjs` 移出到 `e2e/`(排除 `.edge-profile/`、`node_modules/`)并纳入版本库;`fixtures/`、`artifacts/` 继续忽略,可 `node e2e/make-fixtures.mjs` 重建;
  2. `package.json` 加 `"test:e2e": "node e2e/verify.mjs"`,README 开发章节写清跑法;
  3. 删掉 `dev-fixtures/harness/h1.mjs placeholder` —— 语法损坏的残片(`import { path_placeholder }`、重复 `const counts`、乱入的 `report(` 文本),跑不起来,只会误导后来人。

### M4. README 与实现对不上

- `README.md:60` 写「37 项断言」,实际 53 项(50 处静态 `report()` + S12 循环 3 轮)。
- **修法**:改成「`npm run test:e2e` 全绿」,不写具体数字 —— 数字必然继续漂。

## 四、确认没问题的部分(不必改)

- **节点替换严格边界**:产物实测恰好 1 个 `app-data` 节点;0 或 >1 一律拒绝写入。`schema.ts:128` 的 `[/]` 字符类技巧正确避开压缩器改写。
- **转义**:`serializeNode` 把 `<` 全转 `\u003c`;`</script>`、`<b>`、emoji 往返回一致(实测)。
- **只读准入(文件路径)**:v99 文件正确进只读,输入禁用、保存禁用、导出可用。
- **冲突不静默覆盖**:写回前重读磁盘比对,三选一(重载/另存副本/取消);连续写回不误报。
- **降级链**:权限拒绝 → 下载副本,含本地编辑(实测)。
- **XSS 面**:全仓无 `v-html` / `innerHTML` / `eval` / `new Function`,数据只走插值。
- **离线自包含**:116KB、0 个外链 `<script src>`、0 个 `<link>`、`<style>` 内联,`file://` 直开。
- **构建健康**:`vue-tsc --noEmit` 与 `vite build` 均通过(注意:沙箱内会因 `spawn EPERM` 失败,需放开权限)。

## 五、建议执行顺序

1. **H1** —— 一条 `npm run example`,立刻消除开箱即坏的可见故障;
2. **H2** —— 补齐三层错误可见性,让后续所有修复的失败不再静默;
3. **H5** —— 准入旁路,恢复 README 承诺的数据安全闸门;
4. **H3 / H4** —— 草稿层两条数据丢失路径;
5. **M1 / M2** —— 输入体验与草稿可靠性收口(含跨上下文写错 key 的隐患);
6. **M3 / M4** —— 验收网入库、文档校正;
7. **L 系列** —— 随业务功能开发顺手处理。

前 6 步完成后再做日期/交通/住宿/费用汇总。否则新字段会立刻复现 H4 那类「改了却判成没改」的静默丢失。

## 六、给执行侧的三条硬性要求

1. **每个修复必须配一条会失败的验收断言**,先让断言红、再改代码转绿;本次 5 个高优先级问题全部逃过了 53 项断言,根因就是断言只覆盖正向路径。
2. **H4 的修复不要只补 `project.name`**,要用整节点比对 —— 否则下一个业务字段照旧复现。
3. **H5 不要只修一处**,`bootstrap` 与 `restoreFromSafe` 两条路径都要过 `admitNode`,最好抽成工厂让旁路在结构上不可能存在。
