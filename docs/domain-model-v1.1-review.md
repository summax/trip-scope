## 2. P1-01 修订前后对照

**修订前（v1 的两处冲突定义）**：

> v1 §4.0 第 2 条：*预算行实例按版本持有独立身份：版本刷新产生**新行实例**（新 id），旧行实例永不改写*。
>
> v1 §4.10 E15a：*`lineId`｜UUID｜旅行内唯一、**跨版本不变**（实例身份，DM-02）*。

两条不能同时成立：若实例 ID 跨版本不变，刷新就不产生新实例；若产生新实例，"跨版本不变"无从谈起。v1 还存在第三处隐患：手动行按名称建立版本对应关系，属于静默建立对应。

**修订后（v1.1）**：拆分为双身份：

- **budgetLineId（行实例 ID）**：每个预算版本中的行实例独立持有；V1 与 V2 的对应行实例 ID 不同；创建后不因刷新而改变；Payment 归属、转消费归属、审计记录引用的都是实例 ID。
- **logicalLineId（逻辑行 ID）**：识别跨版本属于同一业务预算项的行；同一逻辑项跨版本实例 ID 不同、逻辑 ID 相同；仅由"首次确认铸造 + 刷新传播"建立；对应关系无法确定时不得静默建立；不参与任何金额计算、归属与审计定位。

v1 的三处旧语义已全文替换：§4.0/§4.10 的冲突定义（重写）；"手动行按名称对应"（P3-9/P3-7 已标注作废并改为"不得静默建立"）；sourceObjectId 行的"版本对比"定位改为"逻辑行传播锚点"。

**五点必答（与 §4.10 示例一致）**：

1. V1 支付仍然属于 BL-001（实例 ID），刷新后不变，V1 行已付不变（D-87 第 1 条）。
2. V2 新预算行是 BL-101，金额 600 为新快照值；BL-001 与 BL-101 是两个不同的行实例。
3. 两者通过 LL-001 识别业务对应关系（版本对比显示"同一项：500→600"）。
4. 刷新不得自动转移支付：支付不因 LL-001 相同而转移；对应新预算必须显式转移并留痕（D-87 第 4 条、BC-30）。

## 5. 审计结构及撤销机制说明

**E21 v1.1 结构摘要**：公共字段（auditId、operationType、paymentId、conversionId、amountCents、occurredAt、confirmedBy、actionGroupId、originAuditId）+ 按操作类型专属载荷。

**七操作类型**：

| 操作类型 | 专属载荷 | 需求依据 |
|---|---|---|
| 归属建立/归属变更/支付转移/待处理归位 | before/after（类型+实例 ID+行名+版本序号+逻辑行 ID（如存在）或预算外或空） | D-80b 规则 4、D-87 第 4 条、AC-LED-14a |
| 金额调整 | beforeAmountCents/afterAmountCents（+调整原因【技术建议】） | D-40 二.5 |
| 日期调整 | beforePaymentDate/afterPaymentDate | D-40 二.5 延伸 |
| 支付类型调整 | beforePaymentType/afterPaymentType（跨分类禁令【待确认】） | D-40 二.5 延伸；保护 D-39/D-80b |
| 撤销/重做补偿 | 载荷与原记录相同、前后值互换/同前，originAuditId 指向前序记录 | P2-02 技术设计 |

**撤销/重做补偿链（P2-02）**：原操作→A（originAuditId=空）；撤销→B（前后值互换、originAuditId=A）；重做→C（载荷同 A、originAuditId=B）；链 A→B→C；actionGroupId 组关联；审计追加与业务状态变更同批提交，失败整批不生效（DM-03）。

**五点明确回答**：原审计永久保留（A/B/C 全部只追加）；originAuditId 单链+actionGroupId 组关联；状态恢复走撤销栈数据快照（D-105），不由审计回放实现（审计是事件流不是状态机）；重做追加新记录 C 不复活 A；失败时整批不生效，状态与事件流一致。

**适用边界**：补偿链适用于 E21 审计域；版本清理的撤销属数据快照恢复，清理不是支付域审计事件，不产生 E21 记录（§7.7/§10.4）。

## 6. 历史快照生成和版本清理流程

**三种版本终态**：

| 情况 | 触发 | 数据动作 | 快照 |
|---|---|---|---|
| 版本不再作为当前版本 | 刷新产生新版本 | 旧版本整体冻结（只增不改），P1 至少保留当前版+上一版 | 不生成 |
| 预算行从新版本中消失（情况 A） | 刷新且来源中已无该对象的选择 | 旧行实例与归属支付原样保留，不转待处理 | 不生成 |
| 版本被用户主动清理 | 显式清理操作（P1 保留策略之外的更早版本） | 删除该版本的完整内容（Budget+行实例） | **强制前置** |

**清理流程（与 §7.7 一致，强制顺序）**：① 预检——枚举引用该版本任意行实例的 Payment（含其转消费份额的归属）；② 逐笔生成 E25 快照（八字段：paymentId、budgetId、versionNo、budgetLineId 实例 ID、logicalLineId（如存在）、lineName、lineAmountCents、paymentAmountCents）；③ 完整性校验——快照条数=引用支付条数且字段齐备；④ 校验通过才执行清理（引用支付的 budgetLineId 保留为悬空历史引用）；⑤ 任一步失败→清理整体不生效、数据不变、给出可见错误（DM-08）。

**配套规则**：清理后的支付不转为"待归位"（悬空归属≠待归位，清理≠删行，I-20a 延伸），仍只计入全部现金总额指标中唯一适用的「全程现金总额」；再归属走 D-87 第 4 条显式转移并生成审计（before 冗余信息取自快照）；清理动作的撤销走撤销栈数据快照恢复（恢复版本完整内容，快照随数据回退消失）——清理不是支付域审计事件，不产生 E21 记录；快照只用于追溯、不参与任何金额计算（D-72a 第 4 条）；相对 D-72a"只包含"最小集合补充的 budgetId/paymentId/logicalLineId 为**标识类**字段，仍属最小记录【技术建议】。

## 7. P2-04、P2-05 的待确认结论

**P2-04（刷新来源策略）**——**不裁决，标记待确认**：

- `sourcePlanId` 在 v1.1 中的定位：**首次确认时的来源方案**（原始来源信息留痕，D-2.3"方案→正式预算快照"）；用途 = 来源追溯与现价对比上下文。
- 冻结需求未裁决刷新取数来源；原始来源方案与刷新时所选来源**可能不同**，模型不预设两者相同。
- 两种策略（按原始来源方案刷新 / 按当前组合刷新）对数据结构**无影响**（刷新都表现为"以某一选择集为输入生成新版本行实例集 + 逻辑行传播"），对结果的影响：甲=只吸收该方案显式变更、来源可追溯最强；乙=吸收最新工作状态、可能带入未存档改动（与 C11 张力更大，须显式确认兜底）。两种策略下情况 A、逻辑行传播、支付不转移、快照规则完全一致。
- **结论**：保留来源信息、说明用途、列明两种影响；不认定刷新永远从原始方案或当前组合取数；实现前须人工裁决。

**P2-05（CostSettings 挂载位置）**——**完成边界论证，维持共享为当前取向，仍标待确认**：

- 逐属性边界（详见 §7.8）：归属日期/分摊方式/承担方式+参与人/计价数量 → 消费对象级（共享）；金额表达/票档价格/优惠/附加子项/数量口径声明/适用日期 → 候选级（随方案变化）；名称/应付/承担方式/参与人/归属/分摊设置 → 确认时冻结进预算行（快照级）。
- 对任务问询的回答：不同候选的金额/计价单位不同（候选级），参与人/日期归属不因候选不同而不同（对象级）——两层语义自洽；冻结需求不足以完全确定参与人/分摊设置的层级。
- 两种设计的影响：对象级共享=数据一份、方案对比只差候选价、人员维度为旅行级概念（与 R4 一致），风险是真实使用若需"同对象不同方案不同参与人"需迁移；方案级独立=支持逐方案人员维度对比，代价是数据倍增、录入重复、快照来源变为选择记录、Z 的方案级语义需重新界定。
- **结论**：不直接改为方案独立、不为方便维持现状而回避论证；论证结果支持对象级共享与 D-41~D-44/D-50/D-72 无冲突，最终取舍标**待确认设计**，实现前人工裁决。
