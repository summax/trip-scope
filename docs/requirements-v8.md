## 1. 产品定位（不得改变）

### 1.1 一句话目标

把一次家庭旅行的所有候选价格收进一处，能自由组合、随时看总额、横向比较哪套划算；整个文件和一次旅行的数据装在一个 HTML 里，双击即用、离线运行、发给家人就能看。

### 1.2 核心问题

家庭出游的选择互相牵连：

- 早一天出发，机票可能便宜，但会多一晚房费。
- 换一家酒店可能省 200 元，但打车多 80 元。
- 不同航班、酒店、房型、日期组合会形成不同总成本。

TripScope 解决的不是单个商品价格比较，而是：

**在家庭旅行的整体行程背景下，管理候选报价、自由组合费用、计算完整成本，并比较不同组合的实际经济性。**

### 1.3 核心产品原则（十条，v8 第 10 条为新增）

1. 一个 HTML 文件对应一次旅行。
2. 双击 HTML 即可使用，完全离线。
3. 不需要账号、服务器、数据库服务或网络请求。
4. 候选报价可以大量录入，不能要求逐个打开复杂表单。
5. 所有候选应尽可能同时可见，方便横向比较。
6. 空白（未选择/未填）、待估（未定价）、已定价（含 0 元）、不适用必须是互不相同的状态，界面文本可辨。
7. 所有金额必须准确，任何汇总都能追溯到原始费用。
8. 任何操作都不能静默丢弃用户输入。
9. 规划、定稿、出行、复盘都使用同一个旅行文件。
10. **同一笔钱只被计算一次**：原始金额、分摊金额、支付金额、返利各走各的口径，永不叠加。

## 2. 使用阶段与旅行状态

### 2.1 六个使用阶段（保留，补全产出物）

| 阶段 | 我在干什么 | 工具必须支持 | 阶段产出物 |
|---|---|---|---|
| ① 规划期 | 到处查价，把看到的记下来 | 快速批量录入候选；同物不同日期/房型/票档分别录 | 候选报价库 |
| ② 定稿期 | 反复组合，比哪套划算 | 逐天/逐区段/逐类别挑选；换一个看总额变化；保存多套方案横向比 | 若干具名方案 |
| ③ 决策后 | 定下来，准备出发 | 选定一套成为**正式预算**（金额快照），生成行程简表 | 正式预算 + 行程单 |
| ④ 出行中 | 花钱、记账 | 随手记实付；一项预算可多笔支付；临时支出；看待付 | 支付流水 |
| ⑤ 归来 | 复盘 | 预算 vs 实付 vs 净成本；返利到账登记 | 差额报告 |
| ⑥ 分享 | 给家人看、留档 | 转发文件、导出文字行程单、打印/PDF | 分享副本 |

### 2.2 旅行状态（v8 新增，解决"阶段转换不清楚"）

旅行本身有一个状态，只有四个：**规划中 / 已定稿 / 出行中 / 已结束**。

规则：

1. 状态**只决定默认视图与提醒文案**，不阻止任何编辑（唯一例外是 §3 C6 的"未知新版本只读"）。
2. 默认按日期推断：未到出发日 → 规划中；已过出发日且未过结束日 → 出行中；已过结束日 → 已结束。用户可手动覆盖。
3. 「已定稿」必须由用户显式操作产生（确认正式预算那一刻）。
4. **进入出行中/已结束，仍可回到规划期视角继续加候选**——状态不数据锁。

### 2.3 阶段间的数据流转（v8 新增，逐条对应）

| 从 | 到 | 流转内容 | 不得发生的事 |
|---|---|---|---|
| ① 规划 | ② 定稿 | 候选被方案引用（引用式，实时反映候选变化） | 不得把候选复制进方案造成双份真相 |
| ② 定稿 | ③ 决策 | 方案 → **正式预算快照**（金额与构成冻结） | 不得让后续改候选价静默改动正式预算（C11） |
| ③ 决策 | ④ 出行 | 正式预算的每个条目可被"支付记录"关联 | 不得让同一笔付款同时计入两个预算条目 |
| ④ 出行 | ⑤ 归来 | 支付记录汇总为"已付 / 已退 / 待付 / 押金待退" | 不得把未到账返利算进净成本 |
| ②③ | ⑥ 分享 | 导出为文字/打印/副本文件 | 不得把编辑控件带入打印视图 |
| ④⑤ | ② | 允许回到定稿期改方案 | 不得因此丢弃已记录的支付流水 |

## 3. 底线（C1～C11）

C1～C7 原样保留；C8～C11 为 v8 新增。原提案 C10、C13 不单列，分别并入 C4、C3（映射见附录 A）。

| 编号 | 底线 | 说明 |
|---|---|---|
| **C1** | 完全离线 | 零网络请求；`file://` 双击可用；无外部资源 |
| **C2** | 单文件 | 应用 + 一次旅行数据 = 一个 HTML |
| **C3** | 不静默丢数据 | 任何操作都不允许静默丢弃用户输入；**删除、批量修改、导入、恢复、覆盖写入等破坏性操作必须可撤销，或事先确认**，且不得静默失败 |
| **C4** | 金额准确 | 一律整数分计算，不允许分位误差；**除法与分摊必须严格守恒（各份之和 = 原额），不足一分由最大余数法分配**；住宿按"晚"计价，退房日不计住宿费；**汇总守恒必须按维度分别成立**：`Σ 每类合计 = 总费用`、`Σ 范围内每日合计 + 范围外费用合计 R = 总费用`、`Σ 每人合计 = 总费用 − Z`（三者同时成立，见 D-43、D-51a、D-55） |
| **C5** | 状态不得混淆 | 未选择 ≠ 未填 ≠ 未定价（待估）≠ 免费（0 元）≠ 不适用，五者在界面文本上必须可辨。没查到价必须显式暴露，不得当 0 混入合计，也不得被判为最便宜 |
| **C6** | 可迁移 | 数据版本升级有迁移路径；未知更高版本只读、可导出、不破坏 |
| **C7** | 移动端可用 | 375px 起能正常用，不出现页面级横向溢出 |
| **C8** | 计价三要素 | 每一项费用必须能说清**计价单位、数量、计价周期**；缺一不可，否则视为录入未完成 |
| **C9** | 口径分层 | 原始报价、优惠后应付、实际支付、已到账返利、最终净成本必须分别记录、分别展示，不得相互替代；返利必须声明适用范围后才参与任何口径 |
| **C10** | 比较口径统一 | 任何横向比较（方案之间、预算与实际之间）必须使用同一口径；跨口径比较视为错误 |
| **C11** | 快照不可静默变更 | 修改候选报价不得静默改变已确认的正式预算；必须变则显式确认并留痕 |

## 4. 业务规则（v8 主体）

> 本章是 v8 相对 v7 的核心增量。规则编号 `D-xx` 供实现与验收引用。
> 本章描述**业务语义**，不规定字段名、控件形态或存储结构。

### 4.1 家庭成员与票档（对应审查项 A）

**D-01 成员名册（P1）**
旅行级维护一份家庭成员名册。每位成员至少有：称呼（可只写"爸爸""老二"）、票档、可选年龄或出生日期、可选备注。

**D-02 票档是计价维度，身份不是（P1）**
价格按**票档**区分，票档由用户命名与增删，内置默认四档：成人 / 儿童 / 婴儿 / 老人。成员挂在一个票档上。票档数量不设硬上限，但**同一候选报价上的票档价格项不得重复**。

**D-03 每个候选报价 × 每个票档 = 一个价格状态（P1）**
对任一候选报价上的任一票档，**价格层**只能处于四种状态之一（与组合层的"未选择"合起来共五态，见 C5）：

| 状态 | 含义 | 是否计入合计 |
|---|---|---|
| 未填 | 这个票档用不上，或还没考虑 | 否，且不报错 |
| 待估 | 知道要按这个票档付费，但没查到价 | 否，但整笔标记为"待估" |
| 已定价（含 0） | 有明确金额，0 元也是明确金额 | 是 |
| 不适用 | 该票档不占这个费用（如婴儿免票且不计座） | 否，不警告 |

**D-04 票档价格的三种给法（P1）**
① 绝对金额；② 以另一票档单价为基数的比例（如"成人价 50%"）；③ 免费（明确 0 元）。

比例是**活规则**：基数票档单价变化时，比例价随之重算；重算在整数分上做，单档单价四舍五入到分。比例不得用于"整单一口价"候选（无可乘基数时禁止，界面需说明原因）。

**D-05 特殊票价不靠"逐人覆盖"表达（P1 裁决；逐人覆盖列 P2）**
首版**不提供"给某一位成员单独定价"**。个别成员价格特殊时，用户的做法是**再建一个票档**（如"儿童(半票)""儿童(免)"），把该成员挂上去。
理由：逐人覆盖会形成"人数 × 服务数"的覆盖矩阵，录入成本与出错概率同时爆炸。
**P2 可加**：成员级金额覆盖（仅当真实使用中被反复要求）。

**D-06 儿童年龄不做自动判定（Won't）**
不同服务（航司／铁路／酒店／景区）的儿童年龄规则不同，因此：

- 系统**不根据年龄自动判定成员属于哪个票档**，票档一律由用户指定。
- 系统**不内置任何行业的年龄阈值**。
- 允许在候选报价上记录"年龄规则"文本（如"12 岁以下半价，2 岁以下免"）与可选的年龄阈值数字，仅作提示与留档，不参与计算。

**D-07 成员参与范围（P1）**
"某成员不参加某项费用"由**该费用条目自身的参与人**决定（见 D-30、D-50），不在成员上设全局开关。

**D-08 名册变更的影响（P1）**
成员名册是计价与分摊的输入，因此：

- **新增成员**：不自动改变任何已有费用条目的金额；新成员是否参与某项费用由该条目的参与人决定（默认"全员"含新成员，必须让用户看到这一点）。
- **移除/停用成员**：不得静默删除该成员在各条目上的分摊份额。移除前必须提示"该成员在 N 个费用条目中参与分摊，合计 X 元"，并要求用户选择：把这些条目改为其他参与人，或保留该成员为"历史成员"（仍参与既有费用，但不再作为新条目默认参与人）。
- **改票档**：所有引用该票档的价格项立即按新票档计价重算；已确认的正式预算不变（C11）。
- 任何名册变更都可撤销（C3）。

### 4.2 交通区段（对应审查项 B）

**D-10 交通以区段为管理单位（P1）**
交通的基本管理对象是**区段**，不是日期。一个区段 = 出发地 → 目的地 + 出发日期（+ 可选出发时刻、到达日期时刻）。
区段由用户显式建立，可命名或归组（如"去程""返程""中段"）。

**D-11 一个区段可以有多个候选报价（P1）**
同一区段的多个候选并列，只有"已选"的那个计入金额。候选之间可比较总价、时长、时刻、退改规则。

**D-12 不同方向的区段不得混为一谈（P1）**
去程、返程、中途段是不同区段。系统不得把"家→目的地"与"目的地→家"的候选合并展示或合计。

**D-13 一天可以有多段（P1）**
同一天可存在多个区段（如"家→机场""机场→目的地""目的地→酒店"）。按出发时刻排序；时刻为空时按录入顺序。不做路径衔接校验、不做路程计算。

**D-14 跨日交通的归属（P1）**
跨日到达（如 23:40 起飞、次日 02:10 落地）时：

- 费用**全额归属出发日期**（这是唯一默认，不询问）；
- 到达日期以"信息项"形式展示（不计费）；
- 把**单趟交通**的金额按小时/整天切到两天的做法列为 **P2**，首版不做。
  说明：D-42 的"按天均摊"针对的是**跨多天的区间费用**（3 晚住宿、多日租车、多段套餐），不用于拆分单趟航班。

**D-15 交通套餐与多段联程（P1）**
一个候选报价**可以覆盖多个区段**（如"往返联程含税 3980"）。此时：

- 该候选称为"整段套餐候选"，选中即占用其覆盖的全部区段；
- 被占用区段不得再被其他候选占用（L1 冲突，见 4.11）；
- 套餐金额的分摊走 D-42，原始金额仍是一条整段报价。

**D-16 交通候选的可记录内容（P1）**
区段与候选需要能承载：出发/到达时刻、交通方式（飞机/火车/大巴/自驾/轮渡/其他，可自定义文本）、票档价格、行李额与超重费、选座费、接送/接驳费用、退改规则文本、承运方与班次号、备注。
这些附加成本作为**独立费用子项**记录（见 D-30），不与票价混成一个数。

### 4.3 住宿、房间与人员分配（对应审查项 C）

**D-20 住宿单与房间项（P1）**
住宿以**住宿单**为单位：一家酒店 + 一段入住/退房区间。一个住宿单内可以有**多个房间项**，每个房间项 = 房型 + 间数 + 每间可住人数 + 入住成员 + 早餐安排 + 加床。

- 同晚同酒店多个房型：**合法**，金额相加。
- 同晚多家不同酒店：**合法**，前提是每位成员当晚只属于其中一处（见 D-23）。
- 一个住宿单的日期区间必须连续，且其所有房间项共享同一区间。

**D-21 住宿候选报价**（P1，v8.1 重写）
住宿候选报价分为两类，二者的适用对象不同：

| 类型 | 适用对象 | 计价形态 | 例 |
|---|---|---|---|
| **房间候选** | **单个房间项** | 每次只报一个房型的价，按间夜 / 按晚 / 按整段 | 标准间 1 间 × 3 晚 = 900 |
| **整段套餐候选** | **整个住宿单**（覆盖其全部房间项） | 一口价，不可拆分 | "3 晚连住含双早 3000"，不分房型 |

**房间候选的规则（P1）**

1. **房间项可以独立拥有候选报价**：每个房间项有自己的候选集合。
2. **不同房型独立比较、独立选择**：标准间与家庭房各自挑候选，各自的候选不得混入对方的选择列表。
3. **一个住宿单可以同时包含多个房型**，每个房型按自己的候选计价，金额相加。
4. 房间候选的计价区间必须**覆盖该住宿单的全部晚数**，否则按 D-63 判 L1（覆盖不足）。
5. **房间候选的"间数"必须与该房间项的间数一致**；不一致时按 P2-01 的补充规则处理（L2 警告 + 用户显式确认数量口径 + 未确认前不得静默乘算）：

**补充：间数不一致时的金额处理（**P1**，v8.1 复审新增）**

> **优先级说明（第二轮复审澄清）**：本组规则（5a～5g）**是 P1，首版必须实现**。
> 它在复审问题清单里的编号是 `P2-01`／`R-P2-01`，那只是**问题出处编号**，**不是优先级**。凡见 `R-P2-0x`，一律按"该问题的来源是 P2 类审查项"，其**采纳后的规则本身按正文标注的 P 级执行**。

5a. **候选自身必须声明"报价数量口径"**，二选一，必填：
   - **每间价**（单间价格，总价 = 单价 × 间数 × 晚数）
   - **整单价**（该房型全部间数的合计价，总价不再乘间数）
   未声明数量口径的候选按"计价要素不完整"处理（L1，C8），不参与合计。

5b. **数量口径与房间项一致时**：按上述公式直接计价，不警告。

5c. **候选是"每间价"、房间项间数更多时**（例：候选 1 间 900，房间项 2 间）：
   - 必须标 **L2** 并给出明确文案："候选按 1 间报价（每间 900），该房间项需要 2 间，是否按 1800 元计价？"
   - **未确认前不得静默乘算**：确认前该房间项金额为"待确认"，**不进入总费用**，并按 D-33 的"待确认数量"单独计数（**不作为"待估"统计**；界面显示"待确认数量 N 项"）。
   - 用户显式确认"按间数乘算"后，金额 = 900 × 2 × 晚数，L2 降为 L3 留痕提示。
   - 用户选择"该报价就是整单 2 间的价"时，等价于把候选改判为"整单价"，金额 = 900 × 晚数（这属于修改候选的数量口径，需留痕）。

5d. **候选是"整单价"、房间项间数更多时**：金额**不乘间数**，但必须标 L2（"该候选为整单报价，房间项需要 2 间，请确认此价是否已含 2 间"）。这类不一致的风险方向与 5c 相反（可能**少算**），因此处理规则同样是"未确认前不计价 + 单独显示为待确认状态"，而不是"先按整单价计入再说"——否则用户会看到一个偏低总额却不知道它假设了 1 间。

5e. **房间项间数少于候选声明的间数时**：标 L2（"候选按 2 间报价，房间项只有 1 间"），同样要求用户显式确认、未确认前不计价，不得静默按较小数计算。

5f. **不得用"取较小值""取平均值"等隐式规则消解不一致**：数量口径只能由候选声明 + 用户确认这两步确定。

5g. **"未确认前不计价"不等于"待估"**：它有自己的状态与计数（见 D-33、D-55 逐状态表），不得并入待估统计，也不得因为"先不填"而被当成 0 元或免费。

**整段套餐候选的规则（P1）**

6. 整段套餐是**一个候选**，占用住宿单的**全部晚数与全部房间项**。
7. 套餐选中后，**该住宿单内所有房间项的独立候选报价一律不参与计价**（不是"也相加"，也不是"取较小值"）。
8. 因此住宿单在任一时刻只有两种状态：**逐房间计价**（各房间项各自选候选）或**整段套餐计价**（选中一个套餐，房间项候选全部被压制）。住宿单在任一时刻的**当前生效计价模式**必须明确显示（见 8a）。

**当前生效模式 vs 被保留但未生效的选择（P1，v8.1 复审新增，对应 P2-02）**

8a. 每个住宿单必须能同时表达两件事，且两者**分别可见**：
   - **当前生效计价模式**：逐房间计价 / 整段套餐计价（唯一，决定金额来源）；
   - **被保留但未生效的选择**：另一种模式下的选择记录（保留数据，不参与计价）。

8b. **已选套餐后再给某房间项选候选** → **阻止该操作并提示**（"该住宿单当前为整段套餐计价，需先切换模式"），**不静默覆盖、不进入冲突态**。用户若确实想选，必须先按 8e 把模式切回逐房间计价。

8c. **从逐房间切换到整段套餐**（第 11 条）：房间项候选与房间附加项**全部保留但不计价**，**不产生 L1**（这是用户已显式确认的合法切换），只需在住宿单上持续显示"另有 N 个房间候选未生效"。

8d. **删除整段套餐后**：住宿单**回退到逐房间计价**，并**自动恢复**此前保留的房间项候选与房间附加项。若此前没有任何保留选择，则为空白状态（合法，不警告）。这一回退必须提示"已恢复此前的逐房间选择"。

8e. **反向切换（套餐 → 逐房间）**：同样保留套餐选择但标记"未生效"；原房间附加项随房间候选一起恢复计价（D-22a）。

8f. **任何切换都不得静默删除用户的原有选择**（C3）：被压制的选择只能处于"保留但未生效"状态，可随时切回。

9. 一个住宿单的费用，**要么来自各房间项候选之和，要么来自一个整段套餐**，二者**互斥**，不得同时进入合计（这是 D-43 在住宿上的具体化）。
10. **同时生效即 L1**：若数据中确实出现"整段套餐计价"与"房间候选计价"同时成立（如导入的历史数据、或多端编辑合并后的结果），该住宿单的**房间那一侧**判 **L1 冲突**（"该住宿单已被整段套餐占用"），被压制的那笔不计入合计、不参与排名，且**不得把两侧相加**。正常交互路径下 8b 已在选择阶段阻止，因此这条是**兜底校验**，不是常规操作结果。
11. 若用户在一个已逐房间计价的住宿单上再选整段套餐 → 需显式确认"改用套餐"；确认后进入"整段套餐计价"模式，房间项选择保留但不计价（8c）。**未确认前不得切换**。

**整段套餐覆盖范围的边界（P1）**

12. 整段套餐**只覆盖它所属的那一个住宿单**。跨酒店、跨入住区间的"打包价"必须拆成多个住宿单，或作为一个**自由费用项**录入（D-30）。不得用一个套餐跨住宿单覆盖。

**候选变化的影响范围（P1）**

| 变化 | 受影响对象 |
|---|---|
| 改某个房间候选的价格/日期 | 只有引用该候选的房间项与含该房间项的方案 |
| 改整段套餐候选的价格/日期 | 该住宿单，以及引用它的方案 |
| 删除某个房间候选 | 引用它的房间项进入 L1 悬空（D-71），其余房间项不受影响 |
| 删除整段套餐候选 | 该住宿单失去套餐计价，回落到"逐房间计价"或空白，须显式提示 |
| 房间项增删、间数变更 | 该住宿单的全部候选需重新校验覆盖与间数（D-63、上条第 5 点） |

> 影响范围的判定原则与 D-71 一致：**只影响真正引用它的对象**，不做"整张住宿单全部失效"的粗暴处理。

**D-22 住宿的附加项（P1）**
早餐（含/不含/另付，按人按天或按间按天）、加床（按晚）、税费与服务费（含在报价内/另计）、停车、度假村费，都必须能作为**独立子项**录入，并明确标"已含"或"另计"。
"已含"的子项计入展示但不重复计价。

**D-22a 附加项挂在谁身上（P1，v8.1 新增）**

- 附加项可挂在**房间候选**上（只对该房间项生效），也可挂在**整段套餐候选**上（对整个住宿单生效）。
- **整段套餐生效时，房间候选上的附加项一律不参与计价**（与 D-21 第 7 条一致：被压制的候选连附加项一起压制）。
- 与房间无关的住宿类支出（如整单停车费、度假村费）应作为自由费用项或整段套餐的附加项，不要挂在某个房间候选上，否则换房型时会被静默带走。

**D-23 人员分配的冲突判定（P1）**
判定粒度是「**成员 × 晚**」：

- 同一成员同一晚**只能属于一个房间项** → 否则 L1 冲突（"同一人被安排到两处住宿"）。
- 房间容量：某晚某房间项「入住人数 ≤ 每间可住人数 × 间数」→ 否则 L2 警告（"房间容量不足"）。
- 某晚已有住宿安排，但有成员未分配到任何房间 → L2 警告（"某晚有 N 人未安排住宿"）。
- 某晚完全没有任何住宿 → 合法空白，不警告。

**双占冲突时，排除哪一侧？（P1，第三轮复审新增：此前未定义，是真实缺口）**

先说清**冲突的性质**：冲突发生在「**成员 × 晚**」这一条分配关系上（"爸爸这一晚被放进了两个房间项"），**不是**发生在"两家酒店都花了钱"这件事上。两间房很可能是真实预订，妈妈和孩子也各自需要住宿——**不能因为一个人分错了，就把一整间房的真实费用抹掉**。

因此规则如下：

1. **判定的对象是"冲突的那一晚 × 那个成员"，不是整个房间项。**
   涉及的两个房间项本身仍然合法存在、仍然被选中、仍然可被预订。

2. **默认不自动排除任何一侧**，而是把冲突的两侧都置为「**待定（冲突未解决）**」：
   - 该晚这两个房间项的金额**都暂不计入总费用**（避免系统替用户猜"哪边是假的"）；
   - 该晚的金额计入 **Y**（因异常未计入），且 Y 的金额 = **两个冲突房间项在该晚的金额之和**；
   - 明确文案："爸爸 10/1 这一晚同时被安排在『A 标准间』与『B 家庭房』，请确认他实际住在哪一间"；
   - **不得**自动按"后录入的排除""金额大的保留""金额小的保留"等隐式规则替他选。

3. **用户显式确认后按确认结果恢复**，三种操作可选：
   - **把该成员从其中一侧移除**（最常见）：被移除那一侧的**其余成员不受影响**，该房间项恢复正常计价；冲突解除，Y 相应减少；
   - **保留该成员在该侧、把另一侧的整间房标记为"不入住/取消"**：该房间项从计价中移除（属用户显式操作，须留痕）；
   - **确认是重复录入**：删除其中一侧的房间项（破坏性操作，须可撤销或事先确认，C3）。

4. **恢复后的金额必须完全可追溯**：哪一晚、哪个成员、原来算在谁头上、确认后算在谁头上，都要能回答（D-52）。

5. **不得把"人员双占"实现成"整间房从所有维度消失"**：冲突消除后，被保留的房间项必须回到全部维度（总额/每日/每类/每人），且 `Σ 每人合计 = 总费用 − Z` 仍然成立。

> **一句话**：冲突是"人的分配错了"，不是"钱不存在"。系统只冻结有争议的那一晚两侧金额，等用户说清谁住哪，而不是替他选一家酒店作废。

**已知局限（P1，v8.1 复审标注，不由本文件裁决）**

上面第三条规则会产生**合理误报**：某成员当晚坐红眼航班、住亲友家、或本晚不参加住宿安排时，他确实"没有被分配到房间"，但这不是漏填。

- 本文件**不擅自规定**如何表达"该成员本晚不需要住宿"，该问题保留为 **§9 Q16 未决**（三种备选 A/B/C 均满足"不重复计费"，差别在录入成本与误报量）。
- **Q16 是住宿模块进入完整验收前的业务决策项**：D-23 的告警文案、AC-SEL-11 的期望、以及"未安排住宿"是否可被用户消除，都依赖 Q16 的裁决结果。
- 在 Q16 裁决前，本规则**按 L2 警告执行**（只警告、不影响金额、不阻断排名），并必须在告警文案中保留"如果该成员本晚不需要住宿，此警告可能不适用"的说明，避免用户误以为系统发现了错误。
- 不得为了消除误报而**擅自**增加"本晚不住宿"标记：那是 Q16 的裁决内容，不是本轮的修订范围。

**D-24 取消政策（P1 文本 / P2 日期）**
可记录"免费取消截止日 + 取消费规则"文本；把截止日做成可比较日期并驱动提醒为 **P2**。

**D-25 同一晚多房间、多房型的组合规则（P1，v8.1 新增）**

同晚多房间是家庭出游的常态（1 标间 + 1 家庭房），必须明确它和"冲突"的界限：

| 情形 | 判定 | 金额 |
|---|---|---|
| 同一住宿单内，同房型多间（如 2 间标准间） | 合法 | 按间数计 |
| 同一住宿单内，不同房型各自成项（标间 + 家庭房） | 合法 | 各房间项相加 |
| 同一住宿单，同一房型既有"2 间"的房间项、又有"1 间"的房间项 | **L2 警告**（疑似重复录入） | 仍相加，但提示核对 |
| 不同住宿单（不同酒店）同一晚，成员不重叠 | 合法（拆住） | 相加 |
| 不同住宿单同一晚，成员重叠 | L1（D-23） | 双占的那一晚不计 |
| 同一晚同一房间项被两个成员小组重复选中 | 视为同一房间项 | 只计一次 |

**要点**

1. 多房间的合法判定依据是**成员归属不冲突**，不是房间数量。
2. 房间项之间**不互相占用**：标间与家庭房是并列的两个项，不是一个项的两个候选。
3. 同一晚的住宿总额 = 该晚所有**有效**房间项之和（不含被整段套餐压制的项，D-21）。
4. 若某晚所有房间项的容量之和小于已分配成员数 → L2（D-23）。

### 4.4 费用条目与计价（对应审查项 D 的输入侧）

**D-30 统一的费用条目语义（P1）**
任何一笔花钱的事，在业务上都是一个**费用条目**。费用条目来自四条入口：交通候选、住宿候选、自由费用项（餐饮/门票/当地交通/购物/其他）、临时支出。
每个费用条目必须能说清：计价单位、数量、计价周期、票档价格、参与人、日期归属、附加子项、优惠项。

**D-31 计价单位与周期（P1，底线 C8）**

| 计价单位 | 含义 | 常见周期 |
|---|---|---|
| 人 | 按人头 | 一次性 |
| 间 | 按房间 | 一次性 / 每晚 |
| 间夜 | 房间 × 晚 | 一次性 |
| 人夜 | 人 × 晚 | 一次性 |
| 天 | 按天数 | 一次性 |
| 段 | 按交通区段 | 一次性 |
| 次 | 按次数（接送、门票场次） | 一次性 |
| 份 | 按份数（餐、票） | 一次性 |
| 整单 | 不可拆分的整段报价 | 一次性 |

**D-32 明确录入 0 元是合法且必要的（P1）**
免费、免票、赠送、含在房费内，都必须能录入为一个"已定价 0 元"的条目并带上说明。**未定价不能写成 0 元**，两者显示必须不同（C5）。

**D-33 未定价的表达（P1）**
"知道要花这笔钱但没查到价"是一个独立状态，条目可以只有名称、没有金额。汇总处必须显示"另有 N 项待估"，并且该组合/方案不参与最低价排名。

> **注意区分（v8.1 复审新增）**：「待确认数量」（D-21 第 5c 条，数量口径未获用户确认）与「待估」（没查到价）都是"金额尚未确定"，但**原因不同，必须分开计数与展示**（"待估 N 项" / "待确认数量 N 项"）。两者都不进合计、都不参与排名，但不得合并成同一个计数，否则用户不知道应该"去查价"还是"去确认数量"。

**D-34 优惠的分类（P1）**
优惠分四类，必须分开记录，不得合并成一个"折扣"数字：

1. **商家优惠**（含早、连住立减、会员价差）
2. **平台优惠券/立减**
3. **返利**（下单后返还，有"预计/已确认/已到账"三态，见 4.9）
4. **非现金权益**（赠送早餐、赠门票、免费接送、免费加床）

前三类是**金钱性**的，必须参与计算；第四类**只记录与展示，永不折算成现金抵扣**（C9）。

**D-35 优惠超过原价的处理（P1，v8.1 重写）**

优惠合计大于原始报价（如原价 100、优惠 150）是一个**数据错误或需要用户核对的情况**，不是"免费项目"。规则：

1. **保留原始报价**：原价照实记录，不因优惠过大而被改写。
2. **保留用户输入的优惠金额**：不自动截断到原价，也不静默丢弃多出的部分——否则用户无从发现自己填错了。
3. **应付展示为 0**：作为**异常展示值**，避免出现负数成本。
4. **必须标记 L1**，并附明确文案（"优惠合计 150 已超过原价 100，请核对"）。
5. **这不是免费项目**：不得把它当作明确 0 元（D-32）处理；它不进入任何汇总维度，不参与排名。
6. **方案整体不参与最低价排名**（D-74）。
7. **用户修正优惠后自动解除**：改到 ≤ 原价即恢复正常，重新计入合计与排名，无需其他操作。
8. **不得出现负应付**：任何路径下应付都不得为负数。

**L1 状态下那个 0 元的性质（必须写进界面文案）**
> "应付 0 元"仅表示**不会算成负数**，**不代表该项目已确认免费**。它目前是异常状态，未计入总费用。请核对优惠金额。

**与 D-90 / D-55 的一致性**
- D-90 把"优惠超过原价"列为 L1；
- D-55 把它列为"不计入任何汇总维度"；
- 本文第 3 条说的"展示 0"是**条目自身的金额展示**，不是"以一个 0 元条目进入合计"。两者不矛盾：**展示为 0，但合计中缺席**。

### 4.5 金额口径：五层，永不混淆（对应审查项 D）

**D-36 五层口径定义（P1，底线 C9）**

| 层 | 名称 | 定义 | 用途 |
|---|---|---|---|
| ① | **原始报价** | 单价 × 数量 × 周期 + 附加子项 + 税费（未减任何优惠） | 留档、核对来源 |
| ② | **实际应付** | ① − 商家优惠 − 平台优惠（≥ 0） | **预算口径**：方案对比、正式预算一致使用 |
| ③ | **实际支付** | Σ付款 − Σ退款（针对同一费用条目的流水净额） | 现金口径：记账、待付 |
| ④ | **已到账返利** | 状态为"已到账"的返利合计 | 决算口径的减项 |
| ⑤ | **最终净成本** | ③ − ④ | 决算口径：复盘 |

**D-37 三种口径不得混用（P1，底线 C10）**

- **预算口径**（②）用于：方案对比、正式预算、预算 vs 实际的预算侧。
- **现金口径**（③）用于：已付、待付、押金待退。
- **决算口径**（⑤）用于：归来复盘、净成本、真实省钱多少。

任何界面同时出现两个口径时，必须标注口径名。

**D-38 返利三态与两个固定公式（P1，v8.1 复审修订）**

**三种状态互斥**：预计 / 已确认 / 已到账。任何一笔返利在任一时刻只处于其中一种状态，**同一笔金额不得同时出现在两种状态里**。

**两个汇总口径各用一组状态，互不重叠**

| 汇总值 | 定义式 | 参与的口径 |
|---|---|---|
| **待收返利** | `待收返利 = Σ(状态=预计) + Σ(状态=已确认)` | 含预期返利的方案比较（D-38a）、预期净成本 |
| **已到账返利** | `Σ(状态=已到账)` | 决算口径的减项（⑤ 净成本） |

- **只有"已到账"进入**决算口径的净成本（⑤）：`净成本 = 实际支付 − 已到账返利`。
- **预期净成本**＝应付 − 待收返利（这是"这趟预计实际会花多少"）。
- **已到账的返利已经不属于待收返利**：`待收返利` 中**不得再减去**已到账部分。把两种状态相加再减去一种状态（如"预计 + 已确认 − 已到账"）是**错误公式**，会导致到账后待收金额变成负数或重复扣减。
- **状态迁移只允许单向逐级推进**：预计 → 已确认 → 已到账（允许跳过已确认，直接 预计 → 已到账；不允许回退，需回退时按"撤销该返利登记后重录"处理）。迁移是**整笔状态的替换**，不是"新增一条"：预计 200 改为已确认后，待收仍是 200；改为已到账后，待收变 0、已到账变 200，**净成本减少 200 且只减少一次**。
- 返利**不减少**"应付"（②）：下单时你确实要付全款，返利是之后的钱。
- 返利也**不减少**"已付"（③）：已付是现金流出。

**D-38a 返利必须参与比较（P1，v8.1 修订）**
方案对比必须能切换两种口径，并在界面上标明当前用的是哪一种：

| 口径 | 公式 | 用途 |
|---|---|---|
| **不含返利**（默认） | 各方案 Σ 应付 | 谁当场掏钱多 |
| **含预期返利** | 各方案 Σ(应付 − 该方案可得的待收返利) | 谁最终更划算 |

默认展示"不含返利"是为了与正式预算、支付保持一致（C10）；但只要有方案填了返利，就必须显著提示"切换后可比较含返利口径"，避免用户误以为返利没被计算。

**"该方案可得的待收返利"必须按各方案重新计算，不能照搬**——这是 D-86 的核心。

**D-39 押金、预付款与尾款不得重复计消费（P1）**

- **预付款/定金**：计入"已付"，属于消费的一部分（后面付尾款时只付差额）。
- **尾款**：计入"已付"。
- **押金**：**不计入消费**，单独进入"押金池"，展示为"待退押金"。退还时登记"押金退回"；押金被没收或转为消费时，用户显式操作"转为消费"，此时才进入实际支付。
- 因此：在已付 ≤ 应付的常态下，「已付 + 待付 = 应付」成立，押金在等式之外；若已付超过应付，多出的部分记为"已多付"单独提示，不冲抵押金、不静默丢弃（D-81）。

**D-40 退款冲减（P1）**
退款必须关联到具体费用条目或具体支付记录，冲减对应实际支付；退款不产生"负的支出条目"。无法关联的退款（找不到原支付）必须允许登记为"未关联退款"并显式提示，不得静默忽略。

**退款上限（P1，v8.1 复审新增；第二轮复审按"关联方式"分别定义）**

**退款有两种关联方式，上限各不相同（必须按关联方式判定，不得混用一个阈值）**

| 关联方式 | 累计退款上限 | 说明 |
|---|---|---|
| **关联到具体支付记录** | `≤ 该笔支付的金额` | 一笔 4000 的尾款，对其的累计退款不得超过 4000 |
| **关联到整个预算行**（未指明具体支付） | `≤ 该预算行下"可退款支付"之和` | 可退款支付 = 该行下**非押金**的支付记录之和（预付款 + 尾款 + 全款 + 其他） |

**一、上限的计算基准（P1）**

1. **押金不进入退款额度**：押金走"押金池 / 押金退回"（D-39），不占退款额度，也不被退款冲减。`可退款支付` **不含**押金记录。
2. **已退款金额必须参与剩余额度计算**：额度判断看的是**累计**，不是单次。`剩余可退额度 = 上限 − 该关联对象已发生的退款累计`；本次退款超额度即**拒绝保存**。
3. **两个层级的额度相互独立，不互相放大**：
   - 关联到某笔支付时：看该笔的额度。逐笔退满后，即使预算行还有余额也不能再退这一笔。
   - 关联到预算行时：看整行额度；此时**该行已发生的全部退款（无论当初记在哪一笔上）都计入累计**，避免"逐笔退满 4000 + 1000，再按整行退 5000"这种重复。
4. **任何路径下已付都不得因退款变成负数**；且 `Σ 某行全部退款 ≤ 该行可退款支付之和` 恒成立（整行层面是**硬上限**，逐笔层面是更细的约束）。

**二、超额退款与补偿（P1）**

5. 若确有超过原支付金额的补偿（商家赔付、保险理赔、额外补偿），它是**另一笔资金事项**，必须：
   - 登记为**独立的"补偿收入"条目**并说明来源（它不属于退款，不冲减任何已付，**不占退款额度**）；
   - 或（若用户认为它就是退款的一部分）先调整原支付记录，再登记退款——调整属于显式操作，必须留痕。
6. 已付为 0 之后仍到的退款，只能走第 5 条的补偿收入，不得继续冲减。
7. 押金退回不走退款口径（押金在押金池，D-39）。

> **边界说明（刻意收窄，避免扩大设计）**：本条只解决"让已付变负"与"额度算错"这两个问题，**不引入新的资金来源分类体系**。补偿收入是最小记录：能记一笔、能标注来源、能单独展示，**不进入** ③ 实际支付、**不进入** ⑤ 净成本、**不减少** 任何应付或已付、也不参与预算侧对比、**不计入退款额度**。它不构成第六层口径（D-36 仍为五层）。验收要求见 AC-LED-20/21/22/23。

### 4.6 费用归属日期与跨日分摊（对应审查项 F）

**D-41 每笔费用必须有归属日期（P1，v8.1 修订）**
归属形式二选一：单日，或日期区间（起止，**含首尾**）。
区间费用**默认按天均摊**（除不尽用最大余数法，保证各日之和 = 总额），可按 D-42 切换为其他方式。

**住宿是例外，必须按"晚"而不是按"自然日"（P1，v8.1 新增，规则见 D-46）**
"日期区间含首尾"适用于普通费用（租车、通票、按天计费的场地）；**住宿不能套用这条**，因为退房日当天不产生住宿费。

**D-42 分摊方式（P1 两种 / P2 一种）**

| 方式 | 语义 | 典型用途 | 级别 |
|---|---|---|---|
| **全额计入起始日** | 整笔金额落在归属区间的第一天，其余天为 0 | 机票、一口价费用、跨日航班 | P1 |
| **按天均摊**（住宿按"晚"、交通套餐按"段"） | 区间内每个**计价单位**等额，除不尽用最大余数法 | 3 晚套餐 3000 → 每晚 1000、多日租车 | P1 |
| **按自定义权重** | 每天/每段不同比例 | 旺季淡季不同房价 | P2 |

> **计价单位由费用类型决定**：住宿的计价单位是"晚"，普通跨日费用的计价单位是"自然日"，交通套餐是"段"。同一个"均摊"算法作用在不同计价单位上，结果不同——这正是 D-46 要单独规定住宿的原因。

**D-43 分摊不改变原始费用（P1，v8.1 修订；v8.1 复审拆分为三条独立等式）**
分摊只产生"统计口径上的分配明细"，原始报价仍是那一条整段金额。

**守恒规则：三个维度各有一条等式，同时成立（这是 v8.1 的关键修订）**

| 维度 | 必须成立的等式 | 成立条件 |
|---|---|---|
| **类别维度** | `Σ 每类合计 = 总费用` | 无条件 |
| **日期维度** | `Σ 旅行日期范围内的每日合计 + 范围外费用合计 R = 总费用` | 无条件（R 的引入见 D-45） |
| **人员维度** | `Σ 每人合计 = 总费用 − Z`（Z = 参与人为空但已计入的金额） | 无条件；当且仅当 Z = 0 时化简为 `Σ 每人合计 = 总费用` |

**日期维度为什么必须引入 R（v8.1 复审修订，取代旧写法）**

旧写法"`Σ 每日合计 = 总费用`"与 D-45"范围外费用仍计入总额、但不进入逐日视图"**在数学上不可能同时成立**。因此日期维度的等式拆成两段，并由"范围外费用合计 R"补平：

- `Σ 范围内每日合计` 只统计**归属日期落在旅行日期范围内**的已计入金额；
- `R` = **已计入总额中归属日期落在范围外的部分**（`R` 与"因异常未计入 Y"是两个不同的数，不得混用）；
- 两者相加恒等于总费用。

标准示例（旅行 9/29–10/2）：范围内费用 3000、范围外费用 500。
- 总费用 = 3500；`Σ 范围内每日合计` = 3000；`R` = 500；3000 + 500 = 3500 ✅
- `Σ 每类合计` = 3500 ✅（范围外费用**属于各自的类别**，类别维度不做范围裁剪）
- 若另有一条参与人为空的 300 元（在范围内），则 Z = 300，`Σ 每人合计` = 3500 − 300 = 3200 ✅

**三条禁令**

- 任何实现都不得让"原始金额 + 分摊明细"两条路径同时进入总额。
- **不得**为了维持"Σ 每日 = 总费用"这条旧等式，把范围外费用**静默分配到范围内某一天**（尤其是"摊到最后一天"）。范围外费用就该留在范围外。
- 每个条目在**各汇总维度上的取舍必须一致**（按条目整体排除，不按维度局部排除），具体口径见 D-55。

**D-44 归属默认值（P1，v8.1 修订）**

- 机票/车票：出发日期。
- 住宿：按晚，**第 N 晚归属入住日 + (N−1) 天**（详见 D-46）。
- 多日租车：起始日或按天均摊，用户选。
- 餐饮/门票/当地交通：录入时所选日期（默认当天，默认值可改）。
- 整段交通套餐：起始日或按段均摊，用户选。

**D-45 日期范围之外的费用（P1，与 R8 强相关；v8.1 复审补充守恒口径）**
旅行日期范围是**视图窗口**，不是数据边界（见 D-109）。落在范围外的费用：

- **仍然计入总费用**（否则缩短日期就会改变总额，与 C3 冲突）；
- **计入所属类别合计**（类别维度不按日期范围裁剪）；
- **计入人员维度**（与范围内条目一视同仁，只要参与人合法）；
- 默认**不进入逐日视图**，其金额汇总为 **R**（范围外费用合计）；
- 必须有一个显式入口显示"范围外 N 项，合计 R 元"，并可一键扩展范围。

**守恒关系（P1，与 D-43 一致）**

`Σ 范围内每日合计 + R = 总费用`。这是**唯一允许的日期维度等式**，取代旧的"Σ 每日 = 总费用"。不得为了凑旧等式而把 R 分配到范围内任何一天（D-43 禁令）。

- R 只统计**已计入总额**的范围外部分；因 L1 未计入的范围外条目不进 R（也不进任何维度，见 D-55、D-51a）。
- 范围外费用若同时参与人为空，则它**同时**计入 R 与 Z —— 两个数各自独立，互不抵扣。

**D-46 住宿的日期语义与按晚计价（P1，v8.1 新增）**

**日期语义**

1. 住宿使用**入住日 → 退房日**的区间表达，两端都为日期，**退房日当天不计住宿费**。
2. 住宿区间是**半开区间**：`[入住日, 退房日)`。
3. 实际住宿晚数 = 退房日 − 入住日（按日历日差）。
4. 入住日与退房日相同（住 0 晚）不是有效住宿，必须提示（L2）；退房日早于入住日必须拒绝并提示（L1）。

**按晚计价**

5. 住宿金额的最小计价单位是**晚**，不是自然日。
6. 按晚报价（如"每晚 320"）时，金额 = 单价 × 晚数，逐晚归属，**保留每晚真实金额**，不做平均化。
7. 整段套餐（如"3 晚 3000"）分摊时，把总额分到**这 3 个晚**上；除不尽用最大余数法，保证各晚之和 = 总额（C4）。
8. **退房日那一格的住宿费恒为 0**；该日若另有费用（如当天机票），照常归属该日，不受影响。

**示例（v8.1 标准用例）**

入住 9/29、退房 10/2、总价 3000 元（均价情形）：

| 日期 | 住宿费用 | 说明 |
|---|---:|---|
| 9/29 | 1000 | 第 1 晚 |
| 9/30 | 1000 | 第 2 晚 |
| 10/1 | 1000 | 第 3 晚 |
| 10/2 | **0** | 退房日，不计住宿费 |

- 上表是**均价**示例。若报价是"9/29–9/30 每晚 900，10/1 每晚 1200"，则按真实每晚金额归属，不拉平。
- 若总额除不尽（如 3000 分 7 晚），各晚为整数分且合计严格 = 3000。

**跨月、跨年同样适用**

9. 跨月住宿不设特殊规则：晚数按日历日差计算，**每晚归属该晚所在的自然日**。例：10/31 入住、11/2 退房 = 2 晚，分别归属 10/31 与 11/1；11/2（退房日）为 0。跨年同理。
10. 住宿区间可以超出旅行日期范围（见 D-45），仍按上述规则计算，不影响总额。

### 4.7 个人费用与公共费用分摊（对应审查项 E）

**D-50 承担方式四选一（P1 前三种）**

| 承担方式 | 用途 | 级别 |
|---|---|---|
| 全员均摊 | 房费、租车、门票团购 | P1 |
| 指定成员承担 | 某人的个人购物、单独加床 | P1 |
| 部分成员均摊 | 只有 3 人去的景点 | P1 |
| 按权重分摊 | 复杂比例（如按票价比例） | P2 |

**参与人规则（P1，v8.1 修订：不再承诺无条件四向守恒；v8.1 复审：人员维度统一写为 `Σ 每人合计 = 总费用 − Z`）**

- 每个费用条目的参与人**默认为"全员"**，正常录入时不应为空。
- 若用户把参与人清空 → 该条目仍合法存在、仍计入总费用，但**从人员维度缺席**；按 D-90 记为 **L2 警告**（不是 L1，因为总额仍然可信），并按 D-55 计入"已计入但未分摊 Z"。
- **不得自动分配**：参与人为空时，系统不得替用户选择"全员"或任何成员来完成守恒。默认值只在**新条目创建时**填充，用户主动清空后不再回填。
- 参与人集合的变化不改变条目总额，只改变"算在谁头上"。
- 目的：宁可让用户看到"人员维度不完整、差 Z 元"，也不给出一个看起来对、实则被系统擅自编造的按人分摊。

**D-51 分摊必须严格守恒（P1，底线 C4）**
100 元分给 3 人 → 34 / 33 / 33 或 34 / 34 / 32，**合计必须严格等于 100**；任何人拿到的份额不得为负。余数分配必须确定（最大余数法 + 稳定次序），同一输入必得同一结果。

**D-51a 三类金额与两条分摊守恒（P1，v8.1 复审新增）**

旧写法只有一条不变量「该条目的分摊明细之和 = 该条目应付金额」，这条在"参与人为空"与"L1 异常"两种情形下都**必然不成立**。因此把金额和守恒分别拆开定义。

**三类金额，先分清再求和（同一笔钱只能走一条路径）**

| 名称 | 定义 | 用途 |
|---|---|---|
| **条目原始金额** | 该条目的应付金额（口径 ②，已扣商家/平台优惠、未扣返利） | 进总费用的**唯一**来源 |
| **日期分摊明细** | 原始金额按"晚/天/段"切给各归属日的份额 | 只用于逐日视图求和 |
| **人员分摊明细** | 原始金额按承担方式切给各成员的份额 | 只用于人员维度求和 |

- 三者**不得相加**：总费用只由"条目原始金额"求和（D-43 禁令）。日期分摊与人员分摊都是派生视图，不是新的费用记录。
- 一个条目在同一时刻只有**一套**日期分摊明细与**一套**人员分摊明细；改分摊方式只替换明细，不产生第二份金额。

**日期分摊守恒（P1）**

> 对**正常计入汇总**的条目：`Σ 该条目的日期分摊明细 = 该条目原始金额`。

- 适用对象：所有计入总费用的条目（含明确 0 元、含参与人为空、含归属日期在范围外的条目）。
- 归属日期在范围外的条目，其日期分摊明细**照样守恒到该条目金额**，只是这些明细被 D-45 归入"范围外合计 R"，不显示在逐日视图里。
- **不适用**：因 L1 被排除的条目（它们根本不进汇总，见下）。

**人员分摊守恒（P1，分三种情形）**

| 情形 | 人员分摊 | 该条目对 Z 的贡献 |
|---|---|---|
| 参与人合法且非空 | `Σ 该条目的人员分摊明细 = 该条目原始金额` | 0 |
| 参与人为空（L2） | 人员分摊明细**为空集合**（**不得**编造 0 元份额、**不得**默认全员） | 该条目原始金额全部计入 Z |
| L1 排除条目 | 不进入正常人员分摊，也不进入任何守恒计算 | 0（其金额另计入"因异常未计入 Y"） |

- **不得把参与人为空写成"每人 0 元"**：那会让 `Σ 每人合计` 看起来很完整，实则把 Z 藏起来。
- L1 排除条目**同时**从日期、类别、人员、总额四个维度缺席（D-55 第 1 条），因此它既不参与任何守恒等式，也不计入 Y 以外的任何合计。

**Y / Z / R 的区别（不得混用）**

| 符号 | 含义 | 影响哪条等式 |
|---|---|---|
| **Y** | 因 L1 而**未计入**总费用、**且有可计算金额**的部分之和 | 决定"总费用"本身的大小（Y 不在里面） |
| **Z** | **已计入**总费用、但因参与人为空而未落到人头的金额 | 影响人员维度：`Σ 每人合计 = 总费用 − Z` |
| **R** | **已计入**总费用、但归属日期在旅行范围外的金额 | 影响日期维度：`Σ 范围内每日合计 + R = 总费用` |

> 三者可以同时非零，且互不抵扣。验收 AC-SUM-07 与 AC-SUM-09 专门守这一条。

**Y 只能统计"有金额"的异常，不得伪造金额（P1，第二轮复审新增）**

L1 的成因很多，但**并非每一种都能算出一个金额**。必须把它们分开计数，**不得**为了凑出一个 Y 数而给"没有钱的异常"编造 0 或估值：

| L1 成因 | 是否进入 Y | 展示方式 |
|---|---|---|
| 优惠超过原价（D-35） | ✅ 进入 Y，金额 = **原始报价**（不是展示的 0，也不是负差额） | 计入 Y 金额与条数 |
| 人员双占（同人同晚两处） | ✅ 进入 Y，金额 = **该晚两个冲突房间项在该晚的金额之和**（系统不预设排除哪一侧，见 D-23「双占冲突时排除哪一侧」） | 计入 Y 金额与条数 |
| 套餐与房间重复占用（D-21 第 10 条） | ✅ 进入 Y，金额 = **被排除的房间候选那一侧金额** | 计入 Y 金额与条数 |
| 悬空引用（候选已删除） | ❌ **不进入 Y**（金额已无从得知） | **只计入条数**："N 项因候选删除无法计价" |
| 计价要素不完整（缺单位/数量/周期） | ❌ **不进入 Y**（无法计算） | 只计入条数 |
| 数量口径未声明（D-21 第 5a 条） | ❌ **不进入 Y**（无法计算） | 只计入条数 |
| 待估（D-33） | ❌ **不进入 Y**（本来就没有金额） | 只计入条数，且**单独一类**（"另有 N 项待估"） |
| 数量口径待确认（D-21 第 5c 条） | ❌ **不进入 Y** | 只计入条数，单独一类（"待确认数量 N 项"） |

- 汇总处展示格式必须能容纳"只见条数不见金额"的情况，例如：**因异常未计入 Y 元（N 条，其中 M 条无金额可计）**。
- **禁止**把"无金额可计的异常"按 0 计入 Y 金额——那会让 Y 看起来"完整"，实际上掩盖了"有 N 项根本算不出来"这个更严重的问题。
- Y 的**条数统计必须覆盖全部 L1 条目**（含无金额的），金额统计只覆盖有金额的那部分；两个数字都要可见。

**D-52 归属与分摊必须可追溯（P1）**
每个人看到的金额，必须能回答"这笔钱为什么算在我头上"：来源费用条目、分摊方式、参与人数、我分到多少、余数是否分给我。

**D-53 人均与"每个人的费用"是两件事（P1）**

- **人均** = 总费用 ÷ 参与人数（一个展示指标，不需要守恒到分）。
- **每个人的费用** = Σ 该成员在各费用条目上的分摊额；各人相加 = **总费用 − 未分摊金额 Z**（D-55）。
- 两者显示必须标注区别，避免"人均"被当成"每人应付"。
- 存在未分摊金额时，"每个人的费用"区域必须显示"另有 Z 元未分摊到人（M 条）"。

**D-54 不参与成员的处理（P1）**
某成员不参加某项费用（如婴儿不含门票），从该条目的参与人中移除即可，不改变其票档，也不影响其他条目。

**D-55 未分摊金额与各维度排除口径（P1，v8.1 新增）**

**统一排除原则（按条目整体排除，不按维度局部排除）**

1. 一个费用条目要么**整体进入所有适用的汇总维度**，要么**整体从所有维度排除**；不允许"从人员维度排除、却仍静默计入日期维度"。
2. 被排除的条目必须在界面上**始终可见**，并汇总为一个"未计入金额"合计。
3. 排除只影响**汇总展示**，不影响条目本身的存在、保存与编辑（C3）。

**逐状态口径（与 D-90 的 L1 对齐）**

| 条目状态 | 计入总费用 | 计入每日 | 计入每类 | 计入每人 | 参与排名 |
|---|---|---|---|---|---|
| 正常已定价 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 明确 0 元（免费/免票/赠送） | ✅（0） | ✅ | ✅ | ✅ | ✅ |
| 待估 | ❌ | ❌ | ❌ | ❌ | ❌ |
| 数量口径待确认（D-21 第 5c 条：间数不一致且用户未确认） | ❌ | ❌ | ❌ | ❌ | ❌ |
| 计价要素不完整（缺单位/数量/周期） | ❌ | ❌ | ❌ | ❌ | ❌ |
| 优惠超过原价（异常 0 元，见 D-35） | ❌ | ❌ | ❌ | ❌ | ❌ |
| 人员双占（同一人同晚两处住宿） | ❌（**该晚冲突两侧**） | ❌ | ❌ | ❌ | ❌ |
| **套餐与房间重复占用：只排除"房间候选"那一侧**（D-21 第 10 条） | 被排除的那侧 ❌；**套餐侧照常计入 ✅** | 同左 | 同左 | 同左 | ❌（方案整体不参与排名） |
| 悬空引用（候选已删除） | ❌ | ❌ | ❌ | ❌ | ❌ |
| 参与人为空（其余正常） | ✅ | ✅ | ✅ | **❌** | ✅（L2 警告，不阻断排名） |
| 正常，但日期在旅行范围外（D-45） | ✅ | ❌（范围外，计入 R） | ✅ | ✅ | ✅ |

> **「套餐与房间重复占用」这一行的排除范围必须精确到"房间候选那一侧"（第二轮复审修正）**：
> - D-21 第 10 条已规定：整段套餐生效时，**房间候选那一侧**判 L1、不计入合计；**套餐本身照常贡献金额**。
> - 因此本表这一行**不得**被理解为"整张住宿单从所有维度排除"。举例：套餐 3000 + 冲突房间候选 900 → 总额中**含 3000**、不含 900；**不得**合计成 3900，**也不得**让住宿类变成 0。
> - 方案因存在 L1 而整体不参与最低价排名（D-74），这与"金额是否计入"是两件事。
>
> **最后两行是仅有的两种"部分维度缺席"，且都不得静默**：
> - **参与人为空**：这笔钱确实要花（进总额、进每日、进每类），只是不知道算谁头上。它**只从人员维度缺席**，金额计入 **Z**，必须显式声明。
> - **日期在范围外**：这是视图窗口问题（D-45），不是数据问题。它只从**逐日视图**缺席，金额计入 **R**，其余维度照常。
>
> 「计入每日」一列的"✅"指该条目**在逐日视图里按分摊明细显示**（若其归属日不在旅行范围内，则这些明细归入 R 入口而非逐日格子里）。

**必须显示的四个数（P1，v8.1 复审修订：由三数扩为四数）**

4. 汇总处必须同时能回答四件事：**已计入 X 元** / **因异常未计入 Y 元（N 条，其中 M 条无金额可计）** / **已计入但未分摊到人 Z 元（M′ 条）** / **已计入但归属日期在旅行范围外 R 元（K 条）**。
   - **Y 的金额只统计"有金额"的 L1**；无金额可计的 L1（悬空引用、计价要素不全、待估、数量口径未定）只计入条数，**不得伪造 0 元**（见上文「Y 只能统计"有金额"的异常」）。
5. 关系必须明示，四条等式同时可核对：
   - `总费用 = X`（X 已包含 R 与 Z 涉及的金额）
   - `Σ 每人合计 = X − Z`
   - `Σ 范围内每日合计 = X − R`
   - `Σ 每类合计 = X`（**类别维度不做范围裁剪**，范围外费用仍归入其类别）
6. **不得为了让"每人合计 = 总费用"而自动把 Z 分摊给任何成员**（包括默认全员、默认户主）。未分摊就是未分摊。
7. **不得为了让"每日合计之和 = 总费用"而把 R 摊进任何一天**（D-43 禁令）。R 只能通过"范围外 N 项 / 合计 R 元"入口查看。
8. X、Y、Z、R 四者**互不抵扣**：不能用一个数减去另一个数来"凑平"，每个数都必须由自己的定义直接算出（D-51a）。

**修正后自动恢复（P1）**

9. 用户补上参与人后，该条目自动回到人员维度，Z 相应减少，无需其他手工操作。
10. 用户修正优惠后，D-35 的异常状态自动解除，条目自动回到全部维度（见 D-35 第 7 条）。
11. 用户延长旅行日期范围使某条目回到范围内后，该条目自动回到逐日视图，R 相应减少（D-109）。

### 4.8 报价来源与有效性（对应审查项 I）

**D-60 候选报价的可追溯信息（P1）**
每个候选报价可记录：报价平台/渠道（文本）、查询日期、适用旅行日期、报价有效期（可选）、原始链接（**仅作为文本留档，永不访问网络**）、报价备注（含早、可退、需预付等）。

**D-61 过期提示不做武断推断（P1）**
判定规则只有两条，其余不猜：

1. 填了有效期且已过 → 标记「**已过期**」（L2 警告）。
2. 只填了查询日期 → 显示"查询于 X 天前"，**不做"可能过期"的自动判定**。

（"超过 N 天提醒"这类阈值为 **P2**，因为阈值武断且会制造噪音。）

**D-62 过期不等于不能选（P1）**
过期报价仍可被选用、仍计入合计、仍参与排名，只是带警示标记。理由：用户录入的是他真实看到的价格，系统无权替他作废。

**D-63 适用日期与占用日期不一致（P1）**
候选的"适用旅行日期"必须与它被启用后实际占用的日期一致：

- 住宿候选的适用区间必须覆盖住宿单的入住区间，否则 **L1**（"报价适用 9/29–10/2，但住宿单是 9/29–10/3，缺 1 晚"）。
- 交通候选的适用日期必须是所在区段的出发日期，否则 **L2**（"报价日期与区段日期不一致，可能查的是别的日子"）。
- 允许用户显式确认"就用这个价"，确认后降为 L3 提示并记录该决定。

> 这条防的是查价时的典型错误：**把 9/30 的价填进了 9/29 的候选**，导致方案看起来便宜、实际订不到。

### 4.9 方案、正式预算与快照（对应审查项 G）

**D-70 三级关系（P1）——本节是 v8 最关键的规则**

| 层 | 性质 | 与候选的关系 | 变化时 |
|---|---|---|---|
| **候选报价** | 事实（可编辑） | 自身 | 改价、删除、过期 |
| **普通方案** | 引用（可多个、可命名） | **引用候选**，实时反映 | 候选改了 → 方案金额随之变，并提示"受影响" |
| **正式预算** | 快照（决策时刻冻结） | **不引用**，保存金额与构成副本 | 候选改了 → 正式预算**不变**，只提示"现价与预算差 X" |

**D-71 方案是引用式的（P1）**
方案保存的是"每个消费对象选了哪个候选"这份**选择关系**，不是金额副本。

- 候选改价 → 所有引用它的方案金额**立即按新价重算**，并在方案列表上标记"候选已变化，差额 +X"。
- 候选被删除 → 引用处成为"悬空引用"，该方案进入 L1 冲突（不计入排名），并可一键"重新指定候选"。
- 方案复制 → 复制选择关系与名称，**不复制候选**；副本与原方案继续引用同一批候选。

**D-72 正式预算必须快照（P1，底线 C11）**
确认正式预算时，冻结：每个条目的名称、承担方式、金额（应付口径）、分摊设置、日期归属。
此后：

- 候选改价**不改**正式预算金额；
- 界面必须显示"当前候选现价 vs 预算价"的差额，让用户知道"如果现在订会多花/少花多少"；
- 用户可显式执行「按现价刷新预算」→ 生成**新版本**，旧版本保留（至少保留上一版，P1；完整版本对比 P2）。
- **正式预算行是支付记录的唯一归属对象**（D-80、D-87）；刷新版本后历史支付的归属与金额不变。

**D-72a 预算版本的四条硬规则（P1，v8.1 新增；v8.1 复审增补第 4 条）**

1. **旧版本只增不改**：生成新版本后，任何历史版本的内容都不可再编辑、**也不可删除其预算行**，只能查看与对比。破坏性的删行操作只允许发生在"当前可编辑版本"上（D-87 第 6 条）。
2. **版本必须有可辨识的标识**：至少包含版本序号与生成时间；版本切换在任何相关界面都必须可见。
3. **支付不随版本升级而漂移**：旧版本的支付仍算"旧版本已付"；新版本从"未支付"开始计算待付，除非用户显式转移（D-87 第 4 条）。
4. **版本保留与历史可追溯的分界（v8.1 复审新增）**：
   - **保留数量**：P1 至少保留**当前版 + 上一版**（完整版本历史与版本间全量对比为 P2-04）。
   - **清理旧版本时不得破坏历史支付的归属**：更早的版本被清理后，其下已发生的支付**仍然存在**，并且必须仍能回答"这笔钱当时属于哪一版、哪一行、多少金额"。
   - 因此允许保留一份**最小的历史归属快照**：只包含"该支付当时所属的版本序号、预算行标识与名称、该行金额、支付金额"。它**仅用于显示与追溯，不参与任何汇总计算**。
   - **这不是完整财务系统、也不是无限版本管理**：不保留完整条目结构、不保留候选、不做版本间逐字段差异比对（D-85、P2-04）。清理动作必须显式、可撤销，并明确告知"将清理哪些历史版本的完整内容、哪些归属信息会被保留为快照"（C3）。

**D-73 正式预算的手动调整（P1）**
允许手动追加/修改预算行（如"临时加了机场接送 120"）。规则：

- 手动行必须标注来源"手动"与原因；
- 手动行不覆盖原有快照行，只做增量或显式替换；
- 每次调整记录时间，可撤销。

**D-74 排名资格（P1）**

| 情况 | 计入合计 | 参与"最低价"排名 |
|---|---|---|
| 全部已定价、无冲突 | ✅ | ✅ |
| 明确录入的 0 元条目 | ✅（0） | ✅（合法） |
| 含 1 项以上待估 | ❌（待估那一笔不参与，其余照计） | ❌ 显示"待估，不参与排名" |
| 含 L1 冲突（人员双占/悬空引用/计价要素不全/套餐与房间重复占用/优惠超过原价） | 冲突涉及的那一笔不计；其余照计 | ❌ |
| 参与人为空（其余正常） | ✅（该笔仍进总额） | ✅（L2 警告，不影响排名；但人员维度不完整，须显式声明） |
| 报价已过期 | ✅ | ✅ 但带警示 |
| 返利适用范围未明确 | ✅ | ✅（该返利不计入任何口径，见 D-86） |
| 空方案（一条费用都没有） | 0 | ❌ 提示"疑似漏填" |

**口径澄清**：合计列说的是"哪些钱被算进去"，排名列说的是"这套方案有没有资格评第一"。两者不同：一个有 1 项待估的方案仍然会显示"已计 12800 + 含 1 项待估"，只是它不能当"最便宜"。

**D-75 天数不同的公平比较（P1）**
方案对比必须同时给出三项：总价、人均、日均。总价是主排序，人均/日均是辅助指标，**不得用日均替代总价做唯一排名**。
**日均口径** = 总价 ÷ 旅行自然日数（含首尾）；若存在日期范围外的费用，必须标注口径说明（该费用计入总价但不属于这些自然日，故日均会被抬高）。
**补充（P1，v8.1 复审）**：日均的分母**固定为旅行自然日数**，不因存在 R 而改变；标注文案必须同时给出分子构成（"总价 X（含范围外 R）÷ 自然日 D 天"），让用户看得出日均为何偏高。反向口径"仅按范围内费用计算的日均"可以作为附加展示，但**不得**作为默认或排名依据。

**D-76 非金额属性（P1 只做并排展示）**
方案对比可并排展示：出发/到达时刻、是否含早、婴儿床、泳池、亲子房、可取消性、交通时长。
**P1 只做"结构化标签的并排展示与筛选"**，不做加权评分、不做"折腾度打分"（Won't）。

**D-77 方案数量（P1 无产品上限 + 统一性能指标）**
产品层面不设方案数量上限。性能与体量指标统一到**一处定义**，供 D-77、AC-UX-03、P2-11 共同引用：

| 指标 | 目标值 | 说明 |
|---|---|---|
| 方案数量（流畅） | ≤ 50 套 | 切换、重算均流畅 |
| 方案数量（降级） | 200 套 | 给出提示并启用大面积数据下的列表降级策略 |
| 候选数量（验收线） | ≤ 1000 条 | 筛选/搜索仍需可用 |
| 单次交互响应 | < 200ms | 切换方案、筛选、改价后重算 |
| 单文件体积（告警线） | 1 MB | 超过时提示，但不阻止使用 |

- 这是**产品级验收线**，不是承诺；超过阈值时允许降级（如列表分页/折叠），但不得丢失数据或改变金额。
- 具体阈值如需调整，在 §9 Q7 中裁决，改动后 D-77、AC-UX-03、P2-11 三处同步。

### 4.10 实际支付、退款与记账（对应审查项 H）

**D-80 一项预算 → 多笔支付（P1，v8.1 修订）**

**支付记录的唯一归属对象：正式预算行**

一笔支付必须且只能归属到以下之一（这是 D-87 的边界）：

| 支付归属对象 | 含义 | 是否进预算侧 |
|---|---|---|
| **正式预算行** | 计划里本来就要花的一笔 | ✅ 进入该预算行的实际支付 |
| **预算外支出** | 计划里没有的临时花费（D-82） | ❌ 不进预算侧，单列 |

**集合口径（P1，第二轮复审新增：这条决定所有现金汇总怎么写，必须写在前面）**

- **支付记录是唯一的、统一的集合**：每一笔实际发生的付款就是**一条**支付记录，"归属"只是它的一个取值（预算行 / 预算外），**不是**两个并列的金额池。
- 因此 **"预算外支出"是"归属=预算外"的那部分支付记录**，不是"支付之外的另一笔钱"。任何汇总都**不得**写成 `Σ 全部支付 + 预算外支出` —— 那会把预算外那部分算两次（预算内 5000 + 预算外 300 会显示成 5600，而真实现金流出是 5300）。
- 正确的汇总只有两种写法，都从同一集合出发：
  - **按归属拆分**：`Σ(归属=预算行) + Σ(归属=预算外) + Σ(归属=待处理) = Σ 流出类`（拆分后相加才等于总数，且各份额只出现一次）。其中"待处理"是第三种归属取值，见下文与 D-80b。
  - **整体求和**：直接 `Σ 流出类`，不再另加任何"预算外"项。
- **待处理支付**（D-87 第 6 条情况 B）在归位前**不进入预算侧与预算外侧**，但**仍然计入全程现金**（它确实发生过付款），且必须单独可见。取数细节见 D-80b。
- **不存在"直接挂候选报价"或"直接挂方案"的支付**：方案会随候选变化，而支付是既成事实，两者性质不同。
- 一个预算行可关联**多笔**支付记录，每笔有：金额、日期、类型、支付方式（文本，如"微信/信用卡/现金"）、备注。
- 类型：**预付款 / 尾款 / 全款 / 押金 / 押金退回 / 退款 / 其他**。

**D-80b 记录类型的三分类与取数规则（P1，第三轮复审新增：所有现金公式的唯一取数依据）**

"支付记录"这个集合里混着三种性质完全不同的记录。**任何汇总都必须先按类型筛选，再求和**；直接写"Σ 全部支付"是不完整的表述，因为它没有说明包含哪些类型。

| 分类 | 包含的类型 | 金额符号 | 含义 |
|---|---|---|---|
| **流出类** | 预付款、尾款、全款、其他、**补偿收入的支出侧不走这里** | 正 | 真正花出去的钱 |
| **冲减类** | 退款、押金退回 | 正（记绝对值） | 冲减对应的流出 |
| **押金类** | 押金 | 正（记绝对值） | 只是资金占用，不是消费 |

**三条取数规则（必须逐字遵守，任何汇总不得自创口径）**

1. **`Σ 流出` 只含流出类，不含退款、不含押金、不含押金退回。**
   - 这是"全部支付"在公式中唯一允许的含义：**`Σ 全部支付 ≡ Σ 流出类记录`**（按归属再区分预算行/预算外/待处理）。
2. **退款与押金退回永远作为"减项"单独出现，不得同时出现在被减数与减数里。**
   - 正确：`净额 = Σ 流出 − Σ 退款 − Σ 押金退回`
   - **错误**：把退款先加进"全部支付"、再减一次 Σ退款 → 同一笔退款被扣两次（原始支付 4800、退款 800，会算成 4800 + 800 − 800 = 4800 或 4800 − 800 − 800 = 3200，都不是 4000）。
3. **押金与押金退回自成闭环，不参与任何"消费/已付"计算。**
   - `押金池 = Σ 押金 − Σ 押金退回 − Σ(已转为消费的押金)`，恒不进入 D-81 的已付、不进入净成本。

由此得到 D-81 与 D-87a 各公式的**完整展开式**（此前写作简式，现补全类型过滤）：

| 汇总值 | 完整展开式 |
|---|---|
| 某预算行的已付（D-81） | `Σ(该行流出类) − Σ(关联该行的退款)`；**押金类不计入** |
| ① 当前版本已付 | `Σ(归属=当前版本预算行的流出类) − Σ(关联该版本的退款)`；**押金类不计入** |
| ② 全程已付现金 | `Σ(全部流出类，含预算行/预算外/待处理归属) − Σ(全部退款)`；**是否含押金由 Q2 裁决**（见 D-87a） |
| ⑤ 最终净成本 | `实际支付 − Σ(状态=已到账的返利)`，其中"实际支付"= ③ 口径，**押金类不计入** |

- **验收要求**：AC-LED-19b 保留并补类型过滤（原始支付 4800 + 退款记录 800 → 全程已付 4000，**不是** 4800、**不是** 3200）。

**D-81 已付与待付（P1）**
已付 = Σ(预付款 + 尾款 + 全款 + 其他) − Σ退款（差额为负即"已多付"，必须显式提示）。
待付 = 应付 − 已付，取非负值；当已付 > 应付 时待付记为 0，并另以"已多付 X 元"单独提示。
押金单独成池，不进上述等式（D-39）。

> **取数规则见 D-80b**：上式的 `Σ(预付款+尾款+全款+其他)` 就是"流出类"四项，**退款只作减项、不得先加后减**；押金与押金退回不进本式。

**D-82 临时支出与未预算支出（P1）**
允许记录"没有对应预算条目"的支出：它计入实际支出总额与复盘，**不进入预算侧**，并在复盘里单列"预算外支出 X 元"。

- 预算外支出**不得**被"顺手"归入某个预算行来消除差异；归入是一个显式动作（D-87 第 4 条的转移），且必须留痕。

**D-83 返利登记（P1，v8.1 修订）**
每笔返利必须有：金额（比例或固定，二选一，见 D-86）、**适用范围**（单项 / 多项 / 整单，见 D-86）、状态（预计 / 已确认 / 已到账）、到账日期（到账后填写）。

- 适用范围**必填**；未填的返利只展示、不参与比较与排名（D-86 第 10 条）。
- 一笔返利只能有一个适用范围，不得同时对单项与整单生效（D-86 第 9 条）。
- 比例型返利的计算基数是**实际应付**（扣商家优惠与平台优惠、不扣返利本身），单项/多项/整单三种范围口径一致（D-86 计算基数第 1 条）。
- 返利可挂在费用条目、一组费用条目，或整个方案上；这三种分别对应单项、多项、整单。

**D-84 复盘三差（P1）**

- 预算差 = 应付 − 实际支付（同口径 ② 与 ③，需说明这是"预算 vs 现金"）
- 净成本差 = 应付 − 最终净成本（② vs ⑤）
- **待收返利 = 预计返利 + 已确认返利**（**按适用范围汇总，整单返利按决算时的方案总额重算**）

口径提醒（P1，v8.1 复审修订）：

1. 「待收返利」**不含已到账返利**。已到账返利已经体现在"最终净成本"里，若再从待收里扣一次，等于同一笔返利扣两次（D-38）。
2. 三差使用的都是**同一批费用条目**，因此三差各自的口径基线必须写明；不得用一个"净支出"数同时承担三差。
3. 存在待估项或 L1 异常项时，三差仍需显示，但必须标注"基于已计入金额计算"（D-55）。

三个差必须分开显示，且每个都标注口径（C10）。

**D-85 不做通用财务（Won't 边界）**
不做账户/余额/多账户对账、不做信用卡账单导入、不做发票管理、不做 OCR 识别小票、不做提醒通知。

**D-86 返利的适用范围与计算基数（P1，v8.1 新增；v8.1 复审补全计算基数）**

**每笔返利必须有且只有一个适用范围**

| 适用范围 | 适用对象 | 计算方式 | **计算基数（比例型）** |
|---|---|---|---|
| **单项返利** | 一个指定的费用条目 / 一个候选报价 | 该条目的金额参与计算 | 该**指定条目**的实际应付（②） |
| **多项返利** | 一组指定的费用条目（用户显式勾选） | 只按被勾选条目的金额之和计算 | 被勾选各条目实际应付（②）之和 |
| **整单返利** | 当前方案的**全部**费用条目 | 按该方案总额重新计算 | 该方案中所有符合条件条目的实际应付（②）之和 |

**计算基数（P1，本条对所有比例型返利统一生效）**

1. **比例型返利的基数一律是"实际应付"（口径 ②）**，即已扣除商家优惠与平台优惠、**但未扣除返利本身**的金额。原始报价（①）不能作为基数，因为用户不会为已经优惠掉的部分拿返利。
   - 标准示例：原始报价 1000 − 商家优惠 100 − 平台优惠 100 = 实际应付 800；1% 比例返利为 **8 元**（不是 10 元）。
2. **固定型返利不随基数变化**：填写绝对金额，与条目金额、方案总额均无关（第 4 条）。
3. **不进入基数的条目**（三种范围一律适用）：
   - **待估条目**不参与返利基数（没查到价，不能假装它产生了返利）；
   - **L1 异常条目**不参与返利基数（优惠超过原价、人员双占、计价要素不全、悬空引用、套餐与房间重复占用）；
   - **明确 0 元条目**参与基数计算，但因其应付为 0，对返利金额的贡献为 0（**明确写死，不留解释空间**：0 元条目"在基数里，但加 0"）。
4. **固定返利不随计算基数变化**：0 元条目、待估条目的增减都不改变固定返利金额；固定返利的资格条件（例如"该条目必须存在）"由用户在登记时自行判断，系统不推断。

**规则**

5. **每笔返利必须明确适用范围**，未选择适用范围时不得保存为"有效返利"（可保存为草稿，但不参与任何计算与排名）。
6. **单项返利只计算对应费用**：其他条目变了不影响它。
7. **多项返利只计算指定费用**：未被勾选的条目再贵也不产生返利。
8. **整单返利必须按当前方案重新计算**（比例型），或明确为**固定金额**（固定型）。两种形态只能二选一，不得混用：
   - **比例型**：填写比例（如 1%），每个方案各自用 `该方案适用金额 × 比例` 计算。方案 A 20000 → 200；方案 B 20200 → 202。
   - **固定型**：填写绝对金额（如 200），所有方案都返同样的钱，与方案总额无关。
   - 一笔返利一旦选定了形态，其金额语义就固定；改形态视为改规则，必须显式操作并留痕。
9. **同一笔返利不得重复计算**：一笔返利只能有一个适用范围。若用户既要"单项返 50"又要"整单返 1%"，那是**两笔独立返利**，各自登记；系统不得让同一笔返利既按单项计入又按整单计入。
   - **同一条目不得因多个返利范围被同一笔返利记录命中**：一个条目可以同时被"单项返利 A"和"整单返利 B"覆盖（这是两笔不同返利，合法）；但**同一笔返利记录**不得同时把该条目算两次。
10. **适用范围不明确的返利只展示、不参与排名**：显示为"返利待明确（不影响比较）"，并在方案对比中给出提示。
11. **预期返利与已到账返利分开**：比较口径用"待收返利（预计 + 已确认）"；复盘净成本用"已到账"（D-38、D-84）。
12. **返利口径必须在方案比较界面始终可见**：当前用的是"不含返利"还是"含预期返利"，以及是否含"待明确返利"，都要标明。

**整单返利的边界（P1）**

13. 整单返利的"适用金额"= 该方案中**已定价且无 L1** 的条目应付之和（即实际被计入合计的那部分），**不含待估项、不含异常项**。理由：没查到价的项不该被当成"已经产生返利"。单项与多项返利使用同一排除口径（第 3 条）。
14. 若某方案存在 L1（不可排名），其整单返利仍可展示为参考值，但该方案本来就不参与排名，因此返利不影响名次。

**示例（必须表现一致）**

| 方案 | 应付合计 | 整单返利（比例型 1%） | 含返利口径下的净额 |
|---|---:|---:|---:|
| A | 20000 | 200 | 19800 |
| B | 20200 | 202 | 19998 |

- 若该返利是**固定型 200 元**：A → 19800，B → 20000。
- **不得**出现"A 用 1% 算出 200、B 却仍用固定 200"这类混用。

**D-87 支付与正式预算版本的关系（P1，v8.1 新增；v8.1 复审拆分"不再包含"与"真正删除"）**

**核心原则：支付是既成事实，预算版本是计划。计划可以改，事实不能改。**

1. **支付永远归属到它发生时的那一版正式预算行**。刷新预算生成新版本后，旧支付**不会自动转移到新版本**。
2. 刷新预算后，界面必须能说清三件事：
   - 新版本预算总额是多少；
   - 已发生的支付有多少（属于旧版本）；
   - 这些支付在新预算下对应哪些行、是否有行被删除或金额变动。
3. **新版本与旧版本之间必须能对比**：至少显示总额差、按类别差、以及"哪些行新增/删除/改额"。
4. **已有支付是否可以转移到新版本**：**默认不转移**。若用户显式执行转移，必须逐笔确认，并记录"这笔支付从版本 N 转到版本 M"的痕迹。
   - 转移的前提：目标预算行存在，且**累计金额可容纳**；否则不得转移（避免出现某行已付 > 应付的假象）。
   - **累计校验（P1，第三轮复审新增）**：校验的是**累计**，不是单笔。每次转移必须满足
     `目标行已有支付 + 本次转入金额 ≤ 目标行金额`。
     两笔各 1500 元转入一个"5000 元预算、已有 3000 元支付"的行时，第一笔通过（4500 ≤ 5000），**第二笔必须拒绝**（6000 > 5000）。
   - **超额处理**：**拒绝转移并说明剩余可容纳额度**；不采用"允许转入并标记已多付"（那会让转移动作变成制造异常的手段）。用户若确实多付，应在原归属行上按"已多付"处理（D-81），而不是靠转移制造。
5. **候选改价不得改变历史支付的金额与归属**：支付记录一旦写入，其金额、日期、类型、归属行都不可被候选变化影响（C11 在记账侧的延伸）。
6. **多版本共存期的统计口径**：预算 vs 实际对比默认用**最新版本**做预算侧；同时必须能切换到"按版本 N 对比"，且口径始终可见（C10）。

**"新版本不再包含某预算行"与"预算行被真正删除"是两件不同的事（P1，v8.1 复审新增，必须分别实现）**

**先确定一件事：破坏性操作只可能发生在"当前可编辑版本"上（第二轮复审新增）**

D-72a 第 1 条规定"旧版本只增不改"，因此**冻结的历史版本不可编辑、也不可删除其预算行**。于是"真正删除一个预算行"只可能发生在两种对象上，且都必须满足"该对象未被冻结"：

| 对象 | 是否允许删除其中预算行 | 依据 |
|---|---|---|
| **当前可编辑版本**（最新版，尚未被刷新取代） | ✅ 允许（删除属破坏性操作，须可撤销或事先确认，C3） | D-72a 只冻结"历史版本" |
| **已被刷新取代的历史版本** | ❌ **不允许**（不可编辑、不可删除） | D-72a 第 1 条 |

> **因此不存在"删除 V1 的预算行"这种操作**：一旦 V2 产生，V1 即为历史版本、整体冻结。若用户确实想删掉某一行，正确路径是**在 V2（当前可编辑版本）里删除该行**，再由 D-87 情况 A/B 决定支付归宿。

**两种情况**

| | **情况 A：新版本不再包含某预算行** | **情况 B：当前可编辑版本中的预算行被真正删除** |
|---|---|---|
| 触发场景 | 用户执行「按现价刷新预算」，新版本里没有这一行了 | 用户在**当前可编辑版本**里显式删除该预算行（该行此前已有支付归属于它） |
| 旧版本预算行 | **仍然保留**（旧版本只增不改，D-72a 第 1 条） | 不适用（被删的就是当前版本的行，删后该行不存在） |
| 历史支付 | **继续归属于旧版本的那一行**，金额与归属都不变 | **不得被删除**（C3） |
| 是否自动转为待处理支付 | **否** | **是**：进入"待处理支付"状态 |
| 是否自动被新版本继承 | **不自动继承** | 不适用 |
| 用户后续动作 | 希望这些支付对应新预算时，必须**显式执行转移**（第 4 条），逐笔确认并留痕 | 必须**显式重新归属**或转为预算外支出，逐笔操作并留痕；新归属写入后保留原始金额、日期、支付类型与历史来源信息 |
| 提示文案 | "这 3 笔支付共 3000 元属于 V1 的『住宿』行；V2 已不再包含该行，支付仍保留在 V1" | "该预算行已删除，仍有 3 笔支付共 3000 元需要归位" |

- **禁止把两种情况实现成同一个操作语义**：刷新预算**不得**触碰历史支付，也不得把它们变成待处理；只有**在当前可编辑版本里真正删除预算行**才产生待处理支付。
- **禁止对历史版本执行删除**：情况 B 的操作对象只能是"当前可编辑版本"。对被刷新取代的历史版本，删除入口必须不存在（或禁用并说明"历史版本不可编辑，D-72a"）。
- 待处理支付必须始终可见、可逐笔归位，且在归位前**不计入任何版本的已付**，也不得静默计入预算外支出。

**押金、退款与历史记录（P1）**

7. 押金、押金退回、退款同样是历史事实，遵循上述第 1、5、6 条，不因预算版本变化而改写。
8. 退款应尽可能追溯到原支付（D-40）；无法追溯的必须标"未关联退款"。
9. **不做完整财务系统**：不做账户余额、不做多账户对账、不做账单导入（D-85）。这里的目标只有一个——**在预算与实付之间建立可追溯的对应关系**。

**D-87a 多版本共存时，三个现金指标必须分开，且不得混为一个数（P1，v8.1 复审新增；第二轮重写；第三轮补取数规则与押金双口径）**

多版本共存时，"已付"这个问题至少对应三个**不同性质**的数。它们必须分别计算、分别标注口径：

| 展示名 | 回答的问题 | 计算式 | 性质 |
|---|---|---|---|
| **① 当前版本已付 / 当前版本待付** | "**这一版预算**付了多少、还欠多少" | `Σ(归属=当前版本预算行的流出类) − Σ(关联该版本的退款)`；`当前版本待付 = max(0, 当前版本应付 − 当前版本已付)` | **已付金额**，**不含押金** |
| **② 全程已付现金 / 全程现金总额** | "**这趟旅行**到目前为止一共现金流出多少" | `Σ(全部流出类，含预算行/预算外/待处理归属) − Σ(全部退款)` | **已付金额**；**是否含押金由 Q2 决定** |
| **③ 参考差额** | "拿已发生的支付去对照当前版本的预算，差多少" | `参考差额 = 全程现金【不含押金口径】 − 当前版本应付` | **差额，不是已付**，**恒不含押金** |

**取数规则（第三轮复审补充，与 D-80b 一致，不得偏离）**

- 公式中的"流出类""退款""押金"是 D-80b 定义的三个互斥分类。**"Σ 全部支付"在本文一律指 `Σ 流出类`**，不含退款、不含押金、不含押金退回。
- **退款只作减项，不得先加进"全部支付"再减一次**。正确：`4800 − 800 = 4000`；错误：`4800 + 800 − 800`、`4800 − 800 − 800`。
- **待处理支付仍然计入 ②**（钱确实付了，只是预算归属未定），但**不计入 ①**、不计入预算外。详见下文「待处理支付」段。

**三个必须讲清楚的点（第二轮复审新增）**

1. **② 不得重复计入预算外**。支付记录是统一集合（D-80"集合口径"），预算外支出就是其中"归属=预算外"的那些记录。写成 `Σ 全部支付 + 预算外支出` 会把预算外算两次。**唯一正确的写法是 `Σ 流出类 − Σ 退款`**。
2. **② 必须扣退款**。D-81 的已付是**净额**；全程现金口径同理，否则"付了 5000、退了 2000"会显示成 5000 而不是 3000，与 D-81 自相矛盾。两个口径的**净额性质必须一致**。
3. **③ 是差额，不是第三个"已付"**，不得与前两者并列成"三个已付"，也不得被赋予"已付"的口径名。它可能是负数：`全程已付 4800`、`当前版本应付 6000` → 参考差额 `−1200`（表示"按当前预算还差 1200 才付满"）；若 `全程已付 7000`、`当前版本应付 6000` → `+1000`（表示"已付超过当前预算 1000"）。**正负号含义必须在界面上写明**，且**不得**把它显示为"待付"——待付只由 ① 给出。

**标准场景（必须表现一致）**：V1 预算 5000、V1 已付 4800；刷新产生 V2 预算 6000、V2 尚无支付。

- ①：当前版本已付 **0**，当前版本待付 **6000**。
- ②：全程已付现金 **4800**。
- ③：参考差额 **−1200**（4800 − 6000），标注为"参考：历史支付 4800 对照当前预算 6000，尚差 1200"，**不显示为"待付 1200"**。
- **禁止**把 ① 显示成 4800（把旧版本支付伪装成当前版本付款）；**禁止**把 ③ 显示成"待付"；**禁止**把 ①②③ 合并成一个"已付"。

**待处理支付在现金汇总中的位置（P1，第三轮复审新增）**

删除一条预算行**不会**让已经花出去的钱消失，也不会让用户退回那笔钱。因此"预算归属未定"与"现金是否发生"必须分开处理：

| 指标 | 待处理支付是否计入 | 理由 |
|---|---|---|
| ① 当前版本已付 / 待付 | **不计入** | 它不属于任何一版预算行，计入会污染该版本的付款进度 |
| 预算内已付（按版本或按行） | **不计入** | 原归属行已不存在 |
| 预算外支出 | **不计入** | 它是"待处理"，不是"用户确认的预算外" |
| **② 全程已付现金** | ✅ **仍然计入** | 钱确实付了；删除预算行是计划层面的动作，不改变现金事实 |

- **必须满足的守恒**：删除一条含 3000 元支付的预算行后，`② 全程已付现金` **保持原值不变**（不是减少 3000）。
- 归位（重新归属到某行或标为预算外）后，`②` **不得再次增加**——它始终只有一次计入，只是归属从"待处理"变为"预算行/预算外"。
- 待处理支付必须在界面上**单独可见并计数**（"另有 N 笔待归位，合计 X 元"），且明确标注"已计入全程现金，未计入任何版本已付"。

**关于"只有一个预算版本时"（第二轮复审修正旧写法）**

旧写法说"当预算只有一版时，①②③ 数值相同"，这是**错的**：③ 是差额（`已付 − 应付`），只要应付不为 0，它就不可能等于已付。

正确表述：

- 只有一个预算版本、且**不存在待处理支付与预算外支出**时，`① 当前版本已付` 与 `② 全程已付现金` **数值相等**（两者统计范围重合）。
- **③ 始终独立展示为参考差额**，与 ①② 性质不同，任何情况下都**不得**并入"已付"指标、也不得因"数值刚好接近"而与它们合并。
- 若存在预算外支出或待处理支付，② > ①，**两者不得互相替代**。

**押金：两个口径必须分开，Q2 只影响其中一个（P1，第三轮复审重写）**

押金池独立于"消费"（D-39），这一点已裁决。以下两条**同时成立**，互不牵连：

| 口径 | 是否含押金 | 由谁决定 |
|---|---|---|
| **全程现金口径**（② 的展示值） | **由 Q2 决定**（A 不含 / B 含但单列） | §9 Q2，**未裁决** |
| **预算消费对照口径**（用于计算 ③ 参考差额） | **恒不含押金**（无论 Q2 怎么选） | 本文直接规定，不开放 |

- 因此 ③ 的公式必须显式写成：`参考差额 = 全程现金【不含押金口径】 − 当前版本应付`。
- **这解决了一个隐蔽缺陷**：若用户最终为 Q2 选择方案 B（② 含押金），③ 若直接用 ② 就会把押金差额混进"预算对照"，出现"押金 500 → 参考差额凭空差 500"。用"不含押金口径"计算 ③ 即可彻底避免，**与 Q2 的选择无关**。
- ① 的"当前版本已付/待付"**同样恒不含押金**（D-39 与 D-81 已排除）。
- 押金**不得**进入 ⑤ 净成本。
- Q2 裁决前，② 中的押金必须是**可开关的展示项且口径可见**，不得默认并入或默认剔除后写死。

### 4.11 冲突与提示的分级（v8 新增，解决"什么阻断、什么只提示"）

**D-90 三级，且任何一级都不阻止保存（P1）**

| 级别 | 含义 | 对金额的影响 | 具体情形 |
|---|---|---|---|
| **L1 阻断级** | 数据存在逻辑矛盾，算出来的数不可信 | 涉及条目按 **D-55** 从汇总维度排除；所属方案/组合**不参与排名**；**但整体照样保存** | 待估；计价要素不完整；数量口径未声明（D-21 第 5a 条）；同一成员同晚住两处（**该晚冲突两侧均暂不计入，待用户确认，见 D-23**）；候选被删除但方案仍引用（悬空）；套餐与房间重复占用（D-21）；**优惠超过原价（D-35）** |
| **L2 警告级** | 可能有问题，但可能是用户真实意图 | **正常计入合计**，带可见标记 | 房间容量不足；某晚有成员未安排住宿（Q16 未决期间适用，见 D-23）；报价已过期；费用日期在旅行范围之外；方案因候选改价而金额变化；已多付；住宿 0 晚（D-46）；**候选间数/数量口径与房间项不一致（D-21 第 5c~5e 条：未确认前该笔不进合计并在确认后降为 L3）**；**参与人为空（只影响人员维度，总额仍可信，D-55）** |
| **L3 提示级** | 提醒与留档 | 不影响任何计算 | 空白（未考虑）不是错误；含早/赠送等权益提示；"查询于 X 天前"；用户已显式确认的降级项（含"按间数乘算"已确认、住宿计价模式切换留痕） |

> **补充（v8.1 复审）**：「数量口径待确认」是一个**过渡态**：它是 L2 警告，但在用户确认前该笔**不进合计**；确认后转为正常计价（带 L3 留痕），或在用户放弃时保持不计价。它不能与「待估」合并计数（D-33）。

**精确口径（避免歧义）**

- L1 的"排除"只作用于**出问题的那一笔**（如待估的那一项、双占的那一晚、优惠超额的那一条），不是让整套费用消失。
- 一个条目在**各维度上的取舍必须一致**，唯一例外是"参与人为空"（只从人员维度缺席）与"日期在范围外"（只从逐日视图缺席），且两者都必须显式声明（D-55）。
- 只要方案里存在 **≥1 个 L1**，该方案**整体不参与最低价排名**（D-74），其余条目的金额照常显示与合计。
- L1 与 L2 都**不阻止保存**：用户可能正在录入中途，阻断保存等于丢数据（C3）。

**D-91 静默禁止（P1）**
任何 L1/L2 状态都必须在界面上**可见**（列表标色 + 汇总处计数），不得只在保存时弹一次就消失。

### 4.12 文件身份、保存、撤销与恢复（对应审查项 J）

**D-100 旅行身份（P1）**
一次旅行有一个稳定身份标识，从创建起不变；文件被转发、复制、改名都不改变身份。旅行文件同时带"数据版本号"与"最后写入时间"用于冲突检测。

**D-101 副本的身份规则（P1）**

| 操作 | 身份结果 | 语义 |
|---|---|---|
| 应用内「另存为副本」 | **新身份** | 视为同一起点的新旅行分支 |
| 操作系统的复制粘贴文件 | **同身份** | 同一次旅行的两份文件实例 |
| 应用内「保存」（下载副本，双击模式） | 同身份 | 同一旅行的延续 |

**D-102 多副本冲突（P1）**

- 写回文件前，必须检测"磁盘上的内容是否仍是打开时那份"（按内容比对，不只看时间）。
- 不一致 → 必须让用户在**「以磁盘为准重载」/「以我的编辑另存副本」/「取消」**之间显式选择，**禁止静默覆盖**。
- 两份文件身份相同但内容不同时，界面需显示"这是同一旅行的另一份文件"，避免用户误以为在看两份不同旅行。

**D-103 自动保存的边界（P1）**

- **编辑内容有本地草稿兜底**：编辑后短延迟写入本地草稿；切换文件、导入、关闭页面前必须强制落盘；草稿与文件内容不一致时由用户选择恢复。
- **文件写盘不自动**：写文件是显式动作（受浏览器能力限制，也为了避免静默覆盖）。
- 草稿归属必须绑定到具体旅行身份，**跨旅行不得串写**。

**D-104 保存失败（P1）**
保存失败时：编辑内容必须原样保留在内存与草稿中，给出可见错误，并提供"导出 JSON / 另存副本"两条退路。**禁止"点过了就当存好了"**。

**D-105 撤销（P1 会话内 / P2 跨会话）**

| 项 | 规则 | 级别 |
|---|---|---|
| 撤销范围 | 数据编辑：新增/修改/删除/批量修改/粘贴导入/选择变更 | P1 |
| 撤销步数 | 最近 50 步 | P1 |
| 不覆盖 | 文件保存、文件打开、导出等 I/O | P1 |
| 切换上下文 | 换文件/恢复草稿时清空撤销栈（并明确提示） | P1 |
| 跨刷新撤销 | 不做，靠草稿恢复 | P2 |

**D-106 删除与批量操作的保护（P1，底线 C3）**
删除候选、删除方案、删除费用条目、批量修改、清空日期内数据 → 必须满足至少一条：**可撤销** 或 **操作前确认并说明影响面**（影响多少条、是否被方案引用）。

**D-107 导入的边界（P1）**
"导入"只支持两种语义：

1. **打开另一个旅行文件**（替换当前上下文；当前未保存内容必须先落草稿或确认丢弃）；
2. **导入 JSON 备份**（同上，整体替换）。

**不做"把两份旅行合并成一个"**（合并语义复杂、极易静默丢数据 → Won't）。

**D-108 损坏与未知版本（P1）**

- 文件数据无法解析 → 安全模式：不写回、提供草稿扫描恢复与 JSON 导出。
- 数据版本高于当前应用 → 只读：可查看、可导出 JSON，所有写入禁用。
- 数据版本低于当前应用 → 自动迁移；迁移失败 → 只读 + 原因，原文件不被改写。

**D-109 日期范围与数据保留（P1，底线 C3）**
旅行日期范围是**当前规划视图**，不是数据删除边界：

- 缩短范围**不得删除**任何范围外数据；延长后必须原样恢复显示。
- 修改旅行开始日期**不得**导致任何已有条目被静默平移、覆盖或重新归属。
- 若某项费用的归属日期因范围变化而落到范围外，按 D-45 处理（仍计入总额，进入"范围外"入口）。

## 5. 功能需求（保留 R1～R8 结构）

> 每条只列"必须做到什么"（P1），详细规则引用 §4，验收引用 §7。

### R1 管理候选价格

**要能做什么（P1）**

1. 录入旅行中查到的各类候选：同一航班不同日期不同价、同一酒店不同房型不同价、不同交通方式、整段住宿套餐、整段交通套餐、按天报价。
2. 每条候选明确：计价单位、数量、计价周期（C8）、票档价格（D-03）、优惠项（D-34）、来源与有效期（D-60）。
3. 备注（双早、可退、不可退、含接送）与**金钱性优惠分开**：优惠必须可计算，不能只写在备注里。
4. 批量录入：多行粘贴、一键复制候选、批量修改同一字段。
5. 候选可复制到另一日期/另一区段/另一房型（价格随日期变是常态，录入必须省事）。
6. 大量候选下能快速定位（按名称/日期/类别/状态筛选与搜索）。

**不做**：不逐个打开复杂表单才能录入（录入路径必须短）；不自动抓价。

### R2 组合选择

**要能做什么（P1）**

1. 按日期、按区段、按类别自由组合（D-10～D-15、D-20～D-23、D-25）。
2. 一天多笔费用；一个区段多候选；一晚多房间多房型；套餐整段占用。
3. **住宿的两种计价模式互斥**：逐房间计价 或 整段套餐计价，二选一（D-21）。
4. 空白（未选择）、未填、待估、已定价（含 0 元）、不适用，五种状态并存且界面上可区分（C5、D-03）。
5. 所有候选同时可见、可直接比较（桌面并排；窄屏见 §7 AC-UX 的降级要求）。
6. 冲突检查按 D-90 分级，L1/L2 均可见。

### R3 费用计算

**要能做什么（P1）**

1. 多种计价方式：按人、按间夜、按天、按人天、按整段、一口价、按数量（D-31）。
2. 票档差异计价（D-03/D-04），不同服务可用不同票档与不同年龄规则文本（D-06）。
3. 附加项独立计价：儿童早餐、加床、行李、选座、接送（D-22、D-22a、D-30）。
4. 优惠、返利、免票、0 元、待估分别处理（D-32～D-35）。
5. 整数分计算，除法与分摊严格守恒（C4、D-51）。
6. **住宿按晚计价，退房日不计住宿费**（D-46）；普通跨日费用才使用"含首尾"的日期区间（D-41）。
7. **优惠超过原价时按异常处理**：保留原价与优惠、展示 0 元、标 L1、不进合计、不参与排名（D-35）。
8. **返利必须有适用范围**（单项/多项/整单），整单返利按方案重新计算（D-86）。

### R4 汇总

**要能做什么（P1）**

1. 每日花费、每类花费、总费用、人均、日均、每个人的费用。
2. **守恒按维度分别成立**（D-43、D-51a、D-55）：
   - 类别维度：`Σ 每类合计 = 总费用`；
   - 日期维度：`Σ 范围内每日合计 + 范围外费用合计 R = 总费用`；
   - 人员维度：`Σ 每人合计 = 总费用 − Z`（Z 为参与人为空但已计入的金额；Z = 0 时化简为等于总费用）。
3. 跨日期费用按明确规则分摊，原始金额不变、可追溯（D-41～D-44、D-46）。
4. **汇总处必须同时显示四个数**（D-55）：已计入 X / 因异常未计入 Y（N 条，含无金额可计者）/ 已计入但未分摊到人 Z（M 条）/ 已计入但在范围外 R（K 条）。
5. 不得为凑守恒而自动分配未分摊金额 Z（D-55 第 6 条），也不得把范围外金额 R 摊进任何一天（D-55 第 7 条）。
6. 汇总处显示"另有 N 项待估 / N 项异常 / M 项范围外"（D-33、D-45、D-91）。
7. 每人分项可追溯：来源条目、分摊方式、参与人数、我分到多少（D-52）。

### R5 方案对比

**要能做什么（P1）**

1. 保存具名方案（引用式，D-71），复制、重命名、删除。
2. 横向比较各类别金额、总价差额、贵在哪类。
3. 最低价高亮；不满足排名资格的方案不参与（D-74）。
4. 天数不同 → 同时给总价/人均/日均（D-75）。
5. 非金额属性并排展示与筛选（D-76）。
6. 候选变化时，明确提示哪些方案受影响、差多少（D-71）。
7. 选定方案 → 形成正式预算快照（D-72、D-72a）。
8. **返利口径切换**：不含返利 / 含预期返利，并且当前口径必须始终可见（D-38a）。
9. **整单返利必须按各方案重新计算**，不得把一套方案的返利金额套到另一套（D-86）。
10. **适用范围未明确的返利只展示、不参与排名**（D-86 第 10 条）。
11. **单项与多项返利同样按各方案自身条目金额重算**，基数一律为实际应付（D-86 计算基数）。

### R6 记账与复盘

**要能做什么（P1）**

1. 正式预算行是记账的唯一对照基准；一项预算行可对应多笔支付（D-80、D-87）。**支付记录是统一集合**，"预算外支出"是其归属取值之一，不得在"全部支付"之外再加一次（D-80 集合口径）。
2. 预付款、尾款、押金、退款分类处理，不重复计消费（D-39、D-40、D-81）；**退款额度按关联方式判定**：关联单笔 ≤ 该笔金额，关联预算行 ≤ 该行非押金支付之和，押金不占额度（D-40 退款上限）。
3. 临时支出/预算外支出可记录且进复盘，且不混入预算侧（D-82）。
4. 返利三态登记 + 适用范围必填 + 计算基数按实际应付（D-38、D-83、D-86）。
5. 复盘：预算差、净成本差、待收返利三差分开（D-84）；**待收返利 = 预计 + 已确认，不含已到账**。
6. **预算版本更新后**：历史支付不自动转移，保留原归属；可显式逐笔转移并留痕（D-87）。
7. **候选改价不得改变历史支付的金额与归属**（D-87 第 5 条）。
8. **刷新后新版本不再包含某预算行 ≠ 预算行被真正删除**：前者保留旧行与历史支付、不转待处理；后者（且**只能发生在当前可编辑版本**）才转"待处理支付"并提示归位（D-87 第 6 条、D-72a 第 1 条）。
9. **现金指标必须分开计算、分别标注口径**：① 当前版本已付 / ② 全程已付现金 / ③ 参考差额；其中 ③ **是差额不是已付**，不得与前两者合并（D-87a）。

### R7 输出与分享

**要能做什么（P1）**

1. HTML 文件直接分享，双击可看。
2. 导出纯文字行程单（按天：日期、住哪、怎么走、玩什么、当天花费），可直接粘贴微信。
3. 打印/PDF：去除编辑控件、分页合理。
4. 方案对比文字版。
5. 分享/打印时应可选择**是否显示金额**；默认显示，可切换隐藏（原 Q8 已裁决）。
6. **P2**：长图导出（优先级最低）。

### R8 数据安全

**要能做什么（P1）**（全部继承骨架已实现能力）

1. 单文件、完全离线、双击可用。
2. 改日期范围不丢任何数据（D-109）。
3. 本地草稿兜底、强制落盘时机、草稿箱恢复（D-103）。
4. 多副本写回前必须知情选择、不静默覆盖（D-102）。

## 附录 B：术语（日常语言）

| 说法 | 含义 |
|---|---|
| 候选报价 | 某个东西在某天（或某几天）的一个价格，例如「9/29 合肥→海口 700」 |
| 当前组合 | 此刻正在挑的这一套选择（未存档） |
| 方案 | 存下来的具名组合，引用候选，用于对比 |
| 正式预算 | 确认方案时冻结的金额快照，不随候选变化；有版本（当前版 + 至少上一版） |
| 预算行 | 正式预算里的一条冻结条目，是支付记录的唯一对照对象 |
| 已选 | 挑中的候选；只有已选的计入金额 |
| 票档 | 成人/儿童/婴儿/老人等由用户命名的价格类别 |
| 待估 | 知道要花这笔钱，但还没查到价 |
| 已定价 | 有明确金额（含 0 元、免费） |
| 未填 | 还没考虑；合法状态，不是错误 |
| 不适用 | 该票档不占这笔费用（如婴儿免票且不计座）；合法状态，不警告 |
| 区段 | 一段交通：出发地 → 目的地 + 出发日期 |
| 住宿单 | 一家酒店 + 一段入住/退房区间，可含多个房间项 |
| 房间项 | 住宿单内的一个房型及其间数、容量、入住成员 |
| 房间候选 | 挂在单个房间项上的报价（按间夜/按晚/按整段，只针对该房型） |
| 整段套餐 | 挂在住宿单上的一口价报价，覆盖全部房间项；与房间候选互斥 |
| 晚 | 住宿的计价单位：入住日到退房日之间的每一夜；退房日不计住宿费 |
| 分摊 | 把一笔费用按规则分配到若干晚/若干天或若干人；不改变原始金额 |
| 日期分摊明细 | 条目原始金额按"晚/天/段"切给各归属日的份额；只用于逐日视图求和 |
| 人员分摊明细 | 条目原始金额按承担方式切给各成员的份额；只用于人员维度求和 |
| 未分摊金额（Z） | 已计入总费用、但因参与人为空而未落到任何人头上的金额；`Σ 每人合计 = 总费用 − Z` |
| 因异常未计入（Y） | 因 L1 状态而从全部汇总维度排除、**不在总费用里**的金额；只统计**有金额可计**的异常，无金额的只计条数 |
| 范围外费用合计（R） | 已计入总费用、但归属日期在旅行日期范围外、因而不进逐日视图的金额；`Σ 范围内每日合计 + R = 总费用` |
| 应付 | 原始报价减去各种金钱优惠后的金额（预算口径） |
| 待收返利 | **预计返利 + 已确认返利**（不含已到账；按适用范围汇总，整单按方案重算） |
| 已到账返利 | 状态为"已到账"的返利合计；只用于净成本减项，**不再计入待收返利** |
| 预期净成本 | 应付 − 待收返利（"这趟预计实际会花多少"） |
| 整单返利 | 适用范围为整个方案的全部条目的返利：比例型按各方案总额重算，固定型不随总额变 |
| 返利计算基数 | 比例型返利乘的那个金额：一律为**实际应付**（已扣商家优惠与平台优惠、不扣返利本身），不含待估项与 L1 项 |
| 净成本 | 实际支付减去已到账返利（决算口径） |
| 押金池 | 已付但可退的押金合计，不计入消费 |
| 当前版本已付 | 只统计归属于当前预算版本预算行的支付（扣关联退款）；不等于"全程已付现金" |
| 全程已付现金 | 这趟旅行全部已发生支付（含预算外归属）减去全部退款后的净额；**不得在"全部支付"之外再加一次预算外支出** |
| 参考差额 | `全程已付现金 − 当前版本应付`，**是差额不是已付**，可为负；正负号含义须在界面写明，不得显示为"待付" |
| 待处理支付 | 原归属预算行被真正删除后的支付；归位前不计入任何版本的已付 |
| 补偿收入 | 超过原支付金额的赔付/理赔；只记录与单列展示，不进实际支付、不进净成本、不进预算侧（D-40） |
| 当前生效计价模式 | 住宿单此刻的计价来源：逐房间计价 或 整段套餐计价；另一种模式下的选择仅保留、不计价 |
| 报价数量口径 | 房间候选的金额是"每间价"还是"整单价"；必填，缺失即计价要素不完整 |
| 待确认数量 | 候选数量口径与房间项间数不一致、尚未得到用户确认的状态；不计入合计、不计入待估计数 |
