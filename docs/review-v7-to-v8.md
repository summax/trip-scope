# 第一部分 需求审查（R1～R8）

## 总评

v7 的**结构是对的**（只写需求、剥离实现），但**业务规则处于"待研究"状态**：v7 §10 列了 10 项"留待实现阶段讨论"的开放问题，其中第 6、7 项（"当前组合与方案存档如何共处"、"冲突与提示的分级"）属于**业务规则**而非实现细节，被误推给了实现阶段；另有 9 处业务规则（交通按日期还是按区段、住宿房型与人员分配、报价/实付/返利/净成本关系、成员票价、个人与公共费用、"跨日期费用如何进日汇总、候选变化后方案与预算的稳定性、多笔支付与退款、文件身份与撤销）在 v7 中只有一句话或完全没有落笔。v8 的任务不是加功能，而是把这些"待研究"逐条裁决成"必须如此"。

一句话结论：**v7 缺的不是功能，是口径。**

## A. 家庭成员模型

**推荐方案**：旅行级成员名册（P1），每位成员 = 称呼 + 票档 + 可选年龄/备注。价格全部挂在**票档**上，不挂在成员上。票档由用户自定义，内置成人/儿童/婴儿/老人四档默认值。**不做**逐人金额覆盖。

**推荐原因**

- 家庭人数少（2–8 人）且结构稳定，一份名册足以支撑"按人计价""按人分摊""每个人花多少"三件事。
- 票档制把"人数 × 服务数"的覆盖矩阵压缩成"票档数 × 服务数"（通常 2–3 × N），录入成本降低一个数量级。
- 个别成员特殊（老二 1.2 米免票、老人 65 岁半价）用**新建票档**表达，比逐人覆盖更清晰，也让"这套方案为什么便宜"可解释。

**优先级**：P1（成员名册 + 票档）；P2（成员级覆盖）

**是否必须在领域模型设计前确定**：**是**。成员与票档是计价的最小输入，一旦晚定，所有价格结构都要重做。

**更简单的替代方案**

- 替代 1：**不建成员名册，只填"3 成人 1 儿童"的人数计数**。
  - 优点：录入最快、无成员管理成本。
  - 缺点：无法回答"每个人花多少"（R4 明确要求）、无法表达"老二不去"、无法做人员分配与住宿冲突检查（D-23 全靠成员身份）。
  - 结论：**不可接受**，因为它直接砍掉 R4 的一个核心交付。
- 替代 2：**成员 + 每人一个价格覆盖**。
  - 缺点：录入爆炸、改价不同步。
  - 结论：降级为 P2 可选。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 只记人数计数 | 录入极快 | 无法按人分摊、无法查住宿冲突 | ❌ |
| 成员名册 + 票档（推荐） | 支撑分摊/冲突/按人汇总；录入可控 | 需维护名册（一次性成本） | ✅ P1 |
| 成员名册 + 逐人覆盖 | 表达力最强 | 覆盖矩阵爆炸；改价易不同步 | P2 |
| 票档内置行业年龄规则 | 自动判定省事 | 规则因服务而异，必然算错 | ❌ Won't |

**派生裁决**：D-01、D-02、D-03、D-04、D-05、D-06、D-07。

## B. 交通区段模型

**推荐方案**：交通以**区段**为管理单位（P1）。区段 = 出发地 → 目的地 + 出发日期（可选时刻）。一个区段挂多个候选，只有一个"已选"。整段套餐候选可覆盖多个区段。

**推荐原因**

- 用户真实心智就是"去程/返程/中间怎么走"，不是"第 3 天有交通"。按日期建模会把"去程"和"当天打车"混成一个池子，无法做"同一区段多候选比价"这一核心动作。
- 区段是**稳定的锚点**：改一次出发日期，只需改区段的日期，不需要在一堆按日记录里找。
- 有了区段，"去程/返程候选不混淆"这条验收才可判定。

**优先级**：P1

**是否必须在领域模型设计前确定**：**是**。区段 vs 日期是两种不同的数据骨架，后改代价极大（等于重做交通模块 + 迁移全部历史数据）。

**更简单的替代方案**

- 替代：**沿用"逐天交通"**，用"方向标签"区分去程/返程。
  - 优点：与现有"逐天"视图一致，实现最省。
  - 缺点：①"同一区段 3 个候选比价"要靠标签过滤模拟，脆弱；②日期一变，区段身份消失；③跨日交通（23:40 起飞）无处安放；④整段往返套餐无法表达"占用两个方向"。
  - 结论：**不推荐**，但可作为"轻量模式"：区段仅作为**分组标签**（无独立身份）时的退化形态。若用户后续觉得区段太重，可退回此形态而不改数据（区段 = 有名字的日期分组）。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 纯按日期 | 简单、与日视图一致 | 无法比价、无法表达联程/往返套餐 | ❌ |
| 区段为管理单位（推荐） | 天然支持多候选、套餐、跨日 | 需要一个"区段"概念与视图 | ✅ P1 |
| 区段 + 自动路径规划 | 更智能 | 离线无地图，违反 Won't | ❌ |
| 交通层级树（行程 → 段 → 腿） | 可表达换乘 | 过度设计，用户不维护 | ❌ |

**派生裁决**：D-10～D-16。

**特别说明（跨日交通）**：跨日到达的费用**全额归属出发日**（D-14）。这是有意的简化：20:00 起飞 / 次日 01:00 落地的航班，用户心智上"这是 9/29 的航班"，若按小时切分会产生无意义的分数金额。把单趟航班按天摊开列为 P2，且与 D-42 的"区间费用按天均摊"是两回事（后者针对 3 晚住宿、多日租车、多段套餐这类**跨多天的整笔报价**）。

## C. 住宿模型

**推荐方案**：**住宿单 + 房间项**（P1）。住宿单 = 酒店 + 连续入住区间；房间项 = 房型 + 间数 + 每间容量 + 入住成员 + 早餐 + 加床。冲突判定粒度为「成员 × 晚」。拆住（不同成员住不同酒店）**合法**。

**推荐原因**

- 住宿的真实结构是"一段连续的住宿"，不是"每晚一个决定"。用户说"住希尔顿 3 晚，1 标间 + 1 家庭房"，这是一个整体，套餐报价也是整体。
- 房间项让"同店多房型"（D4 已裁决）自然成立，也让"1 标间 + 1 家庭房"这种最常见的家庭组合可以一次表达。
- 「成员 × 晚」是唯一能同时满足"不能一人住两处"与"父母分房带孩子合法"的粒度。用「房间 × 晚」检查不够（房间不冲突但人冲突）。

**优先级**：P1（住宿单 + 房间项 + 成员分配 + 冲突检查）；P2（取消政策驱动提醒）

**是否必须在领域模型设计前确定**：**是**。房间项与成员分配的粒度决定了"住宿冲突"这个验收项能否存在。

**更简单的替代方案**

- 替代 1：**每晚一行"住宿费用"**，房型只作为备注。
  - 优点：极简。
  - 缺点：无法做"同店两房型并排比差价"（D4 已明确要求）、无法查人员冲突、套餐无法占用、间夜计价无法自动算。
  - 结论：**不可接受**。
- 替代 2：**住宿单 + 房型数量，不做成员分配**。
  - 优点：少一层数据。
  - 缺点：砍掉"同一家庭成员同一晚不能被安排到两家酒店"这条验收；但保留"容量不足"检查（用总人数 vs 总床位）。
  - 结论：**可作为降级方案**。如果用户认为"人员分配"太重，v8 的 D-23 可退化为"总人数 vs 总床位数"的容量检查，牺牲"分住合法性"的精确判定。**列为待确认（Q10，见文末）**。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 每晚一行 | 极简 | 丢房型/容量/套餐/冲突 | ❌ |
| 住宿单 + 房间项 + 成员分配（推荐） | 完整表达真实场景 | 录入稍重 | ✅ P1 |
| 住宿单 + 房型数（无成员分配） | 轻 | 无法判"一人住两处" | 降级可选 |
| 按房间独立记录（每间一个条目） | 简单 | 连住一致性丢失、套餐无处安放 | ❌ |

**派生裁决**：D-20～D-24。

## D. 费用与金额口径

**推荐方案**：**五层口径**（原始报价 / 实际应付 / 实际支付 / 已到账返利 / 最终净成本），优惠四分类（商家/平台/返利/非现金权益），全部整数分计算，应付不为负。

**推荐原因**

- 用户真实会问的三个问题，对应三个口径："这套方案要花多少"（应付）、"我现在付了多少、还欠多少"（支付）、"这趟到底花了多少"（净成本）。把三者合并成一个数，必然在某个场景算错。
- 返利三态（预计/确认/到账）是真实的资金时序，合并会高估省钱。
- 非现金权益（赠早、赠票）折算成钱会导致"净成本比实际支出还低"的荒谬结果。

**优先级**：P1

**是否必须在领域模型设计前确定**：**是**。口径决定"哪些数被存、哪些数被算"，是模型的地基。

**更简单的替代方案**

- 替代：**只存"实付"一个数**，优惠与返利只写备注。
  - 缺点：直接违反 C9 与 R1 的"金钱性优惠必须参与计算"，且"省了多少"无法回答。
  - 结论：**不可接受**（这是 v6 及以前版本的主要缺陷）。
- 替代：**存"原始价 + 一个折扣率"**。
  - 缺点：无法表达"平台券 100 + 返利 200"这种组合，也无法区分返利到账与否。
  - 结论：**不可接受**。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 单一金额 | 极简 | 算不准、无法复盘 | ❌ |
| 原始价 + 折扣率 | 稍好 | 表达不了多类优惠与返利时序 | ❌ |
| 五层口径 + 四类优惠（推荐） | 算得准、可追溯 | 录入字段多，但多数可留空 | ✅ P1 |
| 五层 + 逐条优惠明细表 | 最细 | 录入成本高 | 过度 |

**派生裁决**：D-31～D-40、C8、C9、C10。

**关键提醒**：五层口径**不是五份数据**。②③⑤都是可算出的派生值，只有①（含优惠项）和支付流水是原始录入。实现时若把五个都存成独立字段，会出现"改了①忘了更新②"的不一致 —— 这是领域模型阶段必须用"单一真相 + 派生"来防的（见第五部分不变量 I-04）。

## E. 公共费用与个人费用分摊

**推荐方案**：每个费用条目声明**承担方式**（全员均摊 / 指定成员 / 部分成员均摊 / 按权重[P2]）+ **参与人列表**。分摊用最大余数法，严格守恒，结果可追溯到"哪笔钱、按什么规则、我分到多少"。

**推荐原因**

- 家庭出游 95% 的分摊只需"均摊"和"某人自己花"两种；"部分成员均摊"覆盖"只有 3 人去的景点"。三者已足够。
- 守恒不是"差不多对"，而是可验证的硬约束（C4）。最大余数法是唯一能同时保证"整数分 + 总和相等 + 结果确定"的简单方法。
- "可追溯"决定了用户是否信任这个工具：看到"我要付 3200"却说不出为什么，用户就会回去用 Excel。

**优先级**：P1（前三种承担方式）；P2（按权重）

**是否必须在领域模型设计前确定**：**是**。承担方式决定费用条目是否必须持有"参与人"这一关系。

**更简单的替代方案**

- 替代：**只做全员均摊**，个人支出单独记。
  - 缺点：无法表达"只有妈妈和孩子去的门票"，也无法表达"爸爸的单独机票"。
  - 结论：**不足以覆盖验收 AC-SEL-09**（分住）与 AC-SUM-04。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 只均摊 | 极简 | 表达力不足 | ❌ |
| 均摊 + 指定人 + 部分人均摊（推荐） | 覆盖真实场景 | 需参与人列表 | ✅ P1 |
| + 按权重 | 更灵活 | 权重录入繁琐、易错 | P2 |

**派生裁决**：D-50～D-54。

## F. 跨日期费用分摊

**推荐方案**：每笔费用必须有**归属日期**（单日或区间），区间默认**按天均摊**，可切换为"全额计入起始日"或"按晚/按段均摊"。分摊只产生**统计明细**，原始金额不变；总额由原始金额求和，逐日/逐人由分摊明细求和，两条路径**不叠加**。

**推荐原因**

- "3 晚 3000"在用户眼里是一笔钱，在日视图里必须是每晚 1000，否则"哪天最贵"没法看。
- 若把分摊结果当成新费用存进去，总额会翻倍 —— 这是本项目最容易犯的致命错误，必须在需求层写死"分摊是视图，不是新数据"。
- 两种方式已覆盖真实场景：**全额计入起始日**（机票、一口价）与**按天均摊**（住宿按晚、多日租车、交通套餐按段）。"按权重"（每晚不同价）是真实需求但不是高频，列 P2。

**优先级**：P1（两种方式）；P2（按权重）

**是否必须在领域模型设计前确定**：**是**，但它只影响"派生计算"，不影响原始存储 → 风险可控，可以先定语义、后定算法。

**更简单的替代方案**

- 替代：**不做分摊，日视图只显示"当天开始的费用"**。
  - 缺点：3 晚套餐只在入住日显示 3000，日小计严重失真，"哪天最贵"失去意义。
  - 结论：**不可接受**（R4 明确要求逐日小计）。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 不分摊 | 极简 | 日视图失真 | ❌ |
| 分摊但不守恒（各自四舍五入） | 简单 | 日合计 ≠ 总额，违反 C4 | ❌ |
| 两种方式 + 最大余数法（推荐） | 准确、可解释 | 需固定余数次序 | ✅ P1 |

**派生裁决**：D-41～D-45、C4。

## G. 方案、候选报价与正式预算

**推荐方案**：**三级关系**——候选（事实、可编辑）→ 方案（引用、实时反映、变更提示）→ 正式预算（快照、冻结、变更提示 + 显式刷新）。

**推荐原因**

- 这三个对象回答三个不同的问题："我查到什么价"、"如果我这么选要花多少"、"我当时决定花多少"。混成两个或一个，都必然在某个场景出错。
- 方案引用候选符合"改一次价，所有比较同步更新"的直觉；正式预算快照符合"我已经定了，别偷偷改"的直觉。两者不矛盾，因为用户对它们的期望本来就不同。
- "提示差额"是关键的折中：既不改预算，也不让用户看不见变化。

**优先级**：P1

**是否必须在领域模型设计前确定**：**是，最高优先级**。这是全项目最容易造成"数据静默变化"的地方，也是 C11 的落点。

**更简单的替代方案**

- 替代 1：**只有方案，没有正式预算**（方案就是预算）。
  - 缺点：改候选价 → 已确认的预算静默变化，直接违反 C11。
  - 结论：**不可接受**。
- 替代 2：**方案也快照**（保存即冻结）。
  - 缺点：改价后所有方案不同步，用户要手工重存 N 套；"候选库"失去意义。
  - 结论：**不推荐**，但可作为极端简化：只保留一个"当前组合"（引用）+ 一个"正式预算"（快照），砍掉"多方案"。
  - 这条替代会牺牲 R5 的核心价值（横向比较多套），**不建议**。
- 替代 3：**方案引用 + 方案级手动改价**（不碰候选，只在本方案内覆盖某条价格）。
  - 优点：可做"如果涨 200 会怎样"的推演。
  - 缺点：多一层覆盖，容易与候选变化纠缠。
  - 结论：**P2**。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 只保留正式预算 | 最简单 | 无法比较、改价即改预算 | ❌ |
| 方案=快照 | 稳定 | 不同步、需重存 | ❌ |
| 候选引用 + 方案引用 + 预算快照（推荐） | 直觉正确、可追溯 | 需三处 UI 明确口径 | ✅ P1 |
| + 方案级价格覆盖 | 可推演 | 复杂度上升 | P2 |

**派生裁决**：D-70～D-77、C11。

**附：排名资格规则的必要性**
"含待估项不参与最低价排名"是**防止漏填反而赢**的唯一手段。如果不做，用户会本能地少填一项来"做出"最便宜的方案 —— 这是所有报价工具的通病。同理，"空方案不参与排名"防止"什么都不选 = 0 元 = 最便宜"。

## H. 实际支付与旅行记账

> **2026-11-09 第二轮复审同步**：本节原推荐方案写的是"支付记录是一等对象，**挂在费用条目上**"，与需求正文 D-80/D-87 的最终结论**不一致**。费用条目是活的（随方案与候选变化），把它作为支付的归属锚点，预算刷新后支付就失去了对照基准。正文已裁决为**挂正式预算行**，本节据此改写；原结论仅作历史记录保留在下方"原结论与修正原因"中。

**推荐方案（现行）**：**支付记录是一等对象，但归属对象是「正式预算行」或「预算外支出」**——二者必居其一，且**支付记录构成一个统一集合**，"归属"只是它的一个取值。

- 类型六种：预付款 / 尾款 / 全款 / 押金 / 押金退回 / 退款（另有"其他"）。
- 押金独立成池，不计入消费（D-39）。
- 退款必须关联到原支付或原预算行；无法关联需显式登记为"未关联退款"，且设**累计退款上限**（D-40）。
- 临时支出（预算外）可无预算行，但必须单独归类、单列展示，**不是"支付之外的另一笔钱"**。
- **预算版本刷新不自动转移支付**；旧版本整体冻结（含其预算行不可删除）；历史支付继续追溯到原版本行（D-72a、D-87）。
- 多版本共存时三个现金指标分开：当前版本已付 / 全程现金总额 / 参考差额（D-87a）。

**原结论与修正原因（保留以便追溯）**

原文写"挂在费用条目上"，其理由（"一项预算 → 多笔支付是常态""押金不是花掉的钱""退款必须关联"）**全部仍然成立**，只是归属锚点选错了层：这三条讲的是"支付要能反查计划"，而"费用条目"会随候选改价、方案切换而变化，无法承担"历史事实的稳定锚点"这一职责。改用预算行后，三条理由都不受影响，且额外获得"预算 vs 实际可逐行对比""版本可追溯"两个能力。

**推荐原因**

- "一项预算 → 多笔支付"是真实世界的常态（定金 + 尾款 + 到店补差），不支持就无法记录真实付款进度。
- 押金是"可退的钱"，不是"花掉的钱"。不做区分，用户会在退押金时看到"净成本为负"或"重复计入"。
- 退款若不能关联，用户只能手动改金额，历史就丢了（违反 C3）。
- 归属必须锚在**冻结的快照**（预算行）上，否则"候选改价"会连带改写历史支付的语义（C11 在记账侧的延伸）。

**优先级**：P1

**是否必须在领域模型设计前确定**：**是**（支付归属锚点、支付与预算行的一对多、押金是否独立，都是模型结构问题）。

**更简单的替代方案**

- 替代 1：**每笔实际支出独立记一行，不与预算关联**。
  - 优点：极简，几乎零模型成本。
  - 缺点：无法回答"这项预算还欠多少"（R6 核心）、无法做预算 vs 实际对比（R6 核心）。
  - 结论：**不可接受**，但可作为"预算外支出"这一子集的实现方式（D-82）。
- 替代 2：**支付挂在费用条目上**（本节原方案）。
  - 优点：记账时"离要付的东西最近"，录入直观。
  - 缺点：费用条目随候选与方案变化，预算刷新后支付失去对照基准；同一笔历史支出的语义会随候选改价漂移。
  - 结论：**不可接受**（这是 v8 的原始写法，v8.1 起废弃）。

**备选与利弊**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| 独立支出流水 | 极简 | 无预算对比、无待付 | ❌ |
| 支付挂**费用条目** | 录入直观 | 锚点会漂移，刷新后失去基准 | ❌（v8 原写法，已废弃） |
| 支付挂**预算行**或标预算外 + 类型 + 押金池（现行） | 锚点稳定、可追溯、可版本对比 | 需处理"多付/未关联/待处理" | ✅ P1 |
| + 多币种/多账户 | 更通用 | 已 Won't | ❌ |

**派生裁决**：D-39、D-40、D-80～D-82、D-84、D-85、D-87、D-87a；不变量 I-05～I-07、I-20、I-20a、I-20b；约束 BC-10、BC-11、BC-12、BC-20、BC-21、BC-24。

## I. 报价来源与有效性

**推荐方案**：记录**平台（文本）+ 查询日期 + 适用日期 + 有效期（可选）+ 链接（纯文本）+ 备注**。判定只有两条：填了有效期且已过 → "已过期"；只有查询日期 → "查询于 N 天前"。**不做阈值推断、不联网**。

**推荐原因**

- 用户的真实痛点是"这个价我什么时候查的、还有效吗"，不是"系统帮我判断哪个平台便宜"。
- 任何"超过 N 天就提示可能过期"的规则都是武断的：机票 3 天就变，酒店套餐 30 天不变。用一个阈值必然制造噪音，用户会学会忽略所有提示。
- 链接只作为留档文本，双击可选中复制 —— 不打开、不校验、不请求。

**额外发现（v8 新增 D-63）**：查价时最容易犯的错不是"忘了看有效期"，而是**把错日期的价填进了候选**（9/30 的价填到 9/29）。这类错误**不会报错，只会让方案看起来便宜、实际订不到**，属于典型的静默错误。因此"适用日期 vs 实际占用日期"必须做校验：住宿缺一晚是 L1，交通日期错位是 L2，允许用户显式确认后降级。

**优先级**：P1（除有效期阈值提醒为 P2）

**是否必须在领域模型设计前确定**：**否**（是候选上的附属属性，加字段代价低）。**但"适用日期"必须现在定**，因为它与区段/住宿单的归属日期关系密切。

**更简单的替代方案**

- 替代：**只记"备注"一个自由文本**。
  - 缺点："哪些报价要重新查"这个问题完全无法回答。
  - 结论：**不可接受**（R1 明确要求报价来源与查询时间）。

**派生裁决**：D-60～D-63。

## J. 文件身份与恢复

**推荐方案**

| 议题 | 推荐 | 级别 |
|---|---|---|
| 文件唯一身份 | 旅行 UUID，创建即定，永不改 | P1 |
| 应用内"另存为副本" | 新 UUID（视为新旅行分支） | P1 |
| 系统复制文件 | 同 UUID（同旅行的两份实例） | P1 |
| 双击模式"保存"（下载副本） | 同 UUID（延续） | P1 |
| 多副本冲突 | 写回前内容签名比对，三选一，绝不静默覆盖 | P1（骨架已实现） |
| 自动保存 | **草稿自动（短延迟 + 强制落盘点），文件不自动** | P1 |
| 草稿恢复 | 内容不一致才提示，时间只作展示 | P1（骨架已实现） |
| 撤销 | 会话内 50 步，不覆盖 I/O，切上下文清栈 | P1 |
| 跨会话撤销 | 不做 | P2 |
| 保存失败 | 保留内存与草稿 + 可见错误 + 导出/另存退路 | P1（骨架已实现） |
| 文件损坏 | 安全模式 + 草稿扫描 + JSON 导出，不写回 | P1（骨架已实现） |
| 导入 | 只支持"整体替换"（打开旅行 / 导入备份） | P1 |
| 合并两份旅行 | **不做** | Won't |

**推荐原因**

- "身份"解决的是"这两份文件是不是同一趟旅行"。应用内另存 = 用户主动分叉（新身份），系统复制 = 同一文件的两份拷贝（同身份，冲突检测靠内容签名）。这条规则让两种复制方式都有确定语义。
- 内存中的合并极易静默丢数据，"不做合并"是保护而非限制。
- 撤销不覆盖 I/O，是因为"撤销一次保存"在单文件模型里没有安全含义（磁盘上已经是新内容了）。

**优先级**：P1（合并除外）

**是否必须在领域模型设计前确定**：**是**（身份与撤销栈语义会影响存储与状态结构）；**"不做合并"必须现在定**，因为它决定了导入功能只能做替换。

**更简单的替代方案**

- 替代：**不做文件身份，靠文件名区分**。
  - 缺点：用户改名即失去关联；无法回答"这是副本还是另一趟旅行"；冲突检测只能靠时间戳（会误报）。
  - 结论：**不可接受**（骨架已实现 UUID，回退是倒退）。

**派生裁决**：D-100～D-109。

## 2.11 v8.1 六项 P1 修订的裁决理由

> 这六项在 v8 中都是"看起来写了、实际有歧义"的规则。下面是每一项的**歧义定位 → 备选 → 最终裁决 → 为什么不做更复杂的方案**。
>
> **2026-11-09 复审**：P1-03（守恒）、P1-05（返利）、P1-06（支付与版本）三项在原裁决之上又各收窄了一步——原裁决解决了"该不该拆"，复审解决了"拆完之后每一条等式写成什么"。三处补正分别在各小节末尾的"复审补正"段。

### P1-01 住宿候选报价与房间项

**歧义定位**：v8 只说"住宿单可挂多个候选"，但没说候选挂在哪一层。当住宿单有多个房间项时，"候选"到底描述整张单还是单个房间？这直接决定"两个房型能不能各选各的"。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| A. 候选只挂住宿单（整单一价） | 简单，一单一个价 | 无法同店不同房型分别比价（D4 已明确要求）；家庭最常见的"1 标间 + 1 家庭房"无法表达 | ❌ 与既有裁决冲突 |
| B. 候选挂房间项，套餐另算 | 房型独立比价；套餐仍可整段 | 需要两层候选概念 | ✅ 采纳 |
| C. 候选挂房间项，取消套餐 | 更简单 | 丢掉"3 晚连住 3000"这类真实报价形态 | ❌ 砍掉真实需求 |
| D. 引入"优先级/覆盖关系"的通用机制 | 表达力最强 | 通用覆盖规则难以让用户理解，且易产生隐蔽的双计费 | ❌ 过度设计 |

**最终裁决（B）**：房间候选挂房间项，整段套餐挂住宿单；两者**互斥**而非叠加。

**为什么不用 D**：本任务明确要求"不为消除歧义而选择未经讨论的复杂业务方案"。通用覆盖机制会让"到底算了哪些钱"变成一个需要推理的问题，而 TripScope 的核心价值恰恰是"任何汇总都能追溯到原始费用"（原则 7）。

**最关键的取舍**：互斥而非"取较小值"。取较小值听起来友好，但会让用户无法判断"我到底选了哪个"，也无法解释"为什么总价不是我以为的那两个数之和"。互斥 + 显式切换更笨，但更可信。

### P1-02 住宿日期与按晚分摊

**歧义定位**：D-41 说"日期区间含首尾"，D-42 又说"住宿按晚、住宿一晚 = 一天"。这两句在 9/29 入住、10/2 退房时会得出不同结论：含首尾 = 4 天，按晚 = 3 晚。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| A. 统一含首尾，住宿也按 4 天摊 | 规则单一 | 退房日被算一天房费，与任何酒店报价都不符 | ❌ 直接算错 |
| B. 住宿用半开区间按晚，普通费用含首尾 | 各自符合真实语义 | 需要两套日期语义，用户要理解差异 | ✅ 采纳 |
| C. 全部改半开区间 | 统一 | 租车/通票按"含首尾"计费是真实情况，改了会少算一天 | ❌ 另一头算错 |

**最终裁决（B）**：住宿 `[入住, 退房)`，普通跨日费用 `[起, 止]`。并在 D-46 用表格把"退房日 = 0"写成硬规则，避免实现时"顺手按天均摊"。

**为什么值得引入两套语义**：因为现实就是两套。租车 9/29 取车、10/2 还车，通常计 4 天；酒店 9/29 入住、10/2 退房，就是 3 晚。把两者强行统一，必然有一方算错，而算错的钱不会自己暴露。

**额外收益**：这条同时解释了为什么"7 晚分 3000"要按晚而不是按天——分母变了，余数分配也变了。

### P1-03 四向守恒与参与人为空

**歧义定位**：v8 一边要求"Σ每人 = 总费用"，一边允许"参与人清空"。这两条在实现层必然冲突，只能三选一：①禁止清空参与人；②清空时偷偷分摊；③承认按人合计可以不等于总额。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| ① 禁止清空参与人 | 守恒无条件成立 | 用户正在录入中途会被阻断；且"这笔钱先记下来、回头再分"是真实需求 | ❌ 违反 C3 精神 |
| ② 清空时自动分摊给全员 | 守恒永远成立，界面永远"对" | **系统编造了一个用户没做的决定**，且用户看不出来 | ❌ 最危险 |
| ③ 承认有未分摊金额 Z，显式展示 | 诚实、可追溯 | 需要一个新概念与展示位 | ✅ 采纳 |

**最终裁决（③）**：引入 Z（未分摊金额），人员维度改为 `Σ 每人合计 = 总费用 − Z`，并明令禁止自动分摊。**2026-11-09 复审进一步收窄**：把"有条件成立"改成"**无条件成立 + Z 补平**"，并把单一的分摊不变量拆成"日期分摊守恒 / 人员分摊守恒"两条（D-51a、I-03、FC-19）——因为"分摊明细之和 = 应付金额"在参与人为空与 L1 排除两种情形下都必然不成立，留着它只会让实现者二选一地违反其中一条。

**为什么 ② 是最坏的**：它让汇总永远"看起来对"。用户看到 `Σ每人 = 总费用`，会以为分摊已完成；实际上系统替他做了一个他没同意的决定。一旦他事后发现，整个工具的可信度就没了。而 ③ 虽然会显示"差 320 元未分摊"，但那是一个**用户能理解和修复**的状态。

**同时解决的问题**：任务书第 7 条要求"L1 条目不能在某维度被排除、却在另一维度被静默计入"。这条被写成 D-55 的第 1 条原则（按条目整体排除），并给出逐状态表，把"参与人为空"和"日期范围外"这两种唯一的例外显式列出——**例外可以存在，但必须被写下来**。

**一处级联修正（v8.1 定稿前发现）**：初稿把"参与人为空"归入 L1，与 D-74"参与人为空的方案仍可参与排名"直接矛盾。二选一：把 L1 的含义改成"不参与排名"以外的意思，或把参与人为空降到 L2。**选后者**——L1 的定义是"算出来的数不可信"，而参与人为空时**总额完全可信**（钱确实要花，只是分不到人），不可信的只是人员维度。因此参与人为空是 **L2 警告 + 人员维度缺席 + Z 显式展示**，不改总额、不影响排名。这条修正同时让 D-74 的表格与 D-90 的分级表保持一致。

### P1-04 优惠超过原价

**歧义定位**：D-35 说"应付按 0 计"，D-90 说"L1 不计入合计"。若照 D-35 实现，这个 0 会进入合计，等于把一条**错误数据**当成"免费项目"计入总额；若照 D-90 实现，又与"按 0 计"的措辞矛盾。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| A. 按 0 计入合计 | 简单，总额不为负 | 把错误当免费；用户无法发现；且"明确 0 元"与"异常 0 元"混淆，C5 失守 | ❌ |
| B. 截断优惠到原价 | 数据看起来干净 | 静默丢弃用户输入（C3）；用户永远不知道优惠填多了 | ❌ |
| C. 保留原价与优惠，展示 0，但不计入合计，标 L1 | 诚实、可发现、可自愈 | 需要区分"展示 0"与"计入 0" | ✅ 采纳 |

**最终裁决（C）**：保留全部输入，展示 0 元但**从各维度排除**，标 L1，并强制附文案"0 元不代表已确认免费"，修正后自动解除。

**为什么必须区分"展示 0"与"计入 0"**：这是本项的核心。在界面上，用户需要一个"不会看到负数"的展示值；在计算上，这一笔必须**缺席**。把两者混为一谈，就是 v8 那句话的歧义来源。

### P1-05 返利范围与方案比较

**歧义定位**：v8 允许"整单返利"，但没定义它在方案对比中怎么算。若把返利存成一个固定金额挂在"方案"上，那么方案 A（20000）的返利 200 被套到方案 B（20200）上，就少算了 2 元；反之若每个方案重算，又必须区分"比例型"与"固定型"。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| A. 返利只允许挂单项 | 最精确 | 无法表达"信用卡整单返 1%"这类真实返利 | ❌ 砍掉真实需求 |
| B. 返利只有固定金额 | 简单 | 比例型返利无法表达；用户得自己算 | ❌ |
| C. 返利有适用范围（单项/多项/整单）+ 形态（比例/固定） | 覆盖真实场景，方案间可正确重算 | 多两个属性 | ✅ 采纳 |
| D. 通用"优惠规则引擎" | 最强 | 过度设计，且会让"这笔钱怎么算的"变成黑箱 | ❌ |

**最终裁决（C）**：适用范围必填且唯一；比例型按方案重算，固定型不随总额变；一笔返利只能有一个范围；范围未明只展示不排名。

**为什么"唯一"很关键**：如果允许一笔返利同时标"单项"和"整单"，用户很容易在两次登记里把同一笔返利算两遍，而方案对比会因此给出错误的"最划算"。要求"想两种效果就登记两笔"，把重复计算变成**可见的两次录入**，而不是隐藏的双重生效。

**2026-11-09 复审补正（返利的计算基数）**：原裁决只回答了"范围怎么划"，没回答"乘在哪个数上"。三种范围里只有整单返利写了基数（"已定价且无 L1 的条目应付之和"），单项与多项完全没写。这不是措辞遗漏，而是会直接改变结果的缺口——原价 1000、优惠共 200、返利 1%，按 1000 得 10 元、按 800 得 8 元，**差 25%**，而两种算法都能在原文里找到依据。

**最终口径（D-86 计算基数、BC-19a、I-19b、AC-CAL-17～23）**：
- 三种范围共用同一句：基数 = **实际应付（口径②）** = 原始报价 − 商家优惠 − 平台优惠，**不扣返利本身**。单项取该条目、多项取被勾选条目的和、整单取方案内符合条件条目的和。
- 基数**不含**待估项与 L1 项（没查到价、或数据本身不可信，都不该"已经产生返利"）。
- **明确 0 元条目进基数但贡献 0**（写死，避免实现者就"0 元算不算参与"各写一版）。
- 固定型与基数无关；同一笔返利记录不得把同一条目算两次；同一条目被两笔不同返利覆盖是合法且常见的。
- **不采用**"按原始报价算"或"按含返利的净额算"——前者让用户为优惠掉的部分拿返利，后者是循环定义。

### P1-06 支付与正式预算版本

**歧义定位**：v8 说支付可挂"费用条目、正式预算行或临时支出"。但"费用条目"是活的（随方案变化），"预算行"是死的（快照）。同一笔支付挂在活的条目上，刷新预算后就失去了对照基准。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| A. 支付挂费用条目 | 记账时直观 | 预算刷新后归属失效；候选改价可能"带动"支付语义 | ❌ |
| B. 支付挂方案 | 简单 | 方案是引用式的、会变；支付是事实、不变，两者性质冲突 | ❌ |
| C. 支付只挂预算行（或预算外） | 锚点稳定、可追溯、版本可对比 | 需要"预算行"这一实体与版本概念 | ✅ 采纳 |

**最终裁决（C）**，并补三条：**不自动转移**、**可显式逐笔转移并留痕**、**预算行删除时支付不得删除**。

**2026-11-09 复审补正（关键）**：上面这三条在 v8.1 里只写了"预算行删除时支付不得删除，转为待处理"，却没有区分"**刷新后新版本不再包含该行**"与"**该行被真正删除**"。前者若也转待处理，就直接推翻了同一条的第 1 条（不自动转移）——用户的每一次刷新都会把历史支付的归属拔掉。**最终语义**（D-87 第 6 条情况 A/B、BC-21、I-20a）：
- 情况 A（新版本不含该行）：旧行保留、支付归属不变、**不转待处理**、需显式转移才会对应新预算。
- 情况 B（该行被真正删除）：支付不删、转待处理、逐笔显式归位、保留金额/日期/类型/来源。
另补 D-72a 第 4 条：旧版本被清理时允许保留**最小历史归属快照**（只用于追溯显示，不参与计算），否则"长期追溯"与"至少保留两版"两条仍会打架。

**为什么"不自动转移"是对的**：预算刷新意味着"计划变了"，但已经花出去的钱没有变。如果系统自动把旧支付挪到新预算行，复盘时就会出现"我明明付了 4800，怎么显示成付了 5000"这类无法解释的现象。宁可让用户看到"这笔钱还挂在旧版本上"，也不要替他重新叙述历史。

**为什么不做完整财务**：本项只回答"这笔钱属于计划里的哪一行、还欠多少"。账户、余额、对账、账单导入都已在 Won't 里（D-85）。

## FC-1 日期范围 vs 历史数据保留 —— **存在真实冲突，已消解**

**冲突描述**：R8 要求"缩短日期不丢数据"，若汇总只统计范围内数据，则缩短日期会**改变总额**，用户会认为"数据被删了"（虽然数据还在）。反之若全部计入，逐日视图（6 天）与总额（含 10 天数据）对不上，破坏日期维度的守恒等式。

**消解（D-45、D-109）**
- 数据层面：日期范围**永不删除**任何数据。
- 汇总层面：**总费用始终包含全部费用**（含范围外）。
- 视图层面：逐日视图只显示范围内日期；范围外费用进入"范围外 N 项 / 合计 R"的显式入口。
- 守恒层面（v8.1 复审修订）：**类别维度** `Σ 每类合计 = 总费用`；**日期维度** `Σ 范围内每日合计 + 范围外费用合计 R = 总费用`；**人员维度** `Σ 每人合计 = 总费用 − Z`。三条同时成立，`R` 与 `Z` 都必须显式展示。

**为什么必须引入 R（v8.1 复审记录的真实矛盾）**：旧写法把"Σ 每日 = 总费用"当成无条件等式，与"范围外费用计入总额但不进逐日视图"在数学上不可能共存。旅行 9/29–10/2、范围内 3000、范围外 500 时：逐日之和 3000、总额 3500、类别合计 3500。三条旧规则的任何两条都能满足，三条同时满足不可能。修法只有两种——把 500 偷偷摊到某一天（违反 D-45 的数据保留原则与用户直觉），或承认日期维度需要一个"范围外合计"来补平。**选后者**。

**遗留风险**：已消解。日均费用的分母由 **Q5 裁决为"旅行自然日含首尾"**，D-75 已给出完整公式，并要求在存在范围外费用时标注分子构成（"总价 X（含范围外 R）÷ 自然日 D 天"）。此处不再是待裁决项。

## FC-2 候选报价 vs 正式预算快照 —— **表观冲突，实为两级对象**

**冲突描述**：若正式预算引用候选，改价会改预算（违反 C11）；若正式预算深拷贝后彻底断开，用户又看不到"现在订要多少钱"。

**消解（D-70～D-72）**
- 正式预算 = 快照，**金额冻结**。
- 同时保留"现价对比"这一**只读派生视图**：显示"当前候选现价合计 vs 预算合计，差 +X"。
- 用户可显式「按现价刷新预算」→ 新版本，旧版本保留。
- 关键：**对比是视图，刷新是显式动作**。这样既不静默改，也不失明。

## FC-3 原始金额 vs 每日分摊 —— **最危险的重复统计点**

**冲突描述**：如果"分摊明细"被当成新的费用条目存进去，则总额 = 原始 3000 + 分摊 3000 = 6000。

**消解（D-43、D-51a）**
- 明确：**分摊是派生的统计明细，不是费用条目**。
- 总额只由"原始金额（应付口径）"求和。
- 逐日/逐人合计由"分摊明细"求和。
- 两条路径在**各自维度上分别相等**（v8.1 复审修正：`Σ 范围内每日 + R = 总费用`、`Σ 每人 + Z = 总费用`，**不是**"两条都等于总额"），但**不得相加**。
- 验收：AC-SUM-03、AC-SUM-06、AC-SUM-07 分别守"不重复计""日期维度补 R""人员维度补 Z"这三点。

**实现提醒（不写进需求，但必须警示）**：这条不变量（I-02、I-02a）必须在领域模型阶段用"单一真相 + 派生"保证，不能靠开发者自觉。

## FC-4 返利、退款、预付款的重复扣减 —— **存在，已消解**

**冲突描述**：三种资金流都可能"让金额变少"，若都当成减项，会重复扣。
- 预付款是**消费的一部分**（后面付尾款），不是减项。
- 退款是**支付的冲减**（减"已付"），不是新的负费用。
- 返利是**净成本的减项**（只在"已到账"时），不是"已付"的减项。

**消解（D-37、D-38、D-39、D-40）**
- 三个口径分开：预算口径 / 现金口径 / 决算口径，各自有各自的减项，互不串用。
- 恒等式（v8.1 复审校订）：
  - `已付 + 待付 = 应付`（仅当 已付 ≤ 应付 时成立；押金在等式外）
  - `已付` 的计算见 I-06（引用 D-80b 口径 A，含已转为消费的押金）；且 `Σ退款 ≤ Σ支付`（D-40 退款上限）
  - `净成本` 见 I-07（被减数为消费实际支付，公式定义处为 D-80b）
  - `待收返利 = 预计返利 + 已确认返利`（**不减去已到账**，v8.1 复审修正）
  - `预期净成本 = 应付 − 待收返利`
  - `预算差 = 应付 − 已付`、`净成本差 = 应付 − 净成本`（两差必须分开显示）
- 验收：AC-LED-02、AC-LED-03、AC-LED-05、AC-LED-06、AC-LED-07、AC-LED-07a、AC-LED-20、AC-LED-21 分别守以上各条。

## FC-5 住宿房型组合 vs 成员分配 —— **存在边界冲突，已裁决**

**冲突描述**：同一晚两家酒店 + 成员分住，从"住宿冲突"角度看是合法的；从"同一人不能住两处"角度看又必须检查。若检查粒度选错（按房或不检查），两种场景之一必然出错。

**消解（D-23）**：粒度定为「成员 × 晚」。分住合法，一人两处冲突，容量不足警告，有人未安排警告。

**边界情形（需明示）**
| 场景 | 判定 |
|---|---|
| 同一人同晚两处 | L1 冲突 |
| 不同人同晚两处 | 合法 |
| 房间容量不足 | L2 警告 |
| 有人未安排房间 | L2 警告 |
| 某晚完全空白 | 合法，不警告 |
| 某人当晚不需要住宿（如红眼航班） | 需能标记"当晚不参与住宿" → 见 **Q16**（仍未裁决） |

## FC-6 交通区段 vs 每日汇总 —— **存在，已消解**

**冲突描述**：区段以"出发地 → 目的地"为身份，日汇总以"日期"为轴。跨日航班、联程套餐会让"一个区段跨两天"或"一个候选跨两个区段"。

**消解（D-14、D-15、D-41）**
- 区段有明确的出发日期 → 有天然的日归属。
- 跨日到达：费用全额归属出发日，到达日只作信息展示。
- 套餐跨区段：金额按段均摊（若选），或全额归属首段；原始报价仍是一条。
- 日汇总从"费用条目的归属日期/分摊明细"取数，不从"区段"取数 —— 区段只是费用条目的来源，不直接进入汇总。

## FC-7 未定价 / 零元 / 未选择 —— **存在，已用"状态矩阵"消解**

**冲突描述**：v7 只有三态（空白/未定价/免费），实际还需要"不适用"（婴儿免票且不计座），且"空白"在候选层面（未填价格）与组合层面（未选候选）含义不同。

**消解（D-03、C5）**：五态 + 两个层面（组合层决定"有没有选"，价格层决定"这个票档怎么算"）

| 层面 | 状态 | 语义 | 计入金额 |
|---|---|---|---|
| 组合层 | 未选择 | 这个位置没选任何候选 | 否 |
| 组合层 | 已选择 | 选了某候选 | 是 |
| 价格层 | 未填 | 该票档不参与/未考虑 | 否，不警告 |
| 价格层 | 待估 | 要付费但没查到 | 否，**整笔标记待估** |
| 价格层 | 已定价（含 0） | 明确金额 | 是 |
| 价格层 | 不适用 | 该票档不占此费用 | 否，不警告 |

界面上这些状态必须**文本可辨**（不能只靠颜色），验收 AC-ENT-05/06、AC-SEL-12、AC-UX-06 守此条。

## FC-8 方案无限数量 vs 性能 —— **存在，已用"产品无限 / 工程有目标"消解**

**冲突描述**：D2 已裁决"方案数量不设上限"，但每套方案都要重算（引用候选 → 汇总 → 分摊），50 套 × 1000 候选 = 5 万次计算。

**消解（D-77）**
- 产品层：**不设上限**（不阻止用户）。
- 工程层：给出目标（50 套内流畅，200 套启用虚拟化），并允许在极端数量下给出提示。
- 阈值本身待用户确认（Q7）。
- 关键设计约束（留给实现）：方案汇总必须是**可缓存/可增量**的，不能每次全量重算 —— 但这是实现选择，不在需求内。

## FC-9（自查）"所有候选同时可见" vs 375px 不溢出 —— **存在，已裁决**

**冲突描述**：R2 要求"所有候选同时可见可比较"；C7 要求 375px 页面级不横向溢出。手机屏物理上放不下 N 个候选并排。

**消解（AC-UX-04）**
- 桌面：并排（真正的"同时可见"）。
- 窄屏：**容器内**横向滚动 或 卡片分组 + 关键列固定 + 快速切换对比。
- 需求层只保证：**页面级不溢出**、**同一区段/同一住宿单的候选可在同一视图内切换比较**（不需要来回跳页面）。
- 明确不为窄屏承诺"N 列并排" —— 那是不可能需求。

## FC-10（自查）"撤销" vs "编辑自动保存草稿" —— **存在，已裁决**

**冲突描述**：草稿是持续自动写的；撤销是回退编辑。若撤销也回退草稿，则草稿可能回到很旧的状态；若草稿不回退，刷新后撤销的效果消失。

**消解（D-105、AC-DAT-16）**
- 撤销作用于**当前内存中的编辑**，撤销后草稿按当前状态继续写入（即：撤销结果会被草稿保存下来）。
- 刷新后撤销栈清空，但**撤销后的内容仍在**（因为草稿已是最新）。
- 这两条让"撤销 + 自动草稿"语义自洽，不会出现"撤销了但刷新又回来"。

## FC-11（自查）"金额可为空（待估）" vs "整数分计算" —— **表观冲突，已裁决**

**冲突描述**：C4 要求整数分，待估要求"没有金额"。若用 0 表示"没有金额"，则违反 C5。

**消解（D-33、C5）**：金额类型是"可为空"，空 ≠ 0。所有计算在"非空金额"上做整数分运算；待估项在合计中**缺席**（不是 0），并单独计数。实现层（骨架已有 `parseAmount`）只处理文本 → 整数分，"是否为空"由上层状态表达。

## FC-12（自查）"套餐整段占用" vs "用户想少住一晚" —— **存在，已裁决**

**消解（D-21）**：整段套餐**不可少住、不可拆晚**，这是套餐的经济实质。用户想少住 → 改选按间夜报价的候选。不做"套餐折算到更少晚数"。

## FC-13（自查）"返利要参与计算" vs "返利不减少应付" —— **存在真实冲突，已消解**

**冲突描述**：v7 的原始验收写的是"返利'连住 3 晚返 300'输入后，**总额确实少了 300**（不是只在备注里写一句）"；而 v8 的口径规则说"返利不减少应付、只进入决算口径"。若照字面实现 v7，会造成两个真问题：①**方案对比失真**——同样是"返 300"，能返利的方案看起来更便宜 300，但用户下单时仍要付全款，"当场掏多少钱"这个更常见的决策依据被掩盖；②**与正式预算/支付不一致**——正式预算记的是应付，记账记的是实付，返利若在预算层就减掉，三处数字互相矛盾，违反 C10。

**消解（D-38、D-38a）**：返利仍然**必须参与计算**（满足 v7 的原意：不是只写备注），但落在正确的口径里，且提供两种可切换的对比口径：

| 口径 | 公式 | 含义 |
|---|---|---|
| 不含返利（默认） | Σ 应付 | 当场要掏多少钱 |
| 含预期返利 | Σ(应付 − 待收返利) | 最终更划算 |

- 只要有任何方案带返利，界面必须提示"可切换含返利口径"，让"返利确实被算了"这件事**可见**，而不是悄悄消失。
- 返利还进入"待收返利"（= 预计 + 已确认，**不含已到账**）与"预期净成本"，到账后进入最终净成本（D-38、FC-18）。
- 验收改为 AC-ENT-04（返利可计算、可展示、可汇总、可切换口径），与 AC-LED-06/07/07a 一起守住"返利不能只写在备注里"与"返利不被扣两次"两个意图。

**为什么不能简单照 v7 字面实现**：v7 的"总额"是一个含混的词。这句话的正确解读是"返利必须被系统记住并参与某个有意义的计算"，而非"必须从应付里减掉"。v8 把这句话拆成三个明确的数据流，既保住原意，又消除口径矛盾。

## FC-14（v8.1 自查）"住宿单整段套餐" vs "房间项独立候选" —— **存在真实冲突，已消解**

**冲突描述**：v8 既要求"同店不同房型能并排比差价"（必须让房间项各自有候选），又要求"整段套餐整段占用住宿单"（套餐是一口价，不分房型）。当住宿单既有两个房间项、又被选了一个 3 晚套餐时，到底该算 900+2100=3000，还是算套餐 3000，还是算 6000？v8 原文没有回答。

**为什么这是最危险的冲突**：两种错法都"看起来正常"——
- 若相加：用户以为选了套餐省钱，实际付了双份，而界面不会报错；
- 若取较小值：用户无法解释总价从哪来，也无法知道当前生效的是哪个候选。

**消解（D-21 第 6~11 条、D-22a、D-25、I-18、BC-16）**
- 两类候选分离：房间候选挂房间项，整段套餐挂住宿单。
- **互斥**：任一时刻只有一个模式生效，住宿合计 = 二者之一，不求和、不取小。
- 被压制方连附加项一起不参与计价（D-22a），避免"套餐已含早，却又算了一次房型附加的早餐费"。
- 冲突必须显式（L1），不能让用户在选择另一模式时静默覆盖。

**2026-11-09 复审补充（D-21 第 8a~8f 条、BC-23）**：原裁决只说了"互斥"，没说切换与删除之后用户的选择去哪了。复审补上"**当前生效计价模式**"与"**被保留但未生效的选择**"这对概念：
- 已选套餐后再选房间候选 → **阻止并提示**（不是静默改成冲突态）。
- 从逐房间切到套餐 → 房间候选与附加项**保留但不计价**，**不产生 L1**（这是用户显式确认的合法切换）。
- 删除套餐 → **自动回退并恢复**此前的逐房间选择与附加项。
- 任何切换都**不得静默删除**原有选择（C3）。
这四条的目的是：让"互斥"只作用于**计价**，不作用于**数据**。v8.1 原文把两者混在一起，会导致"换个模式，昨天的房间候选没了"。

## FC-15（v8.1 自查）"区间含首尾" vs "住宿按晚" —— **存在真实冲突，已消解**

**冲突描述**：D-41 说区间含首尾，D-42 说住宿按晚。9/29 入住、10/2 退房时，前者给 4 天，后者给 3 晚。v8 用一句"住宿即按晚、住宿一晚 = 一天"想抹平差异，但这句话本身是错的——**住宿一晚不等于一个自然日**：退房日是一个自然日，却不是一晚。

**消解（D-46、I-17、BC-17、AC-SEL-17～21）**
- 住宿用半开区间 `[入住, 退房)`；普通跨日费用用闭区间 `[起, 止]`。
- 住宿计价单位显式定义为"晚"；退房日归属金额恒为 0。
- 分摊分别以"晚"和"自然日"为分母，两者互不套用。
- 跨月不加特殊规则，按日历日差计算晚数。

**残留风险**：用户可能仍会疑惑"为什么租车 4 天、酒店 3 晚"。这属于现实本身的差异，D-46 要求在界面上对住宿显示"x 晚"而非"x 天"，用词区分即可，不需要额外规则。

## FC-16（v8.1 自查）"L1 不计入合计" vs "L1 也要能看到金额" —— **存在真实冲突，已消解**

**冲突描述**：D-90 说 L1 条目"不计入合计"，但用户仍需要在列表里看到这条的金额（否则无法判断要不要修）。而 v8 的 D-35 又说优惠超额时"按 0 计"——三句话放在一起，实现者很可能写成"存一个 0 并计入"，导致异常被伪装成免费。

- "因异常未计入 Y"必须单独汇总展示，让用户看到"有 3 条共 1500 元没算进去"。
- 优惠超额的 0 元必须与"明确 0 元"（D-32）在状态上区分，并强制附文案"0 元不代表已确认免费"。
- D-55 的逐状态表把"哪些维度缺席"写死，杜绝"某个维度排除了、另一个维度却静默计入"。

## FC-17（复审自查）"Σ 每日 = 总费用" vs "范围外费用计入总额但不进逐日视图" —— **存在真实冲突，已消解**

**冲突描述**：v8.1 同时写着 C4/D-43/R4/I-01 的 `Σ 每日合计 = Σ 每类合计 = 总费用` 和 D-45/AC-SUM-06 的"范围外费用计入总额、不进逐日视图"。旅行 9/29–10/2、范围内 3000、范围外 500 时：逐日视图显示 3000、总额显示 3500、类别合计 3500。**逐日之和不可能同时等于总额**。

**为什么这是最容易被忽视的冲突**：它不产生报错，只会产生"总额对、逐日对，但两者差 500"的现象。用户会先怀疑"是不是有一段没显示"，然后去翻数据，最后失去对工具的信任；实现者则最常见的做法是"把差额补到某一天"——这会让某一天的金额凭空变大，比不显示更糟。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| A. 范围外费用也摊进逐日视图 | 等式成立 | 违反 D-45 与 D-109（范围外数据不该出现在范围窗口里），且用户看不懂"10/2 之后还有钱" | ❌ |
| B. 范围外费用不进总额 | 等式成立 | 缩短日期就会改变总额，直接违反 C3 | ❌ |
| C. 承认日期维度需要"范围外合计 R"补平 | 诚实、可核对、不动 D-45 | 多一个必须展示的数 | ✅ 采纳 |

**消解（D-43、D-45、D-55、I-01、AC-SUM-06/07/12）**
- 日期维度等式改为 `Σ 范围内每日合计 + R = 总费用`，R 独立展示、可点开看明细。
- **明令禁止**把 R 分配到范围内任何一天（尤其"摊到最后一天"）。
- 类别维度、人员维度各自独立成立，不受 R 影响：`Σ 每类 = 总费用`、`Σ 每人 = 总费用 − Z`。
- 三个数（Y / Z / R）互不抵扣（I-21）——这条防的是实现者用"总费用 − 范围外 − 未分摊"去反推某个分量。

## FC-18（复审自查）"待收返利 = 预计 + 已确认 − 已到账" —— **公式本身错误，已修正**

**冲突描述**：D-38 明确三种返利状态互斥，只有"已到账"进净成本；但 D-84 的公式又把"已到账"从待收里减掉一次。到账后待收会变成 0 − 200 = −200（或 200 − 200 = 0，取决于是否先把预计状态清空），无论哪种实现，**同一笔返利都被扣了两次**：一次在待收里，一次在净成本里。

**为什么这是真实冲突而非措辞问题**：返利的状态是**互斥单值**。一旦改为"已到账"，它就不再是"预计"或"已确认"，公式的减项对象已经不存在了。继续减，等于对一笔不在集合里的钱做减法。

**消解（D-38、D-84、I-19a、AC-LED-07/07a）**
- `待收返利 = Σ(预计) + Σ(已确认)`；`已到账返利 = Σ(已到账)`；两集合不相交。
- `净成本 = 实际支付 − 已到账返利`；`预期净成本 = 应付 − 待收返利`。
- 状态迁移是**取值替换**，不是新增记录；迁移后 `待收返利 ≥ 0` 恒成立。
- AC-LED-07a 用"预计 200 → 已确认 → 已到账"三步守"不重复扣减"。

## FC-19（复审自查）"单一分摊不变量" vs "参与人为空 / L1 排除" —— **存在真实冲突，已消解**

**冲突描述**：I-03 原写"任一费用条目的 `Σ 分摊明细 = 该条目应付金额`"。但 D-50/D-55 允许参与人为空（此时该条目分不到人，人员分摊之和为 0 ≠ 300），D-55/D-90 又允许 L1 条目从汇总排除（此时它根本不参与守恒）。三种情形下同一条等式分别成立、不成立、不适用。

**消解（D-51a、I-02a、I-03、BC-09、AC-SUM-07/08）**
- 先分**三类金额**：条目原始金额 / 日期分摊明细 / 人员分摊明细，三者互不叠加。
- **日期分摊守恒**：正常计入汇总的条目，日期明细之和 = 条目原始金额（含 0 元、参与人为空、范围外条目）。
- **人员分摊守恒**：参与人合法非空时成立；参与人为空时人员明细为**空集**（不是一串 0），金额全进 Z；L1 条目**不参与**上述任何守恒。
- 保留 `Σ 每人合计 = 总费用 − Z`。

## FC-20（复审自查）"预算行被删除 → 支付转待处理" vs "旧版本只增不改、支付不转移" —— **存在真实冲突，已消解**

**冲突描述**：D-87 第 6 条说预算行删除后其下支付转"待处理"；但同一条第 1 条与 D-72a 第 1 条说"支付不自动转移""旧版本只增不改"。当刷新预算、新版本不再包含某行时，两句给出相反结论：V1 的 3 笔支付到底还挂在 V1 的 A 上，还是变成待处理？原文没有区分"新版本不含该行"与"该行被真正删除"。

**为什么这个歧义危险**：它是**静默改写历史**的入口。如果刷新预算就产生待处理支付，用户的每一笔历史付款都会在每次刷新后被"拔锚"，而"待处理"看起来像"系统发现了问题"，用户会去归位，于是历史归属被永久改写。

**消解（D-87 第 6 条情况 A/B、D-72a 第 4 条、BC-21、I-20a、AC-LED-14/14a/14b）**
- **情况 A（刷新后新版本不再包含该行）**：旧行保留、支付归属不变、**不转待处理**、新版本不自动继承；想要对应新预算必须显式逐笔转移。
- **情况 B（预算行被真正删除）**：支付不删除、转待处理、逐笔显式归位、保留原始金额/日期/类型/来源。
- 两种情况的**操作语义不得合并**。
- 附带解决 D-72a 与"长期追溯"的张力：旧版本被清理时，允许保留**最小历史归属快照**（版本序号 + 行标识与名称 + 行金额 + 支付金额），仅用于显示追溯、不参与计算。

## FC-21（复审自查）"整单返利有基数" vs "单项/多项返利无基数" —— **存在真实冲突，已消解**

**冲突描述**：D-86 只给整单返利写了"适用金额 = 已定价且无 L1 的条目应付之和"，单项与多项返利没有写基数。示例：原价 1000、商家优惠 100、平台优惠 100、应付 800，返利 1% —— 按 1000 算得 10 元，按 800 算得 8 元，差 25%，而两处都"符合现有条文"。

**消解（D-86 计算基数、BC-19a、I-19b、AC-CAL-17～23）**
- 三种范围的基数**统一为实际应付（②）**：单项 = 该条目应付；多项 = 被勾选条目应付之和；整单 = 方案内符合条件条目应付之和。
- 基数**不含**待估项与 L1 项；**含**明确 0 元条目，但贡献为 0（写死，不留解释）。
- 固定型不受基数影响。
- 同一笔返利记录不得把同一条目算两次；同一条目被两笔不同返利覆盖是合法的。

## FC-22（第二轮复审）"预算外支出"既是支付归属又被当作额外金额 —— **存在真实冲突，已消解**

**冲突描述**：D-80 把"预算外支出"定义为**支付记录的一种归属取值**；但 D-87a 的② 与旧 I-20b 把"全程已付现金"写成 `Σ 全部支付 + 预算外支出`。若预算内支付 5000、预算外支付 300，按该式得 5600，而真实现金流出是 5300——**预算外那 300 被算了两次**。

**为什么容易犯**：D-82 说"预算外支出**单列**"，"单列"被读成"另加一笔"。但"单列"是**展示上的分组**，不是**求和时的增量**。这两件事在文字上只差一个"加"字，在结果上差整整一个预算外金额。

**备选**

| 方案 | 利 | 弊 | 结论 |
|---|---|---|---|
| A. 保留 `全部支付 + 预算外支出` | 与"单列"字面一致 | 重复计算，且随预算外占比增大而失真 | ❌ |
| B. 预算内、预算外分成两个互不相交的金额池 | 概念上"两本账" | 需要同时维护两个集合的完整性，易漏记、易重复归 | ❌ 更复杂 |
| C. 支付为**统一集合**，"归属"只是取值；汇总一律从该集合出发 | 无重复计算，拆分式天然成立 | 需在 D-80 显式声明集合口径 | ✅ 采纳 |

**消解（D-80 集合口径、D-87a、I-20b、I-20c、AC-LED-19a/19b）**
- 支付记录是统一集合；`Σ(归属=预算行) + Σ(归属=预算外) = Σ 全部支付`（拆分后相加才等于总数）。
- 「全程现金总额」必须先用"流出类"过滤再减退款（**不得**用"全部支付 − 全部退款"，那未排除退款记录本身，见 FC-25）；公式定义见 D-80b。**不得**再另加预算外。
- 「全程现金总额」必须扣退款，与 D-81 的净额性质一致（否则"付 5000 退 2000"会显示 5000）。
- 待处理支付**不计入**「当前版本已付」、不计入预算内已付、不计入预算外，但**计入「全程现金总额」**（第三轮复审修正），且必须单独可见（FC-27）。

## FC-23（第二轮复审）"参考差额"被命名为"已付"却定义为差额 —— **存在真实冲突，已消解**

**冲突描述**：D-87a 的第三个指标计算式是 `全程现金总额 − 当前版本应付`，这是**差额**；但它被列进"三个已付"，且原文说"只有一个预算版本时三个指标数值相同"。V1 预算 5000/已付 4800、V2 预算 6000/已付 0 时：①=0、②=4800、③=−1200。只要应付不为 0，③ 就不可能等于已付；"三数相同"在任何有预算的情况下都不成立。

**为什么必须改**：把差额当"已付"展示，用户会看到一个负数"已付"，或把它误读成"待付"。而"待付"只应由「当前版本待付」给出（`max(0, 应付 − 已付)`），两者语义完全不同。

**消解（D-87a、AC-LED-19/19c、术语"参考差额"）**
- 该指标正式命名 **参考差额**，明确"是差额不是已付"，可为正/零/负，正负号含义须在界面写明。
- 删除"三数相同"：改为"无预算外、无待处理时「当前版本已付」与「全程现金总额」数值相等；「参考差额」始终独立为差额"。
- 禁止把「参考差额」显示为"待付"，禁止把三者合并成一个"已付"。

## FC-24（第二轮复审）"历史版本只读" vs "删除某预算行" —— **存在真实冲突，已消解**

**冲突描述**：D-72a 第 1 条说历史版本不可编辑；AC-LED-14a 却要求"用户真正删除 V1 中的那条预算行"（V1 已被 V2 取代，属历史版本）。同一个操作既被禁止又被要求，实现无法同时满足。

**消解（D-72a 第 1 条、D-87 第 6 条前置约束、AC-LED-14a/14c）**
- 破坏性删行**只允许发生在"当前可编辑版本"**；历史版本的删行入口不存在或禁用，并说明"历史版本不可编辑（D-72a）"。
- AC-LED-14a 场景改为"在当前可编辑版本中删除已有支付的预算行"；新增 AC-LED-14c 专门守"历史版本不可删行"。
- 用户想删掉某行时，正确路径是**在最新版本里删**，再由情况 A/B 决定支付归宿——**冻结原则不因这一轮修订而被破坏**。

## FC-25（第三轮复审）"退款是支付记录类型之一" vs "现金汇总再减一次退款" —— **存在真实冲突，已消解**

**冲突描述**：D-80 把退款列为支付记录的类型之一；D-87a 的 ② 又写 `Σ 全部支付 − Σ 全部退款`。若"全部支付"已经包含退款记录，则退款被处理两次。原始支付 4800 + 退款 800：先加后减得 4800，减两次得 3200，**都不是正确的 4000**。

**为什么这是最容易漏的**：两种错法都不会报错，且都"看起来合理"。第三种更隐蔽的错法是"退款记成负数金额"——那样 `Σ 全部支付` 恰好等于 3200，与期望差 800。

**冲突描述**：D-80b 规则 3 写"默认归属 = 押金原记录所在的预算行与版本"（系统已确定），标准场景又写"必须由用户显式选择；系统不得替他决定；默认按规则 3 取 V1"。两句话对同一动作给了两种要求：默认要不要用户确认？

**消解（规则 1 与规则 3 重写）**
- 明确区分**预选**与**决定**：系统只提供**预选值**，**用户确认后**该次转消费才生效、才允许保存。
- 于是"默认归 V1"与"必须显式确认"不再冲突：预选 V1 是省事，确认是生效条件。
- AC-LED-19o 的期望相应改为"未确认归属 → 不允许保存"。

**附带术语问题（同轮修正）**：规则 2 与 AC-LED-19m 曾把历史版本金额称为「**当前版本已付**」——当前版本是 V2，V1 的钱不该叫"当前"。改为三分：**预算行已付** / **指定预算版本已付** / **当前版本已付**（仅指最新版）。D-80b 汇总表的名目同步。

## FC-40（第七轮复审）押金原属预算外或无归属时，默认规则不完整 —— **存在真实冲突，已消解**

**冲突描述**：规则 3 只假设"押金最初挂在某个预算行和版本"。但 D-80 允许押金的归属对象是**预算行 / 预算外 / 空**三种。押金原本就是预算外支出、或原本待归位时，转消费该默认到哪里？原文没有答案，实现只能猜。

**消解（D-80b 规则 3 扩为三情形）**
- **原属某预算行** → 预选同一行、同一版本。
- **原属预算外** → 预选**预算外消费**。
- **原无归属（待归位）** → **没有可预选值**，必须由用户从"预算行 / 预算外"中明确选择，否则不允许保存。
- 新增 AC-LED-19o2（原属预算外）与 AC-LED-19o3（原无归属）守这两种情形。

## FC-41（第八轮复审）禁令下的残余复写与术语失配 —— **存在真实冲突，已消解**

**冲突描述**：第七轮声称已落实"禁止复写公式"，但仍有三处残余，另有一处术语未同步：

1. **I-07 说明列**仍带 `消费实际支付 − Σ(状态=已到账的返利)`——即便处于"解释旧写法"的语境，它仍在 I-07 条目内，而 BC-34/BC-36 对 I-07 是**无条件**禁止。
2. **I-20b** 仍用文字"全程现金中不含押金的部分减去当前版本应付"复述参考差额的计算关系——不是算式，但仍是第二处定义。
3. **AC-LED-19b** 仍写通用式 `Σ 流出类 − Σ 退款`；BC-34/BC-36 明确把"验收条目"列入禁止范围。
4. **I-06** 写"已付分三层：某行已付 / 当前版本已付 / 消费实际支付"，与 BC-38 的三种粒度（预算行已付 / 指定预算版本已付 / 当前版本已付）不符：漏了「指定预算版本已付」，又把「消费实际支付」误并入已付粒度。

**为什么"解释性复述"也要删**：规范文本里不存在"只是说明、不算定义"的豁免。读者摘取 I-07 一行去实现时，看到的就是那个公式；两处并存时，"哪一处是规范"这个问题仍然无解。

**消解（I-07、I-20b、I-06、AC-LED-19b）**
- **I-07**：说明列改为不含算式的文字（"此前说明列曾带算式，违反 BC-34/BC-36，现已改为文字"）。
- **I-20b**：参考差额只保留"是差额不是已付、可为负、恒不含押金、与 Q2 无关"四条性质，计算公式指向 D-80b。
- **I-06**：改为与 BC-38 一致的三种粒度，并显式声明「消费实际支付」是**另一项独立指标**，不属于已付粒度、不得顶替「指定预算版本已付」。
- **AC-LED-19b**：保留 4800 / 800 / 4000 / −2000 等具体数值与两个错误值，删除通用算式，改为"取数规则见 D-80b"。

## FC-42（第九轮复审）"预算版本"被写成所有转消费的必填项 —— **存在真实冲突，已消解**

**冲突描述**：D-80b 规则 2 已明确"归属预算外时只进消费实际支付、不进任何版本的已付"，但三处表述仍把版本当成通用必填：

1. **BC-35** 写"押金转消费必须有归属对象（预算行或预算外）**与归属版本**"——预算外消费本身没有版本概念。
2. **D-80b 小节标题**写"必须落到具体的预算行与**预算版本**"，与"允许归属预算外"不协调。
3. **规则 1** 只说"指定归属对象"，没说明版本何时必填，读者容易理解成两种归属都要填版本。

**为什么这不是措辞小事**：领域模型若照 BC-35 建字段，会得到一个"预算外归属也必须带版本"的约束——要么被迫给预算外编造一个假版本，要么实现时不得不违反不变量。这是**会落到表结构上的歧义**。

**消解（BC-35、D-80b 标题、规则 1 与规则 2）**
- **归属对象对所有转消费必填**；**预算版本只在归属为预算行时必填**；选预算外时**不得要求版本**。
- 标题改为"必须有明确的归属对象；只有归属预算行时才需要预算版本"。
- 规则 2 在两种归属后各自标注"此时版本必填 / 此时无版本"。
- BC-35 的违反后果补上"或对预算外归属错误地要求填写版本"。

## FC-43（第十轮复审）通用留痕规则与验收覆盖未对齐 —— **存在真实冲突，已消解**

**冲突描述**：D-80b 规则 4 已写成"任意原归属→目标归属组合都必须留痕"，但验收只覆盖了两类：

| 变更方向 | 第九轮时的验收 |
|---|---|
| 预算行 → 预算行（跨版本 V1→V2） | AC-LED-19n 覆盖 |
| 预算行 → 预算外 | AC-LED-19q 覆盖 |
| 预算外 → 预算行 | AC-LED-19q 覆盖 |
| **预算行 A → 预算行 B（同一版本内换行）** | **未覆盖** |
| 空 → 预算行/预算外 | AC-LED-19o3 覆盖 |

**为什么"同版本换行"必须单独覆盖**：跨版本换行（V1→V2）同时改变了行与版本，实现者容易把"归属变更"理解成"版本迁移"；而同一版本内从住宿行换到交通行，**版本不变、只有行变**。若实现只按版本处理，这种变更会静默丢失审计，且两行的「预算行已付」不会正确增减。

**消解（AC-LED-19q 增设第三方向、规则 4 列明覆盖组合）**
- AC-LED-19q 增设 ③：**预算行 A → 预算行 B（同一版本内）**，期望值写明"原行=V2 住宿行、目标行=V2 交通行、版本前后同为 V2"，并要求两行已付正确增减、V2 合计不变。
- 规则 4 显式列出首版需要覆盖的组合，并说明**"预算外→预算外"不构成变更**——因为 D-82 的预算外支出不按具体消费对象细分，来源与目标无差别（若将来引入细分则扩展）。

| 修订 | 建模影响 | 风险点 |
|---|---|---|
| T5-P1-01 公式单一来源 | 所有现金公式的**唯一定义处是 D-80b**；I-06/I-07、D-36 ③ 只做引用，不重复定义 | 同一公式出现两处定义，改一处忘一处，实现取哪个都可能错（BC-34、FC-32） |
| T5-P1-02 Q2 双公式入不变量 | I-20b 必须同时给出 Q2=A 与 Q2=B 两条完整公式；"由 Q2 决定"这句话本身不是公式 | Q2 选 B 时按不变量算不出 AC-LED-19e 的 6500（FC-33） |
| T5-P1-03 归属不是关联 | Payment 与 BudgetLine 之间**只有一条**可选关联；归属对象是属性取值，待处理是"归属为空 + 待归位" | 画成三条关联线会诱导实现建三个外键或三张关联表（FC-34） |

### 5.0g 第六轮复审对建模的影响（2026-11-09 第六轮）

> 本轮主题仍是**规范一致性**：公式定义已收敛到 D-80b，但"谁有资格定义公式"这条规则自己没被遵守；另外押金转消费缺了归属维度，导致公式无法取值。

| 修订 | 建模影响 | 风险点 |
|---|---|---|
| T6-P1-01 转消费归属 | 押金的转消费标记需要**归属对象**（预算行或预算外），**归属预算行时才需要版本**；同一笔押金可拆多份，各份归属可不同 | 缺归属时「当前版本已付」无法计算；若默认归最新版本，历史版本的已付会被抽走（BC-35、FC-35） |
| T6-P1-02 公式单一出处 | 只有 D-80b 定义公式；其余位置的公式文字必须删除，改为"指标名 + 指向" | 两处定义并存时，改一处忘一处，无人能判断哪处是规范（BC-34 收紧、FC-36） |
| T6-P2-01 概念三分 | 消费实际支付 / 押金池 / 全程现金总额是三个独立派生量，各有自己的求和范围 | 把"押金待退"当成已付的一部分，会让待付与净成本同时失真（FC-37） |

### 5.0h 第七轮复审对建模的影响（2026-11-09 第七轮）

> 本轮是"规则已写下、但正文没执行"的清理轮。三条都不是新业务规则，而是让既有规则真正生效。

| 修订 | 建模影响 | 风险点 |
|---|---|---|
| T7-P1-01 禁令落地 | 派生指标的公式只存在一处；代码实现应直接对应 D-80b，不从其他章节抄 | 副本被误当规范，改一处忘一处（BC-36、FC-38） |
| T7-P1-02 预选与确认分离 | 押金转消费需要一个"预选归属 + 用户确认"的两步交互；确认是生效条件，不是可选步骤 | 只做预选不做确认，等于系统替用户决定；只做确认不做预选，录入成本过高（BC-37、FC-39） |
| T7-P1-03 已付三分 | 派生层需要三个聚合粒度：按行 / 按指定版本 / 按当前版本；不得用"当前版本"指代历史 | 多版本下"V1 已付"被叫成"当前版本已付"，用户会以为新版本已付款（FC-39 术语段） |
| T7-P2-01 押金原归属三情形 | 押金的归属对象（预算行/预算外/空）决定转消费的预选值；空时必须由用户选 | 只处理"原属预算行"，另两种情形实现会崩溃或静默给错归属（FC-40） |

### 5.0i 第八轮复审对建模的影响（2026-11-09 第八轮）

> 本轮是**收尾轮**：没有新业务规则，只有禁令的彻底执行与一处术语同步。

| 修订 | 建模影响 | 风险点 |
|---|---|---|
| T8-P1-01 禁令彻底执行 | 实现层只从 D-80b 取公式；I-06/I-07/I-20b 与验收条目内不得出现任何可被直接抄写的算式或等价文字 | 残余副本被当作规范直接实现，与 D-80b 分叉（BC-34/BC-36、FC-41） |
| T8-P1-02 已付三分术语 | 「消费实际支付」是独立指标，不是已付粒度；已付只有按行/按指定版本/按当前版本三种 | 用「消费实际支付」顶替「指定预算版本已付」，多版本汇总会串（BC-38、FC-41） |
| T8-P2-01 归属变更通用留痕 | 归属变更审计需要覆盖任意"原归属→目标归属"组合，字段含变更前后归属、金额、时间、确认人 | 只对 V1→V2 留痕，预算外↔预算行变更无审计（FC-41 附项） |

### 5.0j 第九轮复审对建模的影响（2026-11-09 第九轮）

> 本轮只修一处会落到表结构上的歧义：版本字段的适用条件。

| 修订 | 建模影响 | 风险点 |
|---|---|---|
| T9-P1-01 版本适用条件 | 转消费的归属需要两个字段：**归属对象类型**（预算行/预算外）与**归属版本**；后者**仅当类型为预算行时非空**，预算外时为空 | 若无条件要求版本，预算外归属会被迫编造假版本，或实现时违反不变量（BC-35、FC-42） |
| T9-P2-01 建立归属也要审计 | 归属审计不只覆盖"变更"，也覆盖"首次建立"（原归属为空 → 目标归属）；字段含变更前/后归属、金额、时间、确认人 | 首次建立被当作"没有变更"而跳过留痕，后续无法追溯押金去向（AC-LED-19o3） |

**v8.1 新增实体的存在理由**

- **E10a / E10b 必须分开**：房间候选的适用范围是"一个房间项"，整段套餐的适用范围是"整个住宿单"。若混为一个实体靠标志位区分，极易在"套餐生效时是否还要算房间候选"上出错，而这条错误会直接导致双倍计费（I-18）。
- **E13a 必须显式存在**：Z 不是"忘了算"的残差，而是必须展示的量（D-55）。不给它名字，实现时极易被"顺手分摊掉"。
- **E15a 必须显式存在**：支付需要稳定的归属锚点。直接挂"方案"则方案一变支付失去意义；直接挂"费用条目"则快照失去意义（D-87）。

│
├── 候选 Candidate
│      ├──(一对多)── 价格项 PriceItem ──(多对一)── FareTier

│
├── 正式预算 Budget（快照，带版本链）
│      └──(一对多)── 预算行 BudgetLine                    ← v8.1：支付唯一锚点
│                        ├──(一对多)── 支付记录 Payment
│                        └──(一对多)── 返利记录 Rebate（适用范围=单项/多项时）
│
├── 支付记录 Payment
│      ├──(可选 多对一)── 预算行 BudgetLine        ← 归属对象取值①：计划内支付
│      ├── 归属对象取值②：预算外支出（不挂任何 BudgetLine）
│      └── 归属对象取值③：空（不挂任何 BudgetLine）
│              └─ 归属状态 = 待归位 → 即"待处理支付"（状态，不是关联）

**四段关键关系的形态（v8.1 修订）**

> **第六段（第三轮复审补充）**：**补偿收入 → 与任何汇总无关**。E16a 只是"超过原支付金额的赔付/理赔"的留档记录，**不建立到 Payment 或 BudgetLine 的关联**，也**不参与** ③ 实际支付、⑤ 净成本、预算侧对比与退款额度计算（D-40）。这样既满足"不能静默丢弃这笔钱"，又不把它变成收入管理（Won't #11）。

> **关于"支付 → 预算行"的画法（第五轮修正）**：上图刻意**只画一条实线关联**——`Payment ──(可选 多对一)── BudgetLine`。预算外与待处理**都不是关联关系**，而是 Payment 上"归属对象"这一属性的另外两个取值；待处理更只是"归属为空 + 待归位状态"的表现。旧图画成 `BudgetLine | 预算外支出（多对零）| 待处理（多对零）` 三条并列线，会让人误以为存在三种不同的关联，与 FC-31、BC-33 的结论不符。

1. **方案 → 候选/房间候选/整段套餐**：**引用**（弱引用 + 可空）。删除候选造成悬空引用 → L1（D-71）。方案对住宿的选择粒度是**房间项**，不是住宿单整体——除非选的是整段套餐。
2. **正式预算 → 候选**：**无引用**（快照副本）。只保留"来源候选"的可选回溯标识（便于"现价对比"），但**不因候选变化而改金额**（D-72）。
3. **支付 → 预算行**：**可选多对一**（这是 Payment 与 BudgetLine 之间**唯一**的实体关联）。**归属对象**是 Payment 的一个属性，取三种值：**正式预算行**、**预算外支出**、**空**；**归属状态**是另一个属性，取**已归属 / 待归位**。于是：
   - 计划内支付 = 归属对象为预算行 + 已归属（关联线指向某 BudgetLine）；
   - 预算外支出 = 归属对象为预算外 + 已归属（**无** BudgetLine 关联线）；
   - 待处理支付 = 归属对象为**空** + **待归位**（**无** BudgetLine 关联线）。
   **不存在"直接挂候选"或"直接挂方案"**（D-80、D-87）。待处理**不是**第三种关联，也不建独立实体。
4. **房间候选 vs 整段套餐**：**互斥**。一个住宿单同一时刻只允许其中一类生效（D-21 第 8~9 条、I-18）。

## 5.3 关键业务约束

| 编号 | 约束 | 违反后果 |
|---|---|---|
| BC-01 | 一个区段在同一方案中只能激活一个候选（套餐覆盖的子区段除外） | 重复计费 |
| BC-02 | 一个套餐候选覆盖的区段，不得再被其他候选占用 | 重复计费 |
| BC-03 | 同一住宿单的日期区间必须连续；房间项共享区间 | 分摊无法计算 |
| BC-04 | 同一成员同一晚最多属于一个房间项 | 人员双占，成本不可信 |
| BC-05 | 整段套餐不可少住/拆晚 | 金额与报价不符 |
| BC-06 | 一个价格项的比例基数必须是同候选上的另一个票档，且不得循环引用 | 无限递归 |

| **I-20a** | **"新版本不再包含某预算行"与"预算行被真正删除"是两种互斥的事件**：前者 `支付归属不变、不产生待处理支付`；后者 `支付转为待处理、归属为空`。不存在第三种语义 | D-87 第 6 条（v8.1 复审新增）。混为一谈会让历史支付被静默挪动 |
| **I-20b** | **只登记指标名、用途与约束，公式一律不在此处复写（BC-34/BC-36）**。四个现金量的定义处均为 **D-80b**：<br>• **当前版本已付**：范围为该版本预算行的流出类，扣除关联退款，并含该版本已转消费的押金（按归属对象判定）<br>• **全程现金总额 · Q2=A**：不含押金占用<br>• **全程现金总额 · Q2=B**：含押金占用，押金与押金退回相抵<br>• **参考差额**：是差额不是已付；可为负；**恒不含押金、与 Q2 无关**（公式见 D-80b）<br>• **最终净成本**：见 I-07 | 必须成立的三条约束：① 删除含支付的预算行后全程现金总额**不变**，待归位支付归位后**不得二次增加**（I-20c）；② Q2 取 A 或 B，**参考差额结果必须相同**；③ 押金只影响全程现金总额这一个量，**不影响当前版本已付与参考差额**。**公式定义处：D-80b，本行不重复**（第七轮彻底去公式化） |
| **I-20c** | 支付记录是**统一集合**；归属对象只有三种（预算行 / 预算外 / **空**），"待处理"是**归属为空 + 待归位**的状态而非第三种归属值：`Σ(归属=预算行) + Σ(归属=预算外) + Σ(归属=空) = Σ 流出类`；"预算外支出"不是支付之外的另一笔金额；**待处理支付不计入当前版本已付、不计入预算内已付、不计入预算外，但计入全程现金总额**（删除预算行不得让全程现金下降），且归位后不得二次计入 | D-80、D-87a（第二轮新增；第三轮修正待处理支付的处理；**第四轮明确归属与状态分离**） |
| **I-20e** | **记录类型三分类互斥**：流出类（预付款/尾款/全款/其他）、冲减类（退款/押金退回）、押金类（押金）。任何汇总先按类型筛选再求和；`Σ 全部支付 ≡ Σ 流出类`；**退款只作减项，不得先计入流出再减一次** | D-80b（第三轮复审新增） |
| **I-20d** | 退款上限按关联方式判定：关联单笔 → `累计退款 ≤ 该笔金额`；关联预算行 → `累计退款 ≤ 该行非押金支付之和`；押金不占额度；`Σ 某行全部退款 ≤ 该行可退款支付之和` 恒成立 | D-40、BC-24（第二轮复审新增） |
| **I-21** | **Y / Z / R 三者互不抵扣**：`Y` = 因 L1 未计入总额、**且有金额可计**的部分之和（无金额的 L1 只计条数，不得按 0 计入，v8.1 第二轮复审修正）；`Z` = 已计入但参与人为空的金额；`R` = 已计入但归属日在旅行范围外的金额。三者可同时非零，任何"用一个数减另一个数来凑平"的做法都违反本不变量 | D-51a、D-55（v8.1 复审新增，第二轮复审修正 Y 的可量化口径） |

## 5.6 建模阶段的六个"必须坚持"（v8.1 四条 + 复审增补两条）

1. **单一真相 + 派生**：E12 的金额只来自候选；E13 分摊、汇总、净成本、未分摊 Z 全是派生。任何"把算出来的数存下来"的设计，都会在第一次改价时产生不一致（对应 I-04）。
2. **引用与快照不能混**：E14 引用候选，E15 不引用候选；E16 只引用 E15a（预算行）。这三条一旦混淆，C11 与 D-87 都不可能成立（对应 I-13、I-20）。
3. **状态必须落在类型上，不能落在约定上**：未选择 / 未填 / 待估 / 0 元 / 不适用 / **优惠超额异常 0 元** / **数量口径待确认**，用空字符串、0、null 互相冒充是这类项目最常见的缺陷来源（对应 I-14、BC-07、BC-22、FC-7）。
4. **"未分摊"必须是一等公民**（v8.1 新增）：Z 要有独立的存在形式与展示位。凡是"用默认值把空位填满"的实现，都会在用户不知情时编造出一个分摊结果——这比报错更危险，因为它看起来是对的。
5. **三个计数必须分开命名**（复审新增）：`Y`（因 L1 未计入）、`Z`（未分摊到人）、`R`（范围外已计入）。只要实现者手上只有一个"差额"变量，他就一定会用它去凑某一条等式（对应 I-21、BC-25）。
6. **"事件不同"必须建模成不同事件**（复审新增）：预算版本"不再包含某行"与"预算行被删除"；返利"改状态"与"新增一条返利"；住宿"切换计价模式"与"删除选择"。把语义不同的两件事压成一个状态变更，用户的历史就会被静默重写（对应 I-20a、BC-21、BC-23、FC-20）。
