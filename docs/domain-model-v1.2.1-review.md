## 2. P1 修复验证：退款关联引用纳入清理快照

### 2.0 缺口确认与修复概述

外部审查判定成立：v1.2 的清理预检只枚举 Payment.budgetLineId（归属）与 DepositConversion.budgetLineId（份额归属）两类引用，**未枚举退款记录 `refundTarget=预算行` 的 refundTargetId 引用**；E25/E25b 也只记录归属，不记录退款关联目标——清理后退款记录虽存在，但"它按整行关联还是单笔关联、当时关联哪一版哪一行"无法可靠恢复，I-20d 整行退款上限的历史解释随之断裂。

v1.2.1 修复 = **第三层快照 E25c + 预检三类主体 + 冲减类归属语义澄清**：

1. 预检 ③：`type=退款` 且 `refundTarget=预算行` 且 `refundTargetId ∈ 被清理版本的行实例集` → 生成 E25c（十字段，含 refundTarget 关联类型原样保留）。
2. **关联单笔不生成**：目标支付记录不被版本清理、永不悬空，关联语义天然完整；目标支付若曾归属被清理版本，上下文经"退款 → 目标支付 → 其 E25 → 行/版本"链恢复。
3. **未关联不生成**：无目标可悬空；未关联状态本身由活记录显式保留（D-40"显式提示"）。
4. **押金退回不适用**：恒关联押金本金（支付记录，永不悬空），无行引用。
5. **冲减类归属语义澄清**：冲减类不携带 ownershipType/attributionState（作用对象仅由 refundTarget 表达）——审查要求的"退款自身归属与退款目标不一致"场景由此**结构性不可能**，风险被结构消除而非依赖约定。

**清理 V1**：预检三类主体——① Payment 归属 V1 行：{PAY-01, PAY-02}；② DepositConversion 归属 V1 行：∅；③ refundTarget=预算行且指向 V1 行的退款：{REF-01}。

| E25 | (PAY-02, V1) | 同上，paymentAmountCents=4000 |

### 2.2 退款关联场景 R1~R7 逐场景验证

**R1 退款关联预算行、该行被清理**——即 §2.1 原例。快照 E25×2 + E25b×0 + E25c×1，共 **3 条**；关联语义与上限历史均可恢复。

**R2 退款关联单笔、目标支付归属被清理版本**
- 设定：PAY-01 预付 1000 → V1 住宿；REF-01 退款 500，refundTarget=具体支付，refundTargetPaymentId=PAY-01。
- 清理 V1：预检 ① {PAY-01}→E25×1；③ 无（REF-01 关联的是支付记录不是行）。**E25c ×0**。
- 清理后恢复链：REF-01 →（refundTargetPaymentId）→ PAY-01 →（E25）→ V1 住宿行。关联语义（冲减该笔）与行上下文均完整；**不生成 E25c 是正确行为**（无悬空引用；引用链可复原）。

**R3 退款自身归属与退款目标归属不一致场景**
- 结论：**结构性不可能**。冲减类不携带归属对象与归属状态（§4.11 澄清段），退款在所有公式中只经 refundTarget 路径取数（D-80b/D-81/D-87a），自身无归属可与其目标"不一致"。模型层面该不一致被结构消除；实现层也无需为其编写防御分支。
- 该澄清与冻结公式一致（退款只作减项、无归属取数路径），属解读性设计，不新增业务规则。

**R4 未关联退款**
- REF-01 refundTarget=未关联、refundTargetId=空。清理任何版本都不为其生成快照（无目标可悬空）；"未关联"状态由活记录显式保留并持续提示（D-40、AC-LED-10）。全程现金仍正确扣减该退款（Σ 退款与关联无关，D-80b 口径 B/C）。

**R5 押金退回**
- 恒关联押金本金记录（支付记录），无行引用；版本清理永不触碰支付记录 → 永不悬空 → 不适用 E25c。押金池口径不受影响（D-80b）。

**R6 关联行退款 + 多次清理 / 分批清理**
- 设定：REF-01（500）关联 V1 住宿行；另一版本 V2 有归属其行的支付与份额。清理 V1 → E25c(REF-01,V1)；后清 V2 → 只为当时指向 V2 的主体生成快照。键 (REF-01,V1) 与 V2 轮快照键互不相同，无重复、无覆盖。
- 退款金额不重复统计：E25c 不参与任何计算（DM-08）；REF-01 在全程现金中只扣一次（Σ 退款，与关联方式无关）。

**R7 清理失败与撤销清理（含 E25c）**
- 失败：三层快照与清理同批写入，任一步失败整批回滚——版本完整、无悬空引用、无 E25/E25b/E25c 残留。
- 撤销清理：数据快照恢复，本次 E25c 随回退消失；再次清理重新生成同键同内容快照。

### 2.3 P1 修复后的金额守恒检查

1. **退款只作减项（I-20e/D-80b）**：REF-01 在全部口径中只扣一次；关联方式（行/单笔/未关联）不改变其减项身份。清理前后全程现金总额不变。
2. **E25c 零参与计算（DM-08）**：E25c 全部字段不进任何现金指标；上限基数与累计退款的历史复原是**展示层推演**，不产生新的统计路径。
3. **上限语义不变（I-20d）**：清理后不能再对被清理行登记新退款（行不存在），上限的前向校验功能随行终止；其历史解释由 E25/E25c 复原（§2.1 要求 5）。
4. **押金退回与消费无关**：不因 E25c 引入任何新路径（D-80b 规则 3）。
5. **冲减类无归属**：不进入行已付/版本已付的任何取数路径（澄清段 ①），与 §7.5 指标登记表一致。

## 3. P2 修复：来源快照补计价状态

**审查判定成立**：sourceSnapshot 原结构只记"对象→候选"，缺两个影响实际计价的独立状态——住宿计价模式（stayModes，组合层持久状态、不可从候选选择推导，DM-01）与数量口径确认决定（quantityDecision，D-21 第 5c 条）。缺 stayModes 时"该版本按逐房间还是整段套餐生成"不可解释。

**修复后的结构**：

```text
sourceSnapshot = {
  snapshotAt: 时间,
  selections: [{ subjectType, subjectId, candidateId, quantityDecision? }],
  stayModes:  [{ stayId, mode }]
}
```

**论证**：

1. **quantityDecision 入 selections**：数量口径确认决定挂在 PlanSelection 上（§4.8 E22），是选择状态的一部分，随选择一起快照；候选级改判（写入候选 caliberChangeTrail）不属于选择状态，不入快照。
2. **stayModes 独立成列**：模式是组合层持久状态（DM-01），不在 selections 内；同一住宿单选中套餐候选但生效模式为逐房间的组合是合法状态，缺 stayModes 无法解释生成来源。
3. **价格不入快照**（保持 v1.2 决定）：历史时点价格本不可重建，版本行金额是快照真相；来源快照回答"按什么选择状态生成"，不回答"当时候选值多少钱"。
4. **策略甲的追溯路径**：来源方案持久持有 selections（含 quantityDecision）+ stayModes，刷新时点状态可查——但**方案被删除后**该路径断裂，来源展示降级为"来源方案已删除"（版本行快照仍完整）。若要求删除后仍可解释，可裁决"甲策略也始终生成同构快照"（同一结构，成本可控）——已作为备选写入 §4.10 字段行与 §15 P2-1，**随刷新策略一并裁决，不预设**。
5. **不退化候选 ID 列表**（审查要求）：扩展后 sourceSnapshot 足以回答"这个预算版本当时究竟采用了什么选择状态和计价模式生成"。
